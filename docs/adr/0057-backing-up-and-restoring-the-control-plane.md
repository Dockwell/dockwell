# 0057. Backing up the control plane, and restoring it

- Status: Proposed
- Date: 2026-11-08

## Context

The PRD's failure and recovery: losing the control server takes the panel and API offline, workloads keep running, and the control plane's state is backed up off-site automatically and copied, encrypted, to two other agents. `dockwell control restore` promotes any agent, and with no backup, state is rebuilt from what the agents report. Issue #34 asks for it, done when backups are taken on every change batch and at least hourly, a restore works from an agent's copy or an off-site one, state can be rebuilt with no backup at all, and the procedure is documented and tested in CI.

What there is to build on:

- **Two things hold the whole control plane.** The store (SQLite at `<data>/control/state.db`, or Postgres given `--database`) holds every resource and revision, changes, people, passkeys, tokens, settings and the audit log, and, sealed under the install's key, the key-encryption keys, the data keys, every sealed spec, the CA's key and the authenticator secrets ([ADR 0022](0022-secrets-encrypted-at-rest.md)). The install's key, `<data>/control/key`, opens all of it. The panel's ACME account under `<data>/control/acme` is made again on its own, and the local token is the CLI's on that server.
- **Backups and their destinations exist** ([ADR 0033](0033-backups-of-volumes-and-databases.md)): a `backup.destination` is S3-compatible storage with a passphrase, a backup is sealed before it leaves under a key from the passphrase (PBKDF2, then AES-256-GCM in chunks bound to what the file is), and `dockwell open-backup` opens one with the passphrase alone, in either build. Restoring a volume to another server is left for later there.
- **Agents keep what their servers run** (ADR 0054, in #312 and #357): each agent holds a sealed record of each resource its server runs, with its values, its revision and its image, bound to its server's ID, and a fill leaves alone what a restored store doesn't know.
- **Agents dial out, and pin the CA.** An agent connects to the control URL its join ticket gave it, and trusts what the CA signs. The CA is in the store, so a restored control plane is the same CA to every agent; only its address can change.
- **The store checks each agent's certificate by serial.** A connection passes with the server's current certificate, or the one it replaced; anything else reads as another machine holding the server's old key (`identity.CheckConnection`). Agents renew two thirds into a 30-day life, so about one agent in 20 renews each day.
- **A store that goes back forgets.** It forgets what it gave each server after the backup, which certificates it signed, and what was revoked or removed. That holds whether it went back by a restore or by a provider's snapshot, a VM rolled back, or Postgres restored to a point in time, which is what most owners of one server reach for first.
- **Most installs are one server.** For them, losing the control server is losing everything that ran, and the backup is the only way back.

## Decision

### What is backed up: one sealed bundle

- **A bundle is the store, as a snapshot, and the install's key.** Nothing else is needed to run the control plane again, and nothing outside the store and the key is in it.
- **The snapshot is a SQLite database at the store's schema version, whatever the store runs on.** On SQLite, `VACUUM INTO` makes it, outside any transaction, as SQLite requires, into a file made `0600` first, since plain variables are stored in the clear. On Postgres, the store copies every table into a fresh SQLite file in one transaction of the REPEATABLE READ read pool, so the copy is one moment. `PRAGMA integrity_check` runs on it before it's sealed and again on a restore. Restored into Postgres, the schema's migrations run first, and tables are copied in their foreign keys' order. So a restore can move an install between the two.
- **Its header is readable without the passphrase,** and names the build that took it, the store's schema version, the install's ID, the store's generation (below), when it was taken, the key derivation's parameters and salt, and which passphrase sealed it, by when that was set. What's sealed binds the header too, so changing it breaks the seal.
- **It's sealed with the control plane's recovery passphrase,** in ADR 0033's format, AES-256-GCM in 1 MiB chunks bound to the install's ID and the bundle's ID:
  - **argon2id, 64 MiB, 3 passes, one lane:** RFC 9106's second recommended set, with one lane as the smallest server Dockwell supports has one CPU, about a second on a 1 vCPU VPS with 1 GB, which slice 1 checks on one, raising the passes if it takes much less. On opening, the header is at most 64 KiB, memory is between 8 and 256 MiB, passes between 1 and 10, lanes between 1 and 4, and each salt between 16 and 64 bytes. Anything outside those bounds is refused before deriving a key, so a crafted bundle cannot exhaust the restoring server's memory or CPU.
  - **Derived once, as the passphrase is set,** and kept sealed under the install's key beside the passphrase, so a start derives nothing and holds no 64 MiB. Each bundle's key comes from it by HKDF-SHA-256 with the bundle's own random salt and the label `dockwell control bundle` and the install's ID.
  - **Only the full build seals or opens one.** argon2id is in `golang.org/x/crypto`, which the full build links already and the agent build doesn't, and an agent never opens a bundle. The agent build's `open-backup` says to use the full build.
- **The recovery passphrase** is made at the first start: 32 characters of Crockford's base32, 160 random bits, in groups of four, so what stands between a stolen bundle and the install is the passphrase's own length, not the derivation's cost. It's kept sealed under the install's key, so the control plane can seal on its own.
  - Settings → Backups shows it to the owner with a passkey just now, says to keep it somewhere that isn't this install, and has the owner type it back once; the overview says so until they have.
  - The owner can set one of their own, which takes a passkey, is on Activity, and has to be at least 20 characters and estimated at 80 bits or more; the panel says the one it made is stronger.
  - **A new passphrase retires the old one's bundles.** A bundle is taken under the new one at once, and once it's whole in a place, that place's bundles under the old one are deleted. Until then the panel says the old one still opens them. Object lock or a key without delete rights can prevent that deletion: the panel names those copies and their retention expiry, or says the expiry is unknown, and keeps saying the old passphrase opens them. A passphrase that leaked has given away the install's key, its CA and every secret in the bundles it opened: the panel says those need rotating, and that Dockwell has no command for the CA and the install's key yet (ADR 0022), which a follow-up to #34 will track, opened once this record is accepted.
- **What it means.** A bundle and its passphrase are the whole install: its CA can sign a certificate any agent trusts, and every secret is in it. That is no more than the control server's own disk holds, and the panel says to treat the passphrase as such.

### Where it goes

- **To two agents.** The control plane sends each bundle to two connected agents other than its own server's, choosing those with the most room, and the same two while they stay connected; the owner can name them, or leave servers out. Each keeps it, sealed, in `<data>/agent/control-backups/`, checking it has room first, as ADR 0033's backups do. An agent can't open what it keeps. With fewer other servers it goes to as many as there are, and a single server keeps none elsewhere: the panel says the only copy then is off-site, or none.
- **Off-site, to one destination,** an existing `backup.destination` the owner picks. Choosing it, changing it or removing it takes the owner and a passkey just now, as an admin may otherwise edit destinations (ADR 0048 and ADR 0049, in review), and a destination repointed elsewhere would still show a fresh copy. The panel recommends a bucket with object lock or versioning, and a key that can't delete, as a control plane that's taken over holds the key.
- **Named by generation.** Bundles go under `dockwell-control/<install ID>/<generation>/` in the bucket and on agents, and retention touches only its own generation's. So an old control server that comes back can't delete a restored one's bundles, and "the newest off-site" is the newest of the highest generation.
- **The off-site copy is the one to trust.** An agent can't open what it keeps, but one that's taken over can delete it, keep an older one, or not send one back. So the overview and Settings → Backups show how old the newest off-site bundle is, first and largest, to admins, with the agents' copies under it, and an install with no destination is a warning there until it has one.
- **Retention:** each place keeps the newest 24, and one a day for the 7 days before, and drops older ones after a newer one is whole there. A run of failures drops nothing. A destination whose key can't delete needs bucket lifecycle rules for expiry; locked copies remain until their lock expires, and the panel reports them.

### How often

- **After managed state changes, and at least hourly.** Writes to resources and revisions, changes, people, grants, passkeys, tokens' creation and revocation, and settings start a wait; a session's last sight and a token's last use, which every request writes, don't. A bundle is taken a minute after the last such write, or 10 minutes after the first if they go on, and never more than once every 10 minutes. With none, one is taken each hour, so a place that missed one catches up.
- **Every bundle goes to every place it should.** Each place says, on Settings → Backups and the overview, when it last got one, and one that's more than two hours behind is a warning, with why.
- **Its work is bounded.** A bundle is the store's size, a few MB to tens of MB, sealed in a stream and written to a temporary file, never held in memory whole. Past 256 MiB, as a long audit log makes one, it's taken hourly at most, and the panel says so; the audit log's own retention is for that follow-up too. An agent keeps at most 31 per generation and checks room across all the generations it holds before accepting another.

### What the owner writes down

- **Settings → Backups has a recovery sheet** to print or keep: the control plane's address and the install's ID; the destination's endpoint, region, bucket, prefix and access key ID, as its secret is in the store being restored and the owner keeps it; that the passphrase is needed; which servers hold copies, and where; and the commands below, written out for this install. Saying the passphrase is kept asks about the sheet too.
- `dockwell control restore`, given a destination and no prefix, lists what it finds there by install and generation, so a sheet that's lost leaves a way in.

### Restoring

- **`dockwell control restore` runs on the server that becomes the control server,** a server that joined or a new one. On one that runs the agent build, the install script installs the full build with `--restore`, at least the build the bundle's header names. When no compatible published artifact exists, as for a bundle taken by an unreleased build, it prints that build's commit and the commands to build the full binary from it and rerun the restore, rather than installing an older binary. A restore migrates an older schema forward and refuses a newer one than its build. It takes a bundle from this agent's own copies, a file, or a destination (asking for its credentials), and the recovery passphrase. Postgres takes `--database` with its password from `DOCKWELL_DATABASE` or `.pgpass`, never the command line. It refuses a target that already has a store.
- **It writes the store and the key,** mints a new generation (below), and writes the generation's marker off-site before anything else, then records that it was restored from the bundle taken at its time, and starts. If an off-site destination is configured, failing to publish its marker prevents the restore from leading; it prints the failure and how to retry. With no off-site destination, the restore requires the old control server to have been demoted or shut down permanently and says that fencing reaches each agent only when it sees the new generation.
- **It ends what was given out after the bundle, and what it can't vouch for.** Every session ends, and every unspent invite, join ticket and sign-in link is void. The restore's output, and the panel's first screen until the owner confirms with a passkey, list the servers, people, passkeys and tokens "as of" the bundle's time: anything removed since is back, such as a server removed as compromised, a person removed, or a token revoked. Until that confirmation, fills that carry values wait for each server, which runs on from its agent's own records meanwhile (ADR 0054); afterwards they wait for each server an admin hasn't confirmed, so a removed server that's back gets nothing until someone says so.
- **Certificates signed after the bundle are taken once.** An agent whose hello says it kept its records under an older generation, with a certificate for its server's ID that the CA signed and that's unexpired, issued after the bundle's time, is accepted once: that certificate becomes the server's current one, and Activity says so. Without this, every agent that renewed since the bundle would read as another machine holding its key. A server the store doesn't know, with such a certificate, joined after the backup: it's listed as "joined after the backup", for an admin to accept with a passkey, which brings it back with its records as below.
- **Agents find it.** A control plane reached by a domain needs its DNS pointed at the new server, and nothing else. One reached by an address can't be found on its own: the restore prints, for each server in the store, `sudo dockwell agent repoint <url>`, which an agent takes only if what answers there is signed by the CA it already trusts. So the install script and the restore both recommend a domain for the control plane's address, and say why: with one, a restore is a DNS change; without, it's a command on every server.
- **The dead control server's own server is replaced, not left holding everything.** For one server, that's every app. `dockwell control restore --replace <server>` makes a plan, which a person applies in the panel: what the dead server ran is placed on this one, and each volume gets its newest off-site backup restored, through ADR 0033's restore to another server, which this needs and that follow-up adds. Without a backup of a volume the plan says it starts empty, and a person decides. Without `--replace`, the restore says plainly that it restored the control plane, and that what ran on the dead server stays placed there.

### Generations, and who leads

- **The store has a generation: a number and a random ID,** made at the install and moved on by every restore and rebuild. The welcome says it, with the store's position (its highest revision) and the newest bundle's time; an agent's hello says the generation its records were kept under, and the highest generation, position and newest bundle's time it has seen. So the first agent to connect to a restored control plane says when it saw a newer bundle than the one restored, and the panel says the restore is older than it had to be.
- **A restore's number is the time in seconds,** or one more than the highest generation it can find, whichever is higher: the generation markers off-site and the bundles' headers in every place it can read. Two restores in the same second can choose the same number, but their random IDs differ. Publishing the current generation marker uses a conditional write against the marker read: only one wins, and the other stops and requires another restore above it. An agent also refuses an equal number with a different ID, so simultaneous restores cannot alternate control of it.
- **An agent follows only the highest generation it has seen.** It refuses a control plane with a lower number, or the same number and another ID, and says which two, in its log and in the refusal it sends that control plane, which then stops leading every server and says to run `dockwell control demote`. A restore that finds agents reporting a higher generation than it minted stops, and says a newer restore exists.
- **Every control plane checks the off-site markers** as it starts and before each upload: one that finds a higher generation's marker stops leading and says to demote it.
- **`dockwell control demote` lasts.** It stops a control server that comes back, keeps it stopped across reboots and its unit's restarts, and keeps its store, which holds what happened after the bundle.
- **A store that went back without a restore is caught.** An agent that reports a position beyond the store's, in the same generation, means the store went back, as by a snapshot or a point-in-time restore. The control plane then stops leading, and says to run `dockwell control restore --in-place`, which mints a new generation over the store it has, and goes on as a restore does.
- **The fence starts with this version.** Agents older than it send no generation and follow any control plane. Settings → Backups names the servers that can't be fenced yet, and the restore prints them, to update.

### Reconciling with what agents hold

- **The restore notes each resource's and each value's revision in the bundle,** and an agent from an older generation is reconciled against those, resource by resource, as it first connects. Its hello lists its tombstones too, with their revisions.
  - **The same in the bundle and the agent:** the record is kept again under the new generation, at the store's revision.
  - **The agent holds a later revision than the bundle, and the store hasn't changed it since the restore:** it ran after the backup, and what runs wins, within the limits below. The control plane recalls the record, with its values sealed to the stream, and brings it back as a change that adopts it, with no step, as nothing on the server changes: "Brought back from server-1 what it ran after the backup". A variable or secret it pins at a revision the store lacks gets one, holding the value the agent had. The change is on Activity and can be undone, which is then a change with steps.
  - **Changed on both sides:** a conflict, which waits for a person.
  - **The agent holds an earlier revision than the store's live one,** as after `dockwell local` rolled it back while the control plane was away (PRD), or a record that wasn't kept: that's drift, never overwritten by a fill.
  - **The agent holds a tombstone above the bundle's revision:** the resource was deleted after the backup, and comes back as a deletion, a person's call when it would delete a volume.
  - **The store placed it elsewhere, or deleted it, after the bundle:** the store's latest stands, and ADR 0054's forget applies; the agent wins only above the bundle's revision.
  - **The store has something live there the agent doesn't hold:** it's filled, as ADR 0054 has it, once the server is confirmed.
- **It's adopted on its own only when nothing else can be reached through it:**
  - the record gains no host access over what the bundle has of the resource;
  - the resource is placed on that server alone, or, unknown to the store, no other agent holds it, judged once every server has reported or 10 minutes have passed;
  - every variable and secret it brings back is used by nothing placed elsewhere;
  - it isn't in a protected environment, whose changes wait for an admin (ADR 0049, in review);
  - no domain or published port it holds is held elsewhere.
  Anything else waits, listed on the overview and Activity as "brought back, needs a look", until an admin applies it with a passkey just now, or leaves it. What's adopted on its own is marked unreviewed until a person looks, and isn't filled into a new cache, as after a reinstall or a move, until then, so code a taken-over server ran doesn't spread from it.
- **A value that waits holds back what would undo it.** While a shared secret brought back waits, a plan that would deploy an older revision of it elsewhere is held, with the reason, so a value rotated after the bundle isn't replaced by the older, perhaps leaked, one.
- **Once a server is reconciled,** the store records the generation it reconciled at, and the generations the store has been. A server that already reconciled, or that claims a generation the store never was, gets nothing adopted, and a warning goes on its timeline. At most 1,000 records are recalled from one server.
- **An older agent reads nothing after a restore.** A restored control plane can't know what it gave a server after the backup, so of an agent that doesn't write a container's references in (`Hello.writes_references`), it reads, plans and applies nothing until that agent is updated, whatever the store says it names (#120). That's a separate line from the fence above.

### Rebuilding with no backup

- **What agents hold is enough to run what they run.** A new install, with a new CA, can take a server's records: every server joins it again with `dockwell join --bring-back` and a ticket from the new install, as the CA is new, and offers its records, opened under its old server's binding and sealed again under its new one. ADR 0054's records carry the project's and environment's IDs, names and protection for this, which slice 3 adds to them, and the server's ADR 0033 backup records (`.json`) are read back.
- **The rebuild is a plan the owner applies with a passkey,** with host access marked, that makes the projects, environments and resources the records name, by the IDs and names they hold, with their values as variables and secrets, and places each on its server. Where two servers hold one secret at different values, the second's records wait. A volume whose options aren't known, as records keep none, is never made again in place of one that's there.
- **What's lost** is all the store held beyond what runs: people, passkeys, tokens, history, Activity, backups' records, schedules, what ran nowhere. The rebuild says so. It's for when the passphrase or every bundle is gone.

### What a server, or a control plane, that's taken over can do

- **A server's own bundles:** delete them, keep older ones, or not send them back. The off-site copy is the one to trust, and the panel says so.
- **After a restore, say it runs anything,** or claim an older generation whenever it likes. What one agent says it ran can't be checked against anything, so it's adopted on its own only within the limits above, only once, and only for a server that hasn't reconciled. Otherwise a server taken over before a restore could put a privileged spec, or its own image, into a service that also runs elsewhere, and the next deploy would carry it to the fleet.
- **Not its records' values.** A record's values are what that server already ran with, so bringing them back gives the control plane nothing that server didn't have; a secret used elsewhere still waits, and holds back what would deploy an older revision of it.
- **A server removed as compromised, brought back by a restore,** gets no values until an admin confirms it, and the restore lists it among what's back.
- **A control plane that's taken over** holds the destination's key, so it can delete the off-site bundles unless the bucket keeps them; the panel recommends a key that can't delete, and object lock or versioning.

### Who may do what

- Setting the destination, showing the recovery passphrase, and setting one, take the owner and a passkey just now, in a session; each showing of the passphrase is on Activity. Seeing where bundles are and how old they are is an admin's. Taking one now is an admin's, and is on Activity. Confirming servers and people after a restore, and applying what was brought back and needs a look, take an admin and a passkey just now.
- No API token can show or set the passphrase, confirm what a restore brought back, or apply what waits. No bundle can be downloaded over the API. Each method's file names its least role, whether it needs a session, and what a token's scope allows.
- A restore and a rebuild take root on the server they run on, and the passphrase, or the agents' records. The control plane can't be restored over the API.

### Numbers

The agent protocol's fields for this are in 190 to 199: the welcome's generation, position and newest bundle; the hello's generation of its records and the highest it has seen, and its tombstones; a call to keep a bundle and its result; a call to recall a record and its result; and an agent's refusal of a lower generation. Event fields too are in 190 to 199, for a bundle taken, sent, or failing, a restore, a server or person confirmed, and a certificate taken after a restore. The public API's methods for backing up the control plane are a file of their own.

## Consequences

- Losing the control server loses at most the minutes since the last bundle, on two servers and off-site, and what agents ran since comes back from them; an install of one server comes back onto a new one with its apps and their latest volume backups.
- The recovery passphrase, and the destination's secret key, are what the owner has to keep, with the recovery sheet; losing the passphrase with every bundle leaves only a rebuild.
- A restored control plane is the same CA to every agent, and takes the certificates they renewed since, so nothing has to join again; only an install reached by an address needs its agents repointed.
- Two control planes can't both lead the same agents: the generation, the off-site marker and a lasting demote fence an old one, or a second restore, from every agent that has seen the new one, from this version on.
- A restore undoes nothing silently: what was removed since the bundle is listed for the owner to confirm, sessions and unspent invites end, and values wait for each server until it's confirmed.
- After a restore, what a server alone ran comes back on its own, and anything that reaches further, or is in a protected environment, waits for a person, so a restore can leave a list to look at.
- It needs ADR 0033's restore to another server, the audit log's retention, and a way to rotate the CA and the install's key, which that follow-up to #34 lists.
- It comes in four slices: bundles, taken and kept on agents and off-site by generation, with Settings → Backups and the recovery sheet; restoring, with the generation, fencing, certificates taken once, what's back confirmed, repointing, and `--replace`, proved in the Docker job; reconciling with agents' records, tombstones and conflicts included; and rebuilding from agents' records.
