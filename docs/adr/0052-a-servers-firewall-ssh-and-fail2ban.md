# 0052. A server's firewall, SSH and fail2ban, each through a plan

- Status: Proposed
- Date: 2026-11-07

## Context

The PRD makes a server's firewall, fail2ban and SSH hardening a launch requirement (Server, P0), and principle 2 names firewall rules among what every change previews, applies and undoes. 1Panel has all three in its free edition, and an owner moving off it loses them otherwise (#260).

What exists: the `firewall.rule` kind, its driver in `internal/resource/firewall`, and an in-memory backend. No agent registers the driver, so a rule can be planned and runs nowhere.

Each of the three decides who reaches the server. A wrong rule can lock its owner out of SSH, of the panel, or, on the control server, every agent out of the control plane. Server-Firewall.dc.html answers that the way routers and cloud consoles do: a change applies, and rolls back on its own unless someone confirms within 60 s that they still have access. A design review of this record (#288) found that the timer alone protects much less than it seems, and a narrow check of the revision found where the checks around it were still undefined. This record is built around what the timer doesn't cover.

Servers arrive with a firewall already: ufw on Ubuntu, firewalld on AlmaLinux, Docker's own rules everywhere, sometimes plain nftables or iptables-legacy a person wrote. Dockwell is a guest on them, as it is with containers it didn't make ([ADR 0031](0031-containers-dockwell-didnt-make.md)).

## Decision

### nftables, in a table of Dockwell's own

The agent writes one nftables table, `inet dockwell`, and nothing else. `inet` holds IPv4 and IPv6 alike, so a rule covers both unless its sources are of one family. Each change replaces the whole table in one `nft -f -` transaction, `table inet dockwell {}; delete table inet dockwell; table inet dockwell { … }`, so the server is never between two rulesets. nft takes the transaction whole or not at all, so a load nft refuses changes nothing. A load nft took but Dockwell couldn't see through, as nft was stopped or the table couldn't be read back, counts as possibly live: the agent puts back the last confirmed table, as for a timer that runs out, and never takes it that nothing changed. No other tool runs between checking a table, loading it and reading it back, and a caller that leaves once nft has the table doesn't cut the load or its read back short.

nftables runs every base chain on a hook, in every table, and a packet passes only if none of them drops it. iptables-legacy rules run beside nftables's on the same hooks, and a drop in either wins there too. So:

- **Dockwell's table can close what another opens, and can't open what another closes.** That's true both ways: a Dockwell drop overrides a person's own accepts and Docker's. Beside ufw or firewalld, the Firewall tab says which tool also filters, and that a port it closes stays closed whatever Dockwell allows.
- **Rules Dockwell didn't make are the server's own.** The agent reads ufw through `ufw status verbose`, firewalld through `firewall-cmd`, other nftables tables through `nft -j list ruleset`, and iptables-legacy through `iptables-legacy-save`, and the tab lists them, read-only, as containers Dockwell didn't make are. Nothing Dockwell does changes them.
- **The tab works out reach twice:** for what listens on the host, which input rules cover, and for ports Docker publishes, which reach their containers before input rules see them. ufw's and firewalld's rules don't close a published port, and the tab says so beside each.

### What Dockwell's table holds, and in what order

- **Inbound is allowed by default, until someone chooses otherwise.** A server Dockwell meets keeps working as it did. Deny everything else, the mock's fixed last rule, is a policy a person turns on, `firewall.policy`, which is a resource like a rule and so a plan too. Turning it on lists, in the plan, every port something on the server listens on that no rule allows. The owner decided this on 2026-11-07: a default of deny would need every server's ports listed before it joined to be safe, where this leaves each as it was until someone closes it on purpose.
- **Rules apply in a fixed order, whatever order they were made in:** what's always allowed, then every allow, then every deny, then the policy. `FirewallRule` has no order of its own, so that's what decides which wins. With inbound open by default, an allow matters only as an exception to a deny or to the policy. The plan names any rule another makes useless, such as an allow no deny or policy narrows.
- **What keeps the server reachable is always allowed, and comes first:** traffic of connections already open; loopback; ICMP's and ICMPv6's errors, types 1 to 4, and IPv6 neighbor and router discovery, types 133 to 137 with a hop limit of 255; MLD from link-local addresses with a hop limit of 1, types 130 to 132 and 143, so a snooping switch or bridge keeps sending the server its neighbor discovery (RFC 4890, 4.4.1); DHCPv4 and DHCPv6 replies, so a lease renews; ping, ICMP's and ICMPv6's echo request, at most 5 a second with bursts of 10 for each family, as RFC 4890 keeps echo. The table drops nothing of its own beyond the rules and the policy: an earlier draft dropped what the connection tracker calls invalid, on every table, which changes what a server with one allow does with out-of-window and asymmetric traffic, against "a server keeps working as it did". Such packets go on to the rules and the policy like any other. A setting to stop answering ping, as 1Panel has, can come later. On the control server, the agent listener and the panel's own ports are pinned too. A rule that would deny one of these is refused when it's planned, saying which it would cut.
- **SSH is pinned on every server, from where people come in now, on the ports it listens on now,** whenever a rule or the policy would narrow it ([What SSH's pin holds](#what-sshs-pin-holds)). On a control server with no domain, it's also how the panel is reached.
- **On a control server whose panel route trusts proxies** ([ADR 0030](0030-routes-behind-a-tunnel-or-a-proxy.md)), a rule that narrows 80 or 443 is refused: every request reads as the proxy's, so Dockwell can't tell whose address to keep. With a domain and no proxy, 80 and 443 may be narrowed under the timer, but a source list that leaves out the address the person is using now is refused.
- **Under deny everything else, containers still reach the host,** as an app reaches a database on the host's address; the plan says so.

### What SSH's pin holds

The pin is a rule of the always-allowed part: SSH's ports, from the addresses people use for SSH now and those pinned before. It's worked out when a change is planned, and again on the server just before each step loads, over the change as it stands then.

- **Addresses come from the SSH sessions open now that someone has signed in on,** read from the kernel's socket tables, a line at a time: an established TCP connection one of sshd's processes holds, whose local port is one SSH listens on, with its peer's address. So a `-L` forward's connection out isn't a session.
- **A connection nobody has signed in on isn't a session.** Anyone on the internet can open one, and a scanner mid-handshake would otherwise pass as "someone's address to keep", let deny everything else through with nobody's real address pinned, and be pinned itself. What tells them apart is who holds the connection, kernel facts first: OpenSSH hands a signed-in connection to a process that runs as the person, and holds one nobody has signed in on in a process that runs as its own unprivileged user, `sshd` (its ID read from `/etc/passwd`), or, from 10.0, in one named `sshd-auth`. So a connection counts when a process of `sshd` or `sshd-session` that runs as someone other than root and `sshd` holds it, and none that runs as `sshd` or is named `sshd-auth` does. Root's session has one process, as root, so it's told by its title: `root`, or `root@pts/0`, `root@notty` and the like, which `session.c` sets after sign-in. The titles before sign-in veto too: `[accepted]`, `[rexeced]`, `[net]`, `[session-auth]` (read in OpenSSH 8.7, 9.2, 9.6 and 10.0; `<user> [priv]` is set before sign-in as well as after, so it says nothing). A name someone asks to sign in as can't forge a title: it's followed by ` [priv]`, and one long enough to be cut off isn't `root@...`. utmp and logind were weighed and left: utmp lists only sessions with a terminal, logind isn't on OpenRC or without PAM, and both name a host that may not be an address. Where `/proc` doesn't say who holds a connection, or under Dropbear, whose processes say neither, nobody is counted, and narrowing SSH is refused as below unless a rule allows SSH's port. All of them are pinned, IPv4 and IPv6 alike, except a peer on one of Docker's networks, which is a container's session to the host, not a person's. The request's own address isn't used: with no domain, the panel comes over `ssh -L` from `127.0.0.1`, which is loopback and pins nothing.
- **The addresses pinned stay pinned while something narrows SSH, and leave once nothing does.** Each confirmed change keeps the addresses and ports it pinned, with those kept before, in its confirmed state, and every later load pins them as well as the sessions open then. A person who logged out isn't locked out by an agent's restart, a revert, a reboot or the next change, as they would be if the pin were worked out afresh each time. A confirmed change that leaves nothing narrowing SSH, with no deny of its ports and either no policy or a rule that allows each of its ports from anywhere, keeps none: that's how an address leaves. The plan of whatever narrows SSH names every address it stays open from, so a stranger's shows before it's applied.
- **On a control server with no domain, whatever narrows SSH is refused unless a rule allows SSH's port:** deny everything else, and a deny of SSH's port as much, as both leave the same state. The panel is reached through SSH there, and a pin holds only while the address it names does: a home connection whose address changes would lose SSH and the panel at once, which no timer can catch. The refusal says to add the rule first, from anywhere or from the ranges they'll come from.
- **With nobody's address to pin,** no session open from outside the server and none kept, as when the person comes in over Tailscale to the panel, or through a tunnel, a change that narrows SSH is refused, saying to sign in over SSH from where they'll come in, or to add a rule that allows SSH's port, and plan again. What narrows SSH is judged on the state the change leaves, not the rule alone: a deny of one of its ports; deny everything else with no allow of each of its ports from anywhere; and so deleting that allow, or narrowing its sources, under the policy. Such a delete or narrowing is flagged as able to lock you out, as a deny is, so the plan asks for its fingerprint.
- **Ports are every port SSH listens on now:** what the SSH server's listening process holds, the one whose parent isn't an SSH process, away from loopback, so a session's X11 or `-R` listener isn't one; and, under socket activation, what `ssh.socket` or `sshd.socket` holds (their `ListenStream` lines, which Ubuntu 24.04's generator writes from `sshd_config`). With neither, as when inetd holds SSH's port, `sshd -T`'s `port` lines stand in. Where Dockwell finds no SSH at all, port 22 stands for it, and narrowing it is refused, saying so. A `/proc` that can't be read is an error, which refuses the change, never a server with no SSH. The confirm dialog names its port from the same set.

### Where each rule goes

Each rule goes in both places a packet can arrive:

- **The input chain,** for what listens on the host, and for what Docker's userland proxy accepts, which arrives there: IPv6 to an IPv4-only published port, and hairpin traffic from the host to itself.
- **The forward chain, for ports Docker publishes.** It matches traffic Docker translated (`ct status dnat`) by the port it arrived on, `meta l4proto tcp ct original proto-dst 8080`, so `8080/tcp` means what a person means by it: the port on the server. It matches only traffic arriving on an interface that isn't one of Docker's and going to one that is, by name (`iifname`, `oifname`), as Docker's interfaces don't exist yet at boot and `iif` would fail the load; so other port forwards on the server, such as libvirt's, LXD's or k3s's, aren't filtered as published ports. The agent takes Docker's interface names from Docker's network list, not by matching `br-*`, and builds the table again when Docker's networks change, so a new Compose bridge doesn't count as outside: it checks Docker's network list every 15 s, and once as it starts, and loads the confirmed table again with the networks as they are, confirmed on disk as it loads, while no change waits. Each read is bounded; when Docker doesn't answer, a change takes its networks as Docker last listed them, or as the confirmed table has them, and refuses only with neither. On a server without Docker, the table leaves what the server forwards alone, as nothing there is a published port. A name nft can't match, one with a quote or a control character, or ending in `*`, is left out rather than refuse the whole table, which would stop a rollback too; the plan and the tab say its containers' traffic counts as from outside and its published ports aren't filtered, and to rename the bridge.

Both chains hook at `filter`, priority 0: a chain at -200 or lower runs before connection tracking, and couldn't see `ct original`. Traffic between containers, and from them out, is never filtered, and outbound is never filtered: the agent's stream to the control plane goes out, and so do the packages, images and certificates a server fetches.

**Some paths to a container can't be filtered here, and the plan says so for any rule they'd skip:** Docker 28's `routed` and `nat-unprotected` modes, and IPv6 published without NAT, have no translation to match; macvlan and ipvlan networks bypass the host's firewall entirely.

### The confirmation timer, and what it doesn't prove

A change to the firewall or to SSH applies, then waits for a confirmation:

1. **One waiting change per server.** Every kind under the timer (`firewall.rule`, `firewall.policy`, `ssh.config`, and a `fail2ban.jail` that moves with SSH's port) also claims one shared item per server, the server's access, so the engine refuses a second change on that server as busy (`ErrBusy`) until the first is kept or rolled back. Without it, two rules, a rule and the policy, or a rule and `ssh.config` could wait at once, and the first to run out would put back a table without the second.
2. Each agent the change reaches applies all of that change's steps for its server in one transaction, under one timer of 60 s. One confirmation covers the change, not each step.
   - **Each server's steps under the timer run together,** after the change's other builds and before its deletes, a server at a time in the plan's order, so nothing is removed before the wait, and a change nobody confirms rolls back with all it would have removed still there. The timer starts at a server's first such step and starts again at its last, which waits for that server's confirmation before the next server's steps begin. So a server's timer covers its own steps alone: neither a slow step of another kind nor another server's wait can run it out partway. A firewall step depends on nothing, so where it runs in the change is free.
   - **A step of a change the server already put back fails,** so the change rolls back, rather than start a wait of its own from what was confirmed and end applied with only part of the change on that server.
   - **A change to several servers waits on each in turn,** and a confirmation names the server it's for, and the deadline it answers, so one sent twice for the first server can't keep the second untested.
   - **A confirmation keeps a server's part only while the whole change succeeds.** If a later server's part isn't confirmed in time, or a later step fails, the change fails, and rolls back on every server it reached, the ones already confirmed included, with no timer, as any failed change does. A confirmed server holds the change's rules until that rollback reaches it; one that's away when it runs keeps them until it's back and the rollback, which waits for it, puts back what it had before the change.
3. The step's Verify waits up to 90 s, the timer and room for its answer to come back, for the agent's verdict.
4. **The agent decides.** The step passes only on its "kept" answer, sent once a confirmation reached it before the timer ran out. The agent records the change as confirmed on disk before it answers "kept": the table as it loaded, written for the boot unit, and the specs and pins in `confirmed.json`, both in full first, with `confirmed.json` renamed into place last but one; if the table won't follow, the old `confirmed.json` goes back, and the answer is "rolled back", so the disk never says otherwise than the agent. A confirmation reads nothing of the server, neither Docker nor `/proc`, so nothing there can fail it. A confirmation that arrives after gets "already rolled back", and the step fails. Confirming and running out can't both win: the agent takes whichever comes first. The control plane refuses a confirm for a change it has already failed.
   - **Only the session that applied the change may confirm it,** and the control plane holds that in memory: a control plane that starts again during a wait leaves nobody who may confirm it, and the server's timer puts back its firewall. That's safe, and rare enough not to store.
   - **The countdown runs on the control plane's clock.** The agent says how long is left as well as when, and the control plane takes the deadline from that, so a server whose clock is off doesn't show a wrong countdown.
5. **If the timer runs out, the agent rolls back to what was last confirmed,** not to a snapshot taken when the change began: the table as it loaded when it was confirmed, the SSH drop-in and any jail, on its own, without the control plane, which it may no longer reach. The revert reads nothing of the server, neither Docker nor the pins, so a Docker that doesn't answer can't hold it up. If the confirmed table won't load, the agent removes its table, which leaves what the server's own firewall does, never the change's, and tries again every 15 s on its own clock, whether or not its stream to the control plane is up, as that stream may be what the table cut. The change then rolls back as any failed change does. A confirmation that reaches the agent before the change's last step on the server has said it waits keeps nothing: part of the change hasn't loaded.
6. **A waiting change outlives the call and the stream that started it.** [ADR 0017](0017-the-change-api-and-the-agent-stream.md) cancels a call when its stream ends, but the agent's timer and its record of the waiting change are its own: a dropped stream doesn't cancel them, and the verdict goes to the control plane once it's back.
7. **A resumed step waits for the verdict.** A control plane that stops interrupts a change, and Resume plans its steps again (ADR 0017). The agent reports a waiting change as waiting, by its change ID, not as the live table, so a resumed step waits for that change's verdict rather than reading the waiting table as done. Whether a step changes nothing is judged against the last confirmed state, not the live one.
8. **Automatic rollbacks, and steps that change nothing, apply with no timer.** A rollback restores what was confirmed before, so it needs no confirmation of its own, and has nothing to race.
9. **The agent's cache of desired state (#32, ADR 0054) records a change's firewall specs when Confirm keeps them, and only then,** as a step can't say whether it will be kept. The cache's fill skips the firewall's kinds, so a control plane restored from a backup (ADR 0057) never pushes a firewall into the agent that the agent's own confirmed state has moved past. Until #312 is in `main`, no step records a firewall spec in the cache at all; both halves go in with it.

**The timer protects only what the person tests.** Open connections stay allowed, and reloading sshd keeps open sessions, so a click over the panel connection they already have succeeds after almost any change. So:

- **The confirm dialog names the test:** "Open a new SSH session to port 22 from where you are now, with your key, then confirm." For a change to the panel's ports, it's a new tab on the panel's address. Where the change turns deny everything else on on the control server, the dialog asks for both. Keep is offered only to the person who applied the change.
- **The plan, the dialog and the notice name who SSH stays open from.** A plan that narrows SSH lists the addresses pinned and what rules allow its ports from (`PlanStep.stays`), as "SSH on web-1 stays open only from 203.0.113.7/32", and says in one sentence that if that address changes SSH closes to them, with the fix: a rule that allows SSH's port, from where they choose. The timer can't catch an address that changes next week, so the words have to. Turning deny everything else on, or taking away a tunnel's allow under it, also names each WireGuard tunnel whose UDP port no rule allows (an interface `/sys/class/net` calls `wireguard`, its port from `wg show`): SSH over the tunnel passes the test while the tunnel's flow is tracked, and stops at its next handshake. A change that reaches several servers asks for each in turn for now; one dialog once all have applied, counting down to the earliest timer, comes later.
- **The control plane checks SSH on its own, before and after,** on a server that isn't the control server:
  - It opens a fresh TCP connection to each pinned SSH port, from the control plane, and reads the server's SSH banner (`SSH-2.0-`), once before the change applies and once after.
  - It gates the confirmation only when the check before passed and the plan expects the control plane's own address to stay allowed. A failure after then means the table doesn't do what the plan said: the control plane withholds the confirmation, and the timer rolls back.
  - Otherwise it says "can't tell from here", never a pass. The check comes from the control plane's address, not the person's, so it can't say whether the person's next login works.
  - On the control server it's skipped: connecting to its own SSH goes over loopback, which is always allowed.
  - There is no check of the agent. Agents dial out ([ADR 0007](0007-one-binary-two-roles.md)), so the control plane can't open a connection to one, and the agent's stream is outbound and stays open whatever the table holds.
- **The rest is checked before anything applies,** at plan time, by the rules above and below: what's pinned, and that someone can still sign in.

### What a restart or a reboot keeps

**Only what's confirmed survives a restart.** At start, before it connects anywhere, the agent reverts the whole of a change that was unconfirmed when it stopped: the table, the SSH drop-in, with sshd reloaded, and a jail moved with the port. It then loads the last confirmed table as it was written, or, with nothing confirmed, removes any table of Dockwell's, which only the kernel remembered.

- **A change is on disk before its table loads,** and its record goes only once the revert has loaded, so an agent that stops at any point, or a revert that fails, leaves the change to be put back at the next start or check, never live with a verdict that says rolled back.
- **A change recorded as confirmed before the agent stopped is kept,** as the agent stopped after recording it and before it said so.

**A unit at boot puts back every file under the timer, from its confirmed copy.** The agent keeps a confirmed copy of each file it writes under the timer, written as it records the confirmation: the table, `00-dockwell.conf`, and Dockwell's jail file. The unit, `dockwell-access.service`, copies each back and loads the table, so a reboot inside the 60 s comes up with what was confirmed, SSH included, and published ports aren't open with no Dockwell rules until the agent starts:

- It runs `nft -f` on the confirmed table and plain copies of the confirmed files, not `dockwell`, so a broken binary still loads the table.
- It's ordered `After=nftables.service`, as Debian's runs `nft -f /etc/nftables.conf`, whose shipped file starts with `flush ruleset`, and `Before=network-pre.target docker.service ssh.service sshd.service ssh.socket fail2ban.service`.
- On OpenRC the same runs as an early service, after `nftables` and before `net`, `docker`, `sshd` and `fail2ban`.
- `dockwell --uninstall` removes the unit and the table. The SSH drop-in and the jail file stay, as removing them would change who can sign in, and it says where they are.
- **Until the unit ships, a server boots with no Dockwell table** until its agent starts and is ready. The agent loads the last confirmed table then, before it connects anywhere, and reverts a change that waited when the server went down. For those seconds, what comes in is as the server's own firewall leaves it: what Dockwell denies reaches the server, and with deny everything else on, so does everything else, published ports included. Nothing confirmed is lost, and the gap locks nobody out, as Dockwell's table only ever narrows what comes in; what it costs is exposure while the server boots. The tab says so while the unit isn't there.

**Drift is checked every minute, while the table is Dockwell's.** The agent lists `inet dockwell` once a minute, compares it with what it read back right after loading it, and puts it back if something changed or removed it, as `nft flush ruleset` does, and as Debian's `nftables.service` does when it's started, reloaded or restarted on an upgrade. Each time, it puts the drift on Activity. It doesn't wait for the cache of desired state (#32), which isn't built.

**There's a way out on the server.** Once a bad rule is confirmed, `nft delete table inet dockwell` is undone by the drift check within a minute and by the unit at the next boot. So `dockwell firewall off`, run as root on the server, turns Dockwell's table off: it deletes the table and leaves a mark that the drift check and the unit both honour. Activity shows it as drift, with who on the server turned it off if the kernel says. Turning it back on is a change from the panel, with a plan.

### SSH

SSH hardening is a resource, `ssh.config`: whether passwords and root may sign in, and the port. Who may reach the port isn't a second setting of its own: the SSH card reads and edits the firewall rules for sshd's port, so it's in one place.

**Reading SSH comes first, and changes nothing** (`GetServerSsh`, while someone looks at the tab):

- **The values are what sshd's files say now, from `sshd -T`,** which reads the files afresh and asks nothing of the sshd that listens: password login (on when `PasswordAuthentication` is on, or when `KbdInteractiveAuthentication`, or `ChallengeResponseAuthentication` before OpenSSH 8.7, is on with `UsePAM`, as keyboard-interactive asks for a password only through PAM), root login (`PermitRootLogin`, which `sshd -T` prints as `without-password` for `prohibit-password`), the ports, `AllowUsers`, `AllowGroups`, `DenyUsers` and `DenyGroups`, and the ways in Dockwell can't check below. The version comes from `sshd -V`; an `sshd` older than `-V` prints it in its usage, which it prints then.
- **The card never says the sshd that listens has read the files.** sshd reads its files as it starts and as it reloads, never between, so a file that cloud-init, a package or a person changed since isn't what runs: the card could say "Password login: Off" while passwords still work. Three rounds of review tried to prove the opposite from files and times, that sshd had read them since they changed, and each found another way to change what sshd would read without moving what the agent compared: a written time carried over by `cp -p` or `rsync -a`, a rename, a link pointed elsewhere at or above the file, a listener started with `-o`, another sshd binary, a clock that ran ahead and was set right, a file taken from a folder a wildcard matched, the PID file touched by something else. A fourth list of checks would not change that, so the claim is gone: there is no "read since they changed" state, no sentence and no mark that reads as confirmation. What the agent finds is only ever used to warn.
  - **Always, as the card's own lead line:** these are what sshd's files say, and the sshd that listens uses what it read when it last started or reloaded.
  - **A warning, when the evidence says the files changed after that:** its title names the files; one sentence says sshd may still accept what the card says is off until it reloads; and the command that reloads it is shown with a copy button, the one for how it runs: `systemctl reload <unit>` where its cgroup names a systemd service, `rc-service <name> reload` where it names an OpenRC one, else `kill -HUP <pid>`, the signal sshd reloads on. Each value from such a file is marked as not in effect until then, and only in this state.
  - **A warning of its own, when the listener isn't run from these files:** it's another sshd than the one the agent asked, by `/proc/<pid>/exe`, or it was started with `-o`, `-f`, `-p` or `-C`, by its command line, which keeps its arguments (Debian's unit passes `$SSHD_OPTS` from `/etc/default/ssh`). Then the files read may not be the listener's at all, which is said as that, not as files changed.
  - **Nothing more, where the evidence can't be read:** no `/proc`, no sshd that listens, no PID file, a PID file whose time hasn't come yet. The read keeps why for the record; the card doesn't show it, as it's no warning.
- **The evidence, since it only warns, is what's cheap and sound.** A reload doesn't make a new process: on `SIGHUP` sshd runs itself again in place, with the same process ID and start time. What moves is its PID file, which it removes before and writes again once it has read its files (`sighup_restart` and `main` in OpenSSH 8.7, 9.6, 9.8 and 10.0). So the agent finds the sshd that listens by its socket, a process named `sshd`, not started by another of sshd's processes, that holds a TCP socket in the listening state, or the one its PID file names (`pidfile` in `sshd -T`, else `/run/sshd.pid`), and takes that file's time as when it last read its files. It sets against it when each thing sshd reads last changed: `sshd_config`, every file an `Include` named, the folder each is in, `/etc/ssh` included, and each folder a wildcard `Include` matches, as a file taken away or put in place by a rename changes the folder alone; for each, the later of when its content was written and when its inode changed, of the name itself, of what it leads to, and of every link met on the way, at the file or above it.
- **Its limits are known and left.** A clock that ran ahead and was set right, and a PID file something else touched, hide a change from it; inode times on overlay and bind mounts aren't verified; Go's glob isn't `glob(3)`. None can make the card say more than its lead line. A positive statement may come back only with an answer from the daemon itself: a `none` sign-in request to its own port lists the methods it offers (#423).
- **A value sshd -T doesn't print is "can't tell", never "off".** Password login, key login, root login and the ports each have a third state, and output with none of them reads as unreadable. Password login is off only when `PasswordAuthentication no` and a line for keyboard-interactive are both there. A keyword printed twice with two values is "can't tell" too.
- **Each value says the line that sets it.** The agent reads `sshd_config` as `sshd` does: each `Include` where it stands, its files in name order, relative to `/etc/ssh`; the first value of each keyword wins, outside a `Match` block, except `Port`, of which each adds one. A `Match` block lasts until the next `Match` or the end of the file it's in, as `sshd` puts back the including file's `Match` state after an `Include`, and what it sets is listed apart, as `sshd -T` doesn't apply it. A value no file sets is `sshd`'s default. So the tab says, for instance, that cloud-init's `50-cloud-init.conf` turns passwords on, and the write slice can name the file that wins.
- **How far SSH reaches** is the firewall's own read of what listens on its ports, the narrowest of them, never more open than one is.
- **Where it can't be read, the tab says why:** no `sshd`; Dropbear, which Dockwell doesn't read yet; or `sshd -T` failing, as it does on Ubuntu 22.10 and later before the first connection makes `/run/sshd` under socket activation, in `sshd`'s own words. It also says when `sshd_config` includes no drop-in folder, as the write slice will refuse there, and which socket unit holds the port.

- **It's written to `/etc/ssh/sshd_config.d/00-dockwell.conf`,** a drop-in of Dockwell's own. sshd keeps the first value it reads, and reads drop-ins in name order before the main file, so `00-` comes before Ubuntu's `50-cloud-init.conf` and RHEL 9's `50-redhat.conf`.
- **A change goes in this order:** write the file, run `sshd -t`, run `sshd -T` and compare its values with the spec, and reload only then. On a mismatch, the old file goes back without a reload, and the change is refused, naming the file that wins, as an open `Match` block in an earlier file can. `sshd -t` passes in all of those cases, so it isn't enough. The tab shows the values in effect, not what Dockwell wrote.
- **`Match` blocks are checked too.** `sshd -T` alone doesn't apply them, so the agent also runs `sshd -T -C user=…,addr=…` for root and for each member of `sudo` or `wheel`, from each pinned address, and lists any `Match` block that sets one of these values for them as an exception in the plan. Every block that isn't `Match all` is listed, whatever it sets, with the keywords of these it sets if any: a keyword may stand in quotes, and a block Dockwell misreads still shows. Where any exists, the card says in one line that the values are the defaults for every connection and how many blocks can set them otherwise, and lists the blocks under it, each with where it is and which of the card's values it sets.
- **Where `sshd_config` doesn't include its drop-in folder,** as the RHEL 8 family's doesn't and Alpine's may not, Dockwell says so and changes nothing. It never edits `sshd_config`.
- **"Password login off" turns off `PasswordAuthentication` and `KbdInteractiveAuthentication` both,** as PAM still asks for a password through the second while it's on.
- **Turning off passwords or root login checks, at plan time, that someone can still sign in.** An account counts if it's root while root may sign in with keys, or a member of `sudo` or `wheel`, and all of these hold:
  - It has a key in the file `AuthorizedKeysFile` names, that counts: no `command=`; no `restrict` without `pty`; no `expiry-time` passed; and a `from=`, if it has one, that covers a pinned address. Ubuntu's cloud images put a key in root's file with `command="echo 'Please login as the user …';echo;sleep 10;exit 142"`, which signs nobody in.
  - `AllowUsers`, `AllowGroups`, `DenyUsers` and `DenyGroups` let it in.
  - `StrictModes` accepts its file: the file and its folders belong to it or root, and no one else can write them.
  - Its shell isn't `nologin` or `false`.
  - For root, `PermitRootLogin forced-commands-only` isn't a way in.

  It refuses when none counts. Where `AuthorizedKeysCommand`, `TrustedUserCAKeys`, `AuthorizedPrincipalsFile` or GSSAPI is set, Dockwell can't tell, and the plan says so and asks the person to say they've checked.
- **On a control server with no domain, a change that could stop the person's next login is refused** (its port, passwords or root login), as SSH is the way into the panel there; the plan says to give the panel a domain first.
- **Changing the port lists every step it takes,** and refuses where another tool would close the new port: on Ubuntu 22.10 and later, where `ssh.socket` holds the port, `daemon-reload`, so the generator writes the socket's new `ListenStream`, and a restart of the socket; on the RHEL family with SELinux, `semanage port -a`; ufw or firewalld, which it can't open; the firewall rules and the fail2ban jail for the old port, which move with it, and roll back with it. sshd reloads with `systemctl reload` under systemd and `rc-service sshd reload` under OpenRC.
- **The terminal reaches the server through the agent,** so closing port 22 leaves a way in, once that terminal is there (#208). Until it merges, `ssh.config` doesn't ship, and the way back is the provider's console.

### fail2ban

fail2ban is read where it's installed: its jails and recent bans, through `fail2ban-client`. A jail for SSH and one for the ingress are resources, `fail2ban.jail`, written to `/etc/fail2ban/jail.d/dockwell.conf`.

**Reading fail2ban comes first, and changes nothing** (`GetServerFail2ban`, once a minute while someone looks, as each `fail2ban-client` starts Python):

- `fail2ban-client version`, then `ping`, which fails only as fail2ban's server doesn't answer on its socket: stopped, with its words. Then `status` for the jails, and for each, `status <jail>` (failures and bans now and since fail2ban started, and the files or journal matches it reads), `get <jail> maxretry`, `findtime` and `bantime` (`-1` bans for good), and `get <jail> banip --with-time`, from fail2ban 0.11, for when each ban began and ends, in the server's time zone. Before 0.11, the status's list of addresses is all there is.
- **No chart of bans yet.** fail2ban keeps its history in its SQLite database, which the agent would need a SQLite library or the `sqlite3` tool to read; the first costs the agent's memory budget, and the second isn't on most servers. So the card says how many addresses are banned now, and how many bans since fail2ban started.
- **The chart's way forward is fail2ban's own log** (#361). fail2ban writes every ban and unban there, as `NOTICE  [sshd] Ban 198.51.100.77`: in `/var/log/fail2ban.log` and the files `logrotate` keeps beside it, or in the journal under its unit, as its `logtarget` says. The agent can count them by hour and jail over the last days while someone looks, a line at a time, with no SQLite, and the card then says the last 24 hours with the mock's chart.

**Writing jails** (`fail2ban.jail`, the slice after the read):

- **Dockwell keeps the jails its changes kept in its own state, and writes `/etc/fail2ban/jail.d/dockwell.conf` whole from them,** a section for each, in name order, each with `enabled = true`, its filter, the journal (`backend = systemd`) or its log files, its ports, and its counts and times in seconds (`bantime = -1` for good). With no jail left, the file goes.
- **A jail can't say more than its fields.** fail2ban reads the file as root: a new line in a value is the next setting, `[DEFAULT]` sets every jail, the stock ones it would turn on included, and an `action` is a command it runs. So a jail's name is letters, digits, `-` and `_`, and never `DEFAULT` or `INCLUDES` in any case; its filter is a name alone; and a log file is a full path under `/var/log/` of letters, digits and `. _ - + @ :`, with `*` and `?` for the files `logrotate` keeps, so no space, no new line and no `%`. The control plane refuses the rest when it's planned, and the agent checks again before it writes, whatever sent the jail. A log outside `/var/log/` waits for the ingress jail's slice to decide where Caddy's log goes.
- **A `dockwell.conf` Dockwell didn't write stays, and a link is never written through.** The file starts with a line that says Dockwell writes it. One that's there without it is someone else's: a change that would replace or remove it fails, saying to move what it sets to `jail.local`, and the read marks none of its jails as Dockwell's. The file is written beside itself under a name nobody can have put there, then renamed, and what's at its name has to be a regular file: a link there, or at a name Dockwell would guess, would have root write wherever it leads.
- **`fail2ban-client -t` checks the file before anything loads it,** and `fail2ban-client reload` loads it. If either refuses, the old file goes back, fail2ban stays as it was, and the step fails in fail2ban's words. A fail2ban that isn't running loads the file as it starts, and the step says so.
- **Every jail ignores the server's loopback and the control server's addresses,** which the agent resolves from the control plane's address as it writes, and keeps. When the name doesn't resolve, the jail ignores the addresses it last had; with none kept, it reads them back from the file as written, what a jail's `ignoreip` line holds beyond loopback and that jail's own list, and takes them only if writing the jails Dockwell holds with them gives the file back to the byte, so a jail can still be removed while the name doesn't resolve; with none from there either, the change is refused, as the jail would be written without what its plan says it never bans. An address with a zone is left out, as fail2ban takes none, and a control server with only such addresses is refused, not written as none.
- **What a jail ignores is the whole of it.** fail2ban takes a section's own `ignoreip` in place of what `[DEFAULT]` sets, whatever the files' order, so a jail Dockwell writes drops an admin's default whitelist for that jail unless it carries it. So the read asks fail2ban what each jail ignores as it runs (`fail2ban-client get <jail> ignoreip`) and shows it, and the form starts a jail's list from it.
- **The addresses signed in over SSH, and the person's own, are never banned by default.** The form's list starts with what the jail ignores now, the addresses signed in to the server over SSH as it's opened (as the firewall's pins read them: only connections someone has signed in on), and the address the control plane sees the person's browser at, each marked with why it's there and each removable; taking out one of those last two says, there and then, that a ban can land on it as the change applies. The plan names what the jail never bans, and which address signed in over SSH it could ban as it applies, when one was taken out. To revisit when unbanning ships.
- **An edit starts from the jail as Dockwell holds it,** which the read carries beside the jail as it runs, and changes only what the form shows: the count, the two times and the list. Its filter, what it reads and its ports stay, so a failed read of SSH's ports can't empty them, and a time outside the form's choices stays under an option of its own.
- **A jail names a few of each thing:** 32 ports, 16 log files, 64 addresses or ranges to ignore. A range that covers every address, such as `0.0.0.0/0`, or halves that add up to one, is taken, and the plan says the jail then bans nobody. A host name is taken beside addresses and ranges, as an admin's own list may hold one, and fail2ban looks it up.
- **A jail of Dockwell's that shares a name with fail2ban's own, such as Debian's `[sshd]`, sets that jail,** as fail2ban reads `jail.d` after `jail.conf`; the read marks the jails Dockwell writes. The tab offers to set the SSH jail, as it runs or new, closing SSH's ports to what it bans, and to stop writing a jail of Dockwell's, which leaves fail2ban's own as it was.
- **A change to a jail takes a signed-in person and a passkey, and no API token, with no timer** (a kind that decides who gets in, `DecidesWhoGetsIn`, beside the timer's `AccessGuard`).
- **The ingress jail is a slice of its own:** Caddy, which signs nobody in, needs a log on the server and a filter of what it counts as a failure, which that slice decides. **Unbanning** follows too, as a change with a plan and no revision.

- **Its bans aren't in `inet dockwell`,** which is replaced whole: fail2ban keeps them in its own table, as it does.
- **fail2ban takes the last value it reads,** so a person's `jail.local` overrides Dockwell's file, and Debian already turns on `[sshd]` in `defaults-debian.conf`. The tab shows each jail as fail2ban says it runs, not what Dockwell wrote.
- **The SSH jail reads the journal** (`backend = systemd`), as Debian 12 has no `/var/log/auth.log`.
- **The ingress jail watches Caddy,** which signs nobody in itself, so it needs a log source and a filter of its own: what it counts as a failure is decided with that slice. 1Panel's `openresty-auth` is its own jail, and isn't carried over.
- **`fail2ban-client -t` runs before every reload,** and the control server's addresses are in `ignoreip`.
- **A jail change has no timer, and its plan says whom it can ban.** A jail closes nothing until an address keeps failing to sign in, so a confirmation would prove nothing. But a jail that starts counts the failures of the last `findtime`, so an address that failed often enough just before is banned as the change applies, and fail2ban's stock actions drop its open sessions too. So the plan, in the panel and the CLI, names what the jail never bans and any address signed in over SSH that it could ban. **Undo doesn't lift a ban,** and removing Dockwell's jail where the distribution's own goes on doesn't either: the plan says so, with the way back in, from another address or the provider's console with `fail2ban-client unban`. Unbanning from Dockwell is its own slice.
- **Installing fail2ban** is the package manager's, which #276 brings.

### Who may change them

Every change to `firewall.rule`, `firewall.policy`, `ssh.config` and `fail2ban.jail` takes a signed-in person and a passkey just now, as anything that decides who gets onto the server does ([ADR 0032](0032-files-on-a-server.md)), and an admin or the owner (ADR 0048, in #255). No API token may make one. The person who applied it confirms it, in that session. Unbanning an address is an admin's, with no passkey, and is on Activity.

### How the agent runs its commands

The agent drives `nft`, `sshd`, `fail2ban-client`, `ufw`, `firewall-cmd`, `iptables-save`, `iptables-legacy-save`, `systemctl`, `rc-service` and `semanage` as commands, as ADR 0043 (#276) runs a package manager: by fixed paths, with no shell, a clean environment with `LC_ALL=C`, a deadline each, capped output, and one at a time. Standard input is `/dev/null`, except for `nft -f -`, which reads the table there. What a tool starts goes with it, whether the tool ends by itself or at its deadline; what leaves its process group with `setsid()` is out of reach without a cgroup of its own, which ADR 0043 (#276) should say too. It writes with `nft -f -` and reads with `nft -j`. It links no netlink or nftables library, so its idle memory doesn't move. Beyond the drift check's one listing a minute, it reads only while someone looks.

**A server without `nft`** says so, apart from one whose kernel won't load a table, as LXC and OpenVZ containers can refuse: each has its own words in the tab, and neither can be changed. Alpine and some minimal images ship without `nft`; installing `nftables` is a plan step through #276's install path, or `install.sh`'s.

### What the tab says of Dockwell's own firewall

- **Its rules and policy are as the server holds them,** as its agent says in the firewall's read, not the latest plan: what was last confirmed, and, while a change waits for Keep, that change's rules and policy beside them, marked, with nothing else to change until it's kept or put back.
- **Dockwell's table counts in how far what listens reaches,** as the others' do: its pins, its allows, its denies, then the policy, the first that matches deciding. With no other firewall there, the tab says only Dockwell's rules filter what comes in.
- **Turning deny everything else on lists what it closes,** in the plan: each port that listens on the server, or that Docker publishes, that no confirmed rule lets in from anywhere. SSH's ports and the control plane's own stay let in by their pins, so they aren't on it.
- **A server that can't hold Dockwell's table** says why on the tab, and offers no rule or policy.

### How this differs from the mock

- **The locked "Always last" row** becomes the policy, on or off, as the owner decided.
- **Rules other tools made** need a state of their own in the mock: read-only, under each tool.
- **"Used by"** needs what listens on the host and what Docker publishes, which the agent reads alongside.
- **The bans chart** needs a history `fail2ban-client` doesn't give; until the agent reads fail2ban's log for it (#361), the card says the bans now and since fail2ban started.
- **"Recent bans"** are the addresses banned now, the latest first, as fail2ban gives no others; each says its jail and when it began.
- **`openresty-auth`** is 1Panel's jail; Dockwell's would watch Caddy.

## Consequences

- A server keeps working as it did when Dockwell arrives; closing everything else is a choice, made with a plan that lists what would close, as the owner decided.
- Dockwell can't open what ufw, firewalld or iptables-legacy close, and says so. Someone who wants Dockwell to own the firewall turns those off, which the tab says how to do.
- Every firewall and SSH change costs up to 60 s of waiting for a confirmation, and the confirmation is only as good as the test the person runs, which the dialog names. The control plane's own check gates only when it means something, and says "can't tell from here" otherwise. What the timer can't see, a locked-out next login, is refused before anything applies.
- One change under the timer waits on a server at a time; a second is refused as busy until the first is kept or rolled back.
- The table, SSH's drop-in and Dockwell's jail survive reboots as confirmed, and the table survives flushes, as the agent and a boot unit put them back. Drift shows on Activity, and root on the server can turn the table off.
- Tests run the table against real nftables in CI, in a privileged container, and against a fake elsewhere. The install-test images (Debian, Ubuntu, AlmaLinux, Alpine) check the distributions' defaults this record relies on: `nft`'s presence, the sshd drop-ins and their order, fail2ban's defaults, and `ssh.socket`.
- Four of those defaults were checked on 2026-11-07 from the distributions' own packages, as no Docker was at hand to run the images:
  - Debian 13's `nftables` 1.1.7-3: its unit runs `nft -f /etc/nftables.conf`, whose shipped file starts with `flush ruleset`, before `network-pre.target`; it's installed disabled; and stopping it flushes the ruleset.
  - Ubuntu 24.04's `openssh-server` 1:9.6p1-3ubuntu13.20: `ssh.socket` listens on `0.0.0.0:22` and `[::]:22`, and `sshd-socket-generator` writes `ssh.socket.d/addresses.conf` from `sshd_config`.
  - Ubuntu 24.04's `cloud-init` 26.2: `disable_root: true` puts `command="echo …;exit 142"` before root's keys.
  - `sshd(8)`: `-T` applies `Match` blocks only with `-C`.

  The rest come from the review's knowledge until the install tests run them.
