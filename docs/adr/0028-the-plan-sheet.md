# 0028. The plan sheet: one shell, what can't be taken back first, and failures said twice

- Status: Accepted
- Date: 2026-11-05

## Context

Every signature flow runs through the plan sheet: a deploy, a variable, a firewall rule, a rollback, a delete (PRD signature experiences 1 and 3). [ADR 0017](0017-the-change-api-and-the-agent-stream.md) gave it its API, and it showed what that API returned, as it came:
- a form's sheet closed and a second one slid in, with the bright page showing through for about 260 ms;
- what a plan couldn't take back sat below the fold, under a promise of no downtime;
- one port took three rows named after protobuf fields;
- a change that had applied still spoke of what it was going to do;
- a failure read as a chain of Go errors with an environment's ID in it, twice.

Some of that was the panel's to fix. A failure wasn't: the words have to come from the server, or the CLI reads differently from the panel, and the panel can't word what only a driver knows.

## Decision

**One shell, from a form to its plan and back.** `Sheet` takes `over`, a `SheetView` that takes it over without closing it. The form stays mounted underneath, `inert`, with its values, its scroll and its focus. Views crossfade in 120 ms in one grid cell, and the old one stays for that long (`SheetSwap`). The scrim and the panel don't animate, so there is nothing to flash. Each `SheetView` tells the shell its labels and its close, so the dialog keeps one role and Escape closes what shows. A form hands on with `PlanView`, and the shell's own plan sheet is a `Sheet` with nothing but `over`. So Undo, and Cancel from it, happen in the same sheet.

**What can't be taken back comes first, and only that is an alarm.** One Callout at the top of the plan says what matters most, in the form's words. It stays through the run and the arrival, so nothing moves and the risk doesn't disappear once it is applied, with "Apply this only if…" becoming "Keep this only if…".
- Red, with a typed fingerprint and the danger button, is for what is as good as root or loses data: Docker's or containerd's socket, or another container runtime's, the server's own network, privileged mode, a capability or a group that is the same as root (ADR 0021), a system path, destroyed data, and a change that may cut off access. A system path is what the server's security rests on: `/etc`, `/root`, `/usr`, the cron spools, where a runtime keeps its containers such as `/var/lib/docker`, `/var/lib/containers` or `/var/lib/kubelet`, `/home` and a home directory itself, or any `.ssh`, or a path that holds one, such as `/var`. `HostAccess.same_as_root` says which, from `resource.Access.SameAsRoot`, and the panel counts the socket and the host network in any case.
- What a path is depends on where it leads, so a server's agent resolves it while it plans, and the control plane reads it in the fingerprinted plan as `HostAccess.leads_to`. A symlink to `/etc` is `/etc`, red, and says so. A volume plugin with `mountpoint: /etc` reads the same, from its options. An agent's word on host access counts for nothing except this, and it can only make a plan louder: what the path reads as written still counts, and the gate for a person is the control plane's own.
- Amber, with nothing to type and the ordinary Apply, is for everything else that reaches the server: a folder of the app's own, read-only or not, an NFS share, a macvlan network, a network the server already has, a capability or a group short of root. An owner mounts folders routinely, and a warning that comes with each one teaches people to skim the one that matters most. A time zone read from the server (`/etc/localtime`, `/etc/timezone`, `/usr/share/zoneinfo`, read-only) counts as an ordinary path too. That holds of one mounted with `:ro,Z`, which is the one way to widen it: Docker rewrites the labels of what's there, which is more than reading and doesn't give root, so the plan stays amber and says so.
- The gate itself doesn't change. Any host access still needs a signed-in person, tokens are still refused with `needs_session`, and the fingerprint still goes with Apply (ADR 0017, ADR 0021). What changes is what a person is asked to do by hand.

Rows follow the same split: `critical` for the first, `warning` for the second, never `diff-add` green, and first in their resource. Worst leads: root through Docker's socket, then the server's network, then other reach, then data, then lock-out.

**A change's summary stays in the words it was proposed in.** The panel writes what it proposes in the reader's language. The server's own, for a request that gives none, are English, such as "Run blog from a Compose file" from `dockwell compose import`. Activity and the plan show a summary as written, as they do one a person typed: it's the record of what someone said, so nothing can tell it from words to translate. Everything else a plan says that the server writes has a reason and names, so the panel says it in its own words.

**A plan reads as what it means, in the panel.** `useFieldRows` groups a resource's fields into rows: "8080 → 3000, TCP", "web-data at /data", "variable DATABASE_URL, hidden", a route or a firewall rule on one row when all of it comes or goes. A kind or field nobody has words for yet reads as words from its name, as "backends 1 host". The API keeps its paths, as they are what a script compares, and the fingerprint is unchanged. A row can't always be whole: `Diff` compares lists by position, so a port that changes shows the fields that changed.

**A plan says what it is for.** A plan says what happens to resources, which for a deploy or a new port is that a container is made again: true, and no news to whoever deployed. `Plan.intent` says what that comes to, from the method that proposed it: `DeployService`, `AddServicePort` or `RollBackService`. It lives in the stored plan, so it needs no migration, and it isn't in the fingerprint, as `notes` aren't. So the row's tag reads "Deploy", "Publish port" or "Roll back", the counter "1 to update", the step "Deploying nginx:1.29", and the title "Couldn't deploy nginx:broken" or "Rolled back to r127". The downtime stays, as that is the honest part. A change proposed as plain edits has none, and reads as what happens to its resources: a replace is a replace. Deploying the tag it already runs is `REPULL`, which may come to nothing: its downtime says "if there is a newer image", and a pull that finds nothing newer arrives as "web stays as it is", with `StepProgress.note` saying why, no counts and nothing to undo.

**A pull says what it did, not what it expected.** Deploying the tag an app already runs may come to nothing, so a plan can say only what it may do, and it says so where that holds: "1 to update if newer", "about 12 s down, if there is a newer image", "Undo for 7 days if this replaces anything". That holds for a step with nothing to change that a container can't change in place, the same rule as the CLI's. A step with more than that does it whatever the pull finds, and reads as what it is: "web is stopped, so this starts it", which only the server can say (`starts_stopped`), or, leaving a digest a rollback pinned, a deploy that "replaces web with what that names now". Once it has run, `StepProgress.did` says what each step did, server by server, and "web stays as it is" is only said when every step says it left what runs as it was. One server that replaced it is enough for the sheet not to say so. The step's words come with that, and nothing reads them to decide.

**What comes along folds.** The apps of a plan lead, the one with a way in first, open. What it only makes for them goes on one row, "Also creates project blog, a network and 2 volumes", which opens for whoever wants it. An environment that comes with a new project isn't shown at all (ADR 0026). What is at risk, and anything changed or deleted, stays on show, as that is news. A plan with no apps folds nothing. It arrives under the name you gave it, "blog is live".

**Steps wait for a fleet, and sit under the diff.** With one server there is nothing to tell apart, so a plan under review shows no steps (PRD principle 4). What a person has to weigh of how one runs, it says beside the diff (ADR 0027). Once it runs, its steps show under the diff, in the room it leaves, with what the driver is doing and for how long, and the body stays mounted: the reach, the counts and the rows hold their place from review to arrival, as `make e2e` measures. Once it lands, on one server, they go, as they say nothing the plan doesn't. `stepGroups` holds one group today; a rollout's waves (#28) become more of them.

**A plan says its safety net.** "Rolls back to r63 if it fails", from the resource's `base_revision`, as M-Plan-Approve has it. That is what exists today: a step that fails puts back what ran. Waves are still to come. The health checks that gate a deploy came with #28, whose plan says how a step rolls (ADR 0027).


**An arrival says what happened.** The title says "nginx is live", and the first line says where to reach it, or that nothing can yet and what to do about that. Counts and actions go into the past tense. Nothing moves when it lands, as that line is where the plan's reach was while it ran, and it is short enough to stay one line. "Live" is only said of a change this sheet watched apply. Opened from Activity later, the app may have moved on, so it reads "Applied 3 min ago by Mira Chen".

**A failure is said twice, and stops at what is known.** `resource.Failure` carries plain words and the chain behind them. `Error()` is still the chain, so a log and a wrapped error lose nothing, and `resource.Explain` gives the two apart.
- Drivers write the plain words: the fact, then the fix, with no IDs, and "this server" for where. They leave out what follows, such as whether the app runs now, as only the engine knows that: it rolls the change back next. And nothing sends a person to `docker logs`, as a rollback takes the container away, and a container's own output stays out of the record. What a health check said isn't that: it's short, cleaned and masked, and the one fact a person needs, so it goes in the words (ADR 0027). `internal/resource/container/failure.go` reads Docker's and the registries' messages for the failures people hit first: a pull refused, an image not found, no build for the platform, no network, a full disk, a port in use, a mount that fails, a missing command. The rest it reports in its own words, with Docker's reason in them.
- `CallError` gains `plain` beside `message`, so a newer agent speaks to an older control plane as before, and an older agent's message simply reads as it always did.
- `Change.error`, a step's `message` and a deployment's `error` hold the plain words. Once a plan has more than one server, the change's error names which. `StepProgress.detail` holds the chain, which the panel keeps behind a disclosure and `changes get` prints. It lives in the step's progress, so it needs no migration.
- The errors a call returns, which have no step to carry a chain, say the same with no change's ID where a person reads them: "another change is applying web now". This goes beyond the examples ADR 0017 gave. Where an ID helps a script, it stays in parentheses at the end, and the panel leaves it out.

**What a failure comes down to goes with it.** `Failure.Reason` and `StepProgress.reason` say "image", "command", "exits", "unhealthy", "port" or "mount", when the driver knows. A person can only fix what is in front of them, and the Deploy form has an image and nothing else, so an opening's `fix` says "Check the image and tag, then deploy again" there in place of the server's "Check its command and variables", which stays for the CLI and for a Compose file. It is also how a form can mark a failure at its field without reading its words.

**A rollback says how it went, through the API.** A rollback runs on after the change it rolls back has failed, so `rolled_back_by` says only that one was made. `Change.rollback_status` says where it is: applying, waiting for a server, applied or failed, with how many steps, what they put back, who it waits for, and if it failed, why. Each comes from the rollback's own record, read as the change is, and the panel follows it while it moves. So the panel and the CLI say the same thing and neither guesses:
- The sheet's first line says what Dockwell knows of what runs now, because that is what anyone wants to know after a bad deploy, and only then why: "Dockwell is putting nginx:1.29 back", changing live to "nginx runs nginx:1.29 again", which it knows as the rollback has just started it. It says the app was down while that happened only if the rollback put that app back.
- A rollback with no steps knows less. A pull that failed before anything changed reads "nginx stays on nginx:1.29", not "still runs", and not in green: its spec is as it was, and nothing has read whether it runs. It may have stopped or crashed long before, which ADR 0021 says isn't drift. The app's page says the same thing the same way, "nginx is on nginx:1.29, as it was before that deploy", and the CLI says "what was there before still is". Read later, on the record, each says what Dockwell did, "Dockwell put nginx:1.29 back on nginx", since what runs may have moved on.
- A first deploy has nothing to come back to, so once it is cleared away there is nothing to say.
- A rollback that failed says what may be left and what a person can do. There is no way to retry a rollback yet, so what they can do is deploy what should run, or fix it on the server. The app's page says the same across a reload, from `rolled_back_change_id` and `change_state`: "Rollback failed" in its state, the failure in its callout, and "Unknown, as putting it back failed" where the image goes, since the spec it reads is only what was asked for.

**A server lost mid-step gets one answer.** `StepProgress.lost` says the server went away during the step, so nothing can say whether it ran. It reads as that, not as a failure: "edge-1 went offline during this deploy", "Dockwell can't tell whether nginx:1.28 started", "Once edge-1 reconnects, Dockwell puts nginx:1.27 back", with Done as its action, as a form can't help. The app's page says the same: what waits is the rollback, and its image is unknown until then.

**A refusal that stops being true goes away.** "Another change is applying web now" is no longer so once that change ends, and nothing says so, so the sheet looks every 1.5 s while it shows one, and drops it once no change is applying. Any other refusal stays until you act on it.

**You can leave from anywhere.** "Edit and try again" goes back to the form, and Done and × leave altogether, from a failure as from anything else (`onDone`).

**A sheet leaves as it came.** It slides and fades away over the 260 ms it took to come, where it used to cut from scrim to bright page in one frame. A sheet is often unmounted along with what holds it, so what slides away is a copy, inert and hidden from assistive tech, and under reduced motion there is none. Focus goes back to what opened it, or to the page's heading when that has gone, as it has after a first port takes away the button that opened it. It never falls to the body.

**A step says what it is doing.** `StepProgress.activity` is what its driver last said, such as "Pulling nginx:1.27: 12 of 48 MB", apart from `message`, so the panel can tell it from the step's own line and say that in the right tense and language. It is cleared as the step ends.

**The same action keeps its name.** "Delete" from the button to the plan to the arrival, in the panel and the CLI: "to delete", "Delete images", "images is deleted". `PlanAction`'s `destroy` stays as an identifier, as `destroys_data` does for a different thing, data. An undo's summary is "Undo: …", which reads as a sentence. A delete says what stops, what stays and until when, once, in agreement with the footer: "pg stops. pg-data stays, and you can undo this until 12 Nov."

**A loading button keeps its focus.** `Button` with `loading` uses `aria-disabled`, not `disabled`, which drops focus to the body, where Escape no longer reaches the sheet. So the keyboard goes all the way: ⌘↵ applies, focus moves to the heading while it runs, then to the final button, and ⌘↵ takes that too. A key still held from the step before doesn't count, so nobody applies a plan unseen.

## Consequences

- A driver's plain words are English, as every API message is. The panel translates what it words itself, and the reasons it knows, but a failure's words read in English in zh-CN until the API has a way to say them in parts.
- Reading Docker's messages by their words can fall behind a new Docker. The cost is small: a failure the words don't match says Dockwell doesn't recognize it, with what Docker said beside it and the whole chain behind Details.
- `rolled_back_by` still says one was made, whatever came of it, so a script that read it as "rolled back" should read `rollback_status`.
- System paths are a list, and it can't be complete. A path it misses gets the amber warning rather than the alarm, and still needs a signed-in person, so what it costs is a louder word, not the gate. It doesn't catch:
  - what root-run software happens to trust, wherever it is: `/opt`, `/srv`, an app's own directory that a root service reads its scripts from, and `/var/log` where a root job parses what is there;
  - a folder inside a home directory, other than `.ssh` and a dotfile at its top, and a home outside `/home`;
  - a volume plugin's options other than an absolute path under a system path, and whatever a plugin does on its own;
  - a symlink changed after the plan, since Docker resolves it again when it starts the container. The plan's fingerprint covers what it read then, not the server's disk;
  - anything an agent can't read: a server that's offline, or one on an older agent, reads as written, and so does a path that doesn't exist yet.
- The CLI still says "to replace" for a deploy, as its plan view is for what happens to resources. The summary above it says what it is for.
- A sheet's copy stays in the page for 260 ms after it closes. It names nothing and takes no input, but a test that looks by CSS class or text, not role, can see it.
- `Sheet`'s `title` is optional when `over` holds all it shows. A form that keeps its sheet mounted under a plan keeps its effects running. None of today's do anything while covered, and `useSheetViewAway` says when a view is covered or leaving, which is how the plan sheet's window-wide ⌘↵ stands down.
- The design system's PlanDiff and Sheet READMEs and `index.d.ts` describe the imported reference, and say "destroy" and know nothing of `over`. They change on the next re-import from Claude Design.
- `make e2e` now measures contrast and runs axe over the sheet in a real browser, in both themes, and the fake engine can fail each way a first deploy really does.
- **The plan can still move for what nothing knew at the review, and that stays.** Room is held for what a plan says it will lead with. A failed read's notice moves it down about 104 px. On HTTPS it moves down about 60 px as it lands, and up about 164 px as the certificate arrives, when what said it was on its way goes. On a phone it moves about 118 px from the review to applying, as a phone's review has no lead line, which keeps the plan on screen there. Holding room for a notice that may never come would leave a gap in every plan, for a move that can't cost anything: by then the plan is approved, nothing in it is about to be pressed, and the footer's buttons don't move.
- **A title stays on one line, so a very long name takes its verb with it.** An 89-character domain cuts off "is created". A title that wraps moves the plan under it, and the subtitle says what the change was, whole, on as many lines as it takes, as the row under it says how it stands. So it stays cut.
