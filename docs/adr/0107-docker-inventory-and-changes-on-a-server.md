# 0107. Docker inventory and changes on a server

- Status: Accepted
- Date: 2026-11-20

## Context

Server Overview lists containers Dockwell did not make, while Apps shows the services it owns. To diagnose a machine, a person needs to see what Docker runs and keeps on it in one place. The view must preserve the ownership boundary in [ADR 0031](0031-containers-dockwell-didnt-make.md) and the plan and revision model in [ADR 0009](0009-resources-revisions-and-plans.md).

## Decision

- A server's Docker workspace shows what the selected Engine runs and keeps. The same workspace can inspect several servers. Each row has a server and its Engine identity. In a fleet, counts say which servers could answer, and a plan names the servers it touches.
- Machine inventory is an install-admin read. The agent projects typed facts before sending them. Environment, commands, arbitrary labels, driver options and health check output stay on the server. Compose project and service names are identity fields. Ownership combines those names with the control plane's records and the agent's adopted IDs. Project-scoped Apps, Compose and Volume reads retain their roles.
- Detail uses an immutable Engine ID. Existing container URLs and the legacy name-following logs keep their behavior. A missing ID can point to the container now using its name. Terminal exact-ID exec keeps the same session, host-access, passkey and audit rules as a container shell.
- Each connected agent reports capabilities. Only an open view subscribes to inventory changes and requests container samples. Reads, cursors, messages and subscriptions are bounded. When a view loses its stream it obtains a new snapshot. Logs and terminal traffic keep their existing separate streams.
- Every managed change uses its current resource and a reviewed revision plan. A configuration or lifecycle change to an external container begins with take-on. Start and Stop are revision edits for the entire placed workload. They name the base revision and alter only its desired run state. Docker uses an effective restart policy of `no` while stopped. The agent keeps the configured policy by Engine ID, and a deploy creates the replacement without starting it. Start restores the policy and verifies health. The change plan calls out the effects on routes, checks and dependants.
- Restart remains a reviewed transient action. From an instance row it pins the full Engine ID and server in the plan, rechecks placement and identity before applying, then restarts that container in place.
- The exception to spec revisions covers only removal of local images, build cache records and Docker networks for which Dockwell holds no desired state. A reviewed plan freezes exact identities and servers and rechecks identities and dependencies at apply. Changes in either require review again. An install admin applies the plan with a passkey. Record per-object receipts in Activity. Daemon-wide prune and force delete are prohibited. Verify an ambiguous result before resuming. A concurrent Docker command between the recheck and deletion can add a tag that is removed with the reviewed image or make Docker remove a network named after a vanished ID, while moving a tag to another image leaves that image untouched. All volume removals, named or anonymous, go through take-on and a revision.
- An image is dangling when it has neither a tag nor a repository digest. Local image cleanup deletes by full ID, including opt-in unused images with at most one tag and references in one repository. Images with multiple tags or references in multiple repositories stay protected. Keep the images used by Dockwell infrastructure and by deployments that are live, pending or within the seven-day undo window. Deployments record the local image ID separately from the registry digest.
- Exact build-cache removal is enabled for Docker Engine Community 27.3.1 and 28.5.2. In those releases, [Moby 27.3.1](https://github.com/moby/moby/blob/v27.3.1/builder/builder-next/builder.go) and [Moby 28.5.2](https://github.com/moby/moby/blob/v28.5.2/builder/builder-next/builder.go) pass the anchored ID filter to their bundled [BuildKit 27.3.1 cache matcher](https://github.com/moby/moby/blob/v27.3.1/vendor/github.com/moby/buildkit/cache/manager.go) and [BuildKit 28.5.2 cache matcher](https://github.com/moby/moby/blob/v28.5.2/vendor/github.com/moby/buildkit/cache/manager.go). The request sends the anchored ID and the reviewed last-use cutoff. BuildKit treats `inuse` and `shared` as presence fields, and its default prune skips records in use, shared records, and internal and frontend records. Check the cache listing immediately before and after the prune. If Docker reports an extra removal, an eligible unreviewed record disappears, or the outcome cannot be verified, the agent pauses cleanup on that server. The Cleanup page explains the pause and an install admin can re-enable cleanup there with a passkey. The pause survives receipt expiry.
- Image pull, tag, load, build, export and push use reviewed plans and receipts. These actions leave managed state untouched and sit outside the exception to principle 2. Only an install admin may apply them. Any step that deletes an artifact requires a passkey.
- Daemon settings that Dockwell takes on are revisioned field by field. A supported daemon manager validates and atomically applies the approved keys while preserving other keys. A local watchdog keeps the previous configuration available through a disruptive restart. Verify effective settings and Engine health before reporting success.

## Numbers

The agent's Docker topic uses tags 400 to 419. Inventory list, detail, subscription and notifications use 400 to 403. Hello carries the capability at 400. The terminal call and public terminal request use 400 for the Engine ID and 401 for arguments. `DesiredResource.exact_restart_id` uses 408. The `DockerCapabilities.workload_controls` flag uses 3 within that message. `Container.desired_run_state` and `AdoptContainerRequest.expected_container_id` use 400. `RestartServiceRequest` uses 400 for the server and 401 for the Engine ID. The public Docker messages have message-local fields.

## Consequences

Docker, Apps and Projects share links and the same plans. An older agent can still serve its existing pages and actions, and Docker inventory reports that the agent needs an update. The agent's idle budget stays at 40 MB. Cleanup and daemon writes need real Engine checks, including interrupted apply and recovery, before their controls ship.
