# 0107. Docker inventory and changes on a server

- Status: Accepted
- Date: 2026-11-20

## Context

Server Overview lists containers Dockwell did not make, while Apps shows the services it owns. To diagnose a machine, a person needs to see what Docker runs and keeps on it in one place. The view must preserve the ownership boundary in [ADR 0031](0031-containers-dockwell-didnt-make.md) and the plan and revision model in [ADR 0009](0009-resources-revisions-and-plans.md).

## Decision

- A server's Docker workspace shows what the selected Engine runs and keeps. The same workspace can inspect several servers. Each row has a server and its Engine identity. In a fleet, counts say which servers could answer, and a plan names the servers it touches.
- Machine inventory is an install-admin read. The agent projects typed facts before sending them. Environment, commands, arbitrary labels, driver options and health check output stay on the server. Compose project and service names are identity fields. Ownership combines those names with the control plane's records and the agent's adopted IDs. The Compose workspace and its plans use install-admin access. Project-scoped Apps, Compose import and export, and Volume reads retain their roles.
- Detail uses an immutable Engine ID. Existing container URLs and the legacy name-following logs keep their behavior. A missing ID can point to the container now using its name. Terminal exact-ID exec keeps the same session, host-access, passkey and audit rules as a container shell.
- Each connected agent reports capabilities. Only an open view subscribes to inventory changes and requests container samples. Reads, cursors, messages and subscriptions are bounded. When a view loses its stream it obtains a new snapshot. Logs and terminal traffic keep their existing separate streams.
- Every managed change uses its current resource and a reviewed revision plan. A configuration or lifecycle change to an external container begins with take-on. Start and Stop are revision edits for the entire placed workload. They name the base revision and alter only its desired run state. Docker uses an effective restart policy of `no` while stopped. The agent keeps the configured policy by Engine ID, and a deploy creates the replacement without starting it. Start restores the policy and verifies health. The change plan calls out the effects on routes, checks and dependants.
- Restart remains a reviewed transient action. From an instance row it pins the full Engine ID and server in the plan, rechecks placement and identity before applying, then restarts that container in place.
- A managed Compose workspace edits the environment's portable projection from an explicit snapshot. The plan applies YAML differences to the saved specs and checks each touched revision. Sealed values and settings outside the projection stay with their resource. An omission cannot delete a service or network without naming it for review. Deleting a stack keeps its volumes by default, and the revision engine checks dependency links across environments. Backup previews identify their volume or database and use the existing backup operation on the chosen server. Each source has its own result.
- The exception to spec revisions covers only removal of local images, build cache records and Docker networks for which Dockwell holds no desired state. A reviewed plan freezes exact identities and servers and rechecks identities and dependencies at apply. Changes in either require review again. An install admin applies the plan with a passkey. Record per-object receipts in Activity. Daemon-wide prune and force delete are prohibited. Verify an ambiguous result before resuming. A concurrent Docker command between the recheck and deletion can add a tag that is removed with the reviewed image or make Docker remove a network named after a vanished ID, while moving a tag to another image leaves that image untouched. All volume removals, named or anonymous, go through take-on and a revision.
- An image is dangling when it has neither a tag nor a repository digest. Local image cleanup deletes by full ID, including opt-in unused images with at most one tag and references in one repository. Images with multiple tags or references in multiple repositories stay protected. Keep the images used by Dockwell infrastructure and by deployments that are live, pending or within the seven-day undo window. Deployments record the local image ID separately from the registry digest.
- Exact build-cache removal is enabled for Docker Engine Community 27.3.1, 28.5.2 and 29.4.1. The request sends the anchored ID and the reviewed last-use cutoff. Before and after each prune, verify the cache listing. If Docker reports an extra removal, an eligible unreviewed record disappears, or the outcome cannot be verified, the agent pauses cleanup on that server. The Cleanup page explains the pause and an install admin can re-enable cleanup there with a passkey. The pause survives receipt expiry. [Moby 27.3.1](https://github.com/moby/moby/blob/v27.3.1/builder/builder-next/builder.go) · [BuildKit in 27.3.1](https://github.com/moby/moby/blob/v27.3.1/vendor/github.com/moby/buildkit/cache/manager.go) · [Moby 28.5.2](https://github.com/moby/moby/blob/v28.5.2/builder/builder-next/builder.go) · [BuildKit in 28.5.2](https://github.com/moby/moby/blob/v28.5.2/vendor/github.com/moby/buildkit/cache/manager.go)
- In 29.4.1, Moby converts the reviewed timestamp to a keep duration and passes the anchored ID as a regex to the BuildKit controller. Vendored BuildKit 0.29.0 treats `inuse` and `shared` as presence fields. Its default prune excludes records in use, shared records, and internal and frontend records before matching the regex and cutoff. CI requires exact removal on both 29.4.1 image stores. [Moby ID filter and cutoff](https://github.com/moby/moby/blob/6c91b92cc71077b70c779c510da125301a8e40f3/daemon/internal/builder-next/builder.go#L659-L714) · [Controller call](https://github.com/moby/moby/blob/6c91b92cc71077b70c779c510da125301a8e40f3/daemon/internal/builder-next/builder.go#L227-L239) · [BuildKit exclusions and match](https://github.com/moby/moby/blob/6c91b92cc71077b70c779c510da125301a8e40f3/vendor/github.com/moby/buildkit/cache/manager.go#L1148-L1189) · [Field adapter](https://github.com/moby/moby/blob/6c91b92cc71077b70c779c510da125301a8e40f3/vendor/github.com/moby/buildkit/cache/manager.go#L1634-L1658) · [Regex matcher](https://github.com/moby/moby/blob/6c91b92cc71077b70c779c510da125301a8e40f3/vendor/github.com/containerd/containerd/v2/pkg/filters/filter.go#L163-L174)
- Image pull, tag, load, build, export and push use reviewed plans and receipts. These actions leave managed state untouched and sit outside the exception to principle 2. Only an install admin may apply them. Any step that deletes an artifact requires a passkey. Image operations in this delivery require a signed-in session and the reviewed fingerprint. API-token apply is a later decision. Push, alias replacement and tag removal require a fresh passkey scoped to the exact change and fingerprint.
- Pull resolves and verifies a platform manifest before review, then pulls that manifest digest. The classic store identifies the result by config digest. The containerd store identifies it by the OCI manifest digest and reports the target descriptor. Both use the full Engine ID for tag writes, receipts, and read-back. A matching platform manifest or matching index with the reviewed platform present needs no change. Compare only confirmed kinds of digest. Tagging preserves other aliases and both images on a move. Retained desired state and the agent's infrastructure references can protect an alias even while it is absent. Docker offers no atomic compare-and-swap for tags, so the agent rechecks immediately before the write and verifies the result afterward. A lost reply is checked before any new review. Remove tag stays unavailable until Engine can guarantee an identity-bound, alias-only removal.
- For image cleanup the containerd store can list an explicit digest reference alongside tag names. Count it once as digest evidence. Several independent references on one image block non-forced deletion by ID even within one repository. Exercise images and cleanup on Engine 29.4.1 with its containerd store and on the classic store in CI. Exact build-cache removal stays limited to the approved Engine versions above.
- Image plans hold the saved registry login ID, name, host and revision where needed. The control plane reopens that revision at apply and seals its credentials for the selected agent and frozen operation. Review refuses a Docker Hub login on an Engine with mirrors. Docker receives auth only for the selected registry and pinned digest, after a fresh challenge check. The panel and stored records contain no credentials or raw registry output.
- Network and volume inventory read Engine attachments, including stopped containers. Network creation and volume creation use create-only revisions and verify the Engine object carries the approved creation marker. Network attachment changes edit the workload's saved spec, check the full network and container IDs and the observed attachment again at apply, and use the normal rollout and undo. The cleanup exception covers eligible external networks. It excludes all volumes, including unused and anonymous ones. Volume removal requires a reviewed revision that checks for named dependants. Volume browsing uses Files access and volume backup uses the existing Backup preview for the selected managed placement.
- Image import and export stage their bytes on the selected agent. Unreviewed uploads and sealed downloads have a 24-hour outer lease. The upload commits each prefix with its SHA-256 and reconciles committed offsets on restart. Validate Docker save archives and rewrite them before giving bytes to Engine. Load by verified config and layer identities with no original tags. Add only reviewed aliases that are still free. An interrupted load can leave anonymous images for normal cleanup. Export by full Engine ID and the reviewed platform, and include only reviewed aliases. Serve the sealed archive with a strong ETag and byte ranges to the creating actor and session. The agent opens single-use mTLS file streams for the exact lease and byte extent. The private spool is outside managed backup inputs and Files.
- The agent shares three transfer slots between Files and image artifacts. One validation slot serializes archive checks and Engine load or save on each server. Finish records the check before replying, and the agent resumes the queue on restart. The creating session can list, resume or abort its leases. An archive with no reviewed change expires after 15 minutes of inactivity. Queued checks and archives held by a pending or applying change stay staged. The agent journals the change binding before publication and reconciles it with the control plane when connected. Gzip reserves an initial expansion estimate of four times the uploaded size, capped at 256 MiB, and reserves more as it expands. Uploads retry admission when the shared lane is full. Apply takes a slot within the change deadline. A completed import keeps its receipt and releases the archive. A sealed export stays available to its creating session for range retries until it expires or the session aborts it.
- Push stages one installed platform from a full Engine image ID and reviews its hashed Distribution manifest. Destination checks and publication use the saved login over HTTPS, with repository-scoped pull and push permissions when the registry provides tokens. Only an absent destination or the exact digest is eligible. Upload only missing blobs and check the destination again before one manifest write. A registry tag can still change between that check and the write. Publication by digest avoids changing a tag. A lost acknowledgement or different read-back leaves an unknown receipt and offers a read-only check. Dockwell never retries an ambiguous write or deletes remote content to recover. A definite refusal or timeout before publication records that no manifest was published. Azure, GCS and S3 redirects for blob requests are followed on public HTTPS without registry credentials. Four push sends can run per agent. Archive validation releases its slot before sending.
- Daemon settings that Dockwell takes on are revisioned field by field. A supported daemon manager validates and atomically applies the approved keys while preserving other keys. A local watchdog keeps the previous configuration available through a disruptive restart. Verify effective settings and Engine health before reporting success.
- The daemon editor owns registry mirrors, finite logging defaults and IPv4 address pools. Insecure registries, live restore, bridge IPv6, the data root and the image store are read-only. Writes require a reviewed revision and a fresh install-admin passkey bound to its fingerprint. The local systemd worker validates the whole candidate with the installed `dockerd`, records the previous file, and checks the result after activation. Docker can reload a changed mirror list when the file specifies it. Removing a nonempty list by restoring an absent key, changing logging, or changing address pools requires a reviewed restart. The worker refuses a file that differs from the reviewed base and restores the previous file if activation fails or the agent cannot acknowledge it. After the agent connects, background recovery settles incomplete transactions without blocking the control plane. A live worker keeps its lock so the resumed apply can acknowledge it. A lasting recovery failure is visible in Docker settings. An install admin can review the pending local file against the last verified running file and approve activation of supported settings without taking ownership. The revision engine leaves recovery to the worker. Changes to logging defaults affect new containers. An existing workload receives limits through its own replacement revision.

- Compose templates are project resources with no server placement. A template holds one portable Compose file, named inputs and optional Git provenance pinned to a commit. It has the ordinary review, revision history and undo. Project viewers can read it and developers can create, edit, remove and use it. A backup of the control-plane store includes saved revisions. Saving from a stack reads an independently sealed projection without secret values. Revisions written before the projection was introduced need a new revision before Save as template can read them. A deployment creates a new Compose environment through the existing planner from an exact template revision. Secrets are generated or supplied at review and stored as sealed environment values. Template edits or removal leave deployed workloads and reviewed plans independent.

### Standalone Dockerfile builds

A build is a reviewed image action with a receipt. It uses the existing BuildKit
runner and queue on the chosen server. A folder is copied through the FileService
path guard, with Docker's ignore rules applied. Uploads use the same resumable
artifact lane as image archives. The review freezes the context hash or Git
commit, the Dockerfile hash, the native platform and each approved base-image
manifest. BuildKit's source policy enforces those manifest pins. Dockerfile
overrides are private artifacts tied to the change.

A build may use explicitly selected registry logins. The control plane rechecks
their revisions when applying and seals the credentials for that change and
agent. The runner checks the registry challenge again when work begins. The
standalone cache is shared only by builds with the same login set and revisions.
Logs use the existing bounded recorder and mask known credential forms.

BuildKit writes its result to private scratch space. Before handing it to Docker,
Dockwell checks the unique output tag and requires free space above the disk
floor for twice the archive size plus 256 MiB of working space. The disk watch
cancels the load if available space drops below the floor. User cancellation
before the handoff leaves the output tag absent. After the handoff, the receipt
reports the image Docker took or that the outcome could not be verified.
Existing aliases can be assigned to the result through a separate tag review.

This delivery uses `PlanDockerMaintenanceRequest.build` 14,
`DockerImageAction` 6–8 and 14, `DockerImageReceipt.build_id` 9,
`DockerImageOutcome` 5, `DockerImageSupport.can_build` 4,

401. The build log and cancellation share the existing response messages.
The pending push and untag fields stay reserved for their approved deliveries.

## Consequences

Docker, Apps and Projects share links and the same plans. An older agent can still serve its existing pages and actions, and Docker inventory reports that the agent needs an update. The agent's idle budget stays at 40 MB. Cleanup and daemon writes need real Engine checks, including interrupted apply and recovery, before their controls ship.

Compose templates use `Spec.kind.compose_template` 401. The four ComposeService methods use message-local fields and no agent messages.
