# 0111. CI deploys of prebuilt images

- Status: Accepted (slice 2 built)
- Date: 2026-11-26

## Context

Dockwell can build from Git or deploy the image a pipeline has already pushed. The second path needs a receipt tied to the commit, a way for the pipeline to wait for rollout, and a token that does just that. A pipeline may retry a request whose response it lost, including while Dockwell restarts. See [ADR 0046](0046-builds-from-git.md), [ADR 0071](0071-api-tokens-narrowed-to-projects-and-a-role.md) and [ADR 0098](0098-connecting-github-as-an-app.md).

## Decision

### Correlation and rollout

- `DeployService` accepts a CI provider, repository URL, full commit SHA, Git ref and run URL. URLs are HTTPS without user information, query strings or fragments. These facts come from the pipeline and identify its reported source. Dockwell keeps each attempt's reported provenance in normalized columns keyed by change. The latest-attempt key can move independently of that history.
- The plan keeps the requested image reference and the immutable manifest digest. Accept an image by digest, or resolve its tag on a target server using the app's registry login and the existing image-read call. Store the pinned image in the proposed service spec. The rollout and rollback use the usual revision engine. The deployment record inherits provenance from the change that produced its revision.
- Migration 0061 adds a unique key on service ID, manifest digest and normalized commit SHA. The transaction that records the plan claims the key. A racing request returns the winning change and leaves no duplicate plan or event. A retry follows an applicable plan, an applying change, or a successful change whose pinned revision still owns the live deployments. A failed, discarded, stale or replaced attempt lets the transaction move the key to a new plan. An older commit can deliberately redeploy its digest and uses the same approval rules. A CI attempt can record a new revision for the same image to keep its own commit visible. Both CI tables advance the control backup position on SQLite and Postgres. A tag that moves to another digest is a different artifact.
- The API returns provenance for changes and service deployments. Deployments and Activity show the commit and CI run. GitHub and GitLab have known commit URL formats, and other providers supply a commit URL.
- `dockwell services deploy --wait` applies the plan and follows its terminal result. It prints a link to the change and leaves approval of protected or host-sensitive plans to someone in the panel. It retries transient proposal failures when it has correlation, and reconnects to dropped watches by reading the change again. The default deadline is 30 minutes. Failed, rolled back, awaiting approval at the deadline, timed out and discarded outcomes have distinct rollout exit codes.

### Tokens and shipped workflows

- The Deployments sheet uses `TokenService.CreateToken` and the existing passkey step-up. Deploy scope is a read-write credential bound to exactly one service, its existing environment and project, capped at developer. It allows planning a correlated deploy for that service and applying, reading and streaming that deploy's change. The issuer's current role and ordinary host and protected-environment rules still apply. The token name and target are audited using existing token events. Only the creation response carries the secret.
- The GitHub composite action is at `ci/github/action.yml`, addressed by the Dockwell release tag or commit. With a commit pin, pass a matching release tag to choose the CLI. The GitLab input template at `ci/gitlab/dockwell-deploy.yml` is includable from the same release tag and can move unchanged to a GitLab Catalog project. Both invoke the same script. GitLab downloads the release asset and verifies its checksum with a checksum-pinned Cosign before executing it. The script uses a pinned Cosign executable, the exact Dockwell tag's release-workflow certificate identity and issuer, and the signed SHA-256 of the Linux amd64 or arm64 full binary archive. The CI token is read from the runner's environment.
- No agent protocol change is required. Public fields are `DeployServiceRequest.deploy_origin` 6, `Change.deploy_origin` 25 and `ServiceDeployment.deploy_origin` 7. `DeployOrigin` uses fields 1 through 8. `DeployProvider` uses values 0 through 3. `TokenScope` adds value 3, `CreateTokenRequest.deploy_service` is 9, and `Token.deploy_service`, `Token.deploy_environment` and `Token.deploy_service_name` are 12, 13 and 14.

### Status in slice 2

- **Token-bound repository (no pipeline-chosen status targets).** The repository a CI deploy may report status to is owned by Dockwell on the deploy token (`api_tokens.deploy_repository`, set at creation in **Deploy from CI** from the GitHub App or GitLab connection picker, or updated later on **Settings -> API tokens** via `TokenService.SetTokenDeployRepository`). A deploy whose provenance names a different repository still deploys (slice 1 is unchanged), but Dockwell posts nothing before consulting any provider. Tokens created before slice 2 have an empty `deploy_repository` and report nothing until a repository is set. `DeployStatus.token_repository` is populated only for the token's owner; all provider-not-reached conditions collapse into a single reason so callers cannot enumerate repositories across projects or installations.
- **Durable outbox (migration 0062).** `ci_status_outbox` records each status transition (`queued`, `applying`, `healthy`, `failed`, `rolled_back`, `discarded`) inside the same revision transaction as the change state transition, with a monotonic per-change `transition` number, `environment_name`, `token_id`, `allowed_repository`, provenance copied from `ci_deploy_origins`, the image digest, public panel change URL (`/changes/<id>`, or empty when no public panel domain is configured; never the private listen address), a per-transition `idempotency_key` (`dockwell:<change_id>:<transition>:<state>`), delivery state (`pending`, `delivered`, `skipped`, `failed`, `superseded`), structured `reason_code` (`DeployStatusReason`), provider `remote_id` and `remote_url`, `credential_ref` kept separate from `ci_deploy_origins`, `attempts`, `next_attempt_at`, `retry_since` (initialized to 0 and set on the first delivery attempt), and `last_error`. Discarded, stale, or superseded planned CI deploys enqueue a final `discarded` transition (`cancelled` on GitHub, `canceled` on GitLab). Changes without a `ci_deploy_origins` row receive no outbox entries. `ci_status_outbox` is excluded from the control backup change-position triggers (like `alert_deliveries` and `alert_sends`) so retries do not churn backup schedules while snapshots still capture the table; `controlbackup.Extract` marks any restored `pending` outbox rows as `superseded` so a restored control plane never replays historical statuses.
- **Worker ordering, host isolation, no-regression, and bounded retries (`internal/control/cistatus`).** Delivery runs asynchronously outside the revision engine and its write lock. Due changes are grouped by provider host and processed concurrently across hosts (up to 4) while skipping remaining changes for an unreachable host in the current pass so one slow self-managed instance cannot stall others. Per-change serialization uses a ref-counted lock map that shrinks back to empty once idle. Transitions deliver in ascending `transition` order; any pending transition older than `max(delivered transition)` is marked `superseded`, and a newer due transition supersedes an earlier backing-off transition. Transient failures (network errors, HTTP 429, 5xx) retry with exponential backoff (5 s base, capped at 5 m, honoring and capping `Retry-After`) and resume cleanly across control-plane restarts. After a bounded window measured from the first attempt (30 minutes or 12 attempts), delivery marks the entry `failed` with `DEPLOY_STATUS_REASON_GAVE_UP`, stores provider detail in `last_error`, and records `ci_status.failed` on the audit log and Activity. `ChangeService.RetryDeployStatus` only accepts `failed` or `skipped` entries (returning `not_retryable` otherwise), refreshes `allowed_repository` from the deploy token, records `ci_status.retried` on the audit log, and starts a fresh retry window.
- **GitHub Check Runs (`checks: write`).** Dockwell reports GitHub CI deploys as Check Runs named `"Dockwell / <env> / <service>"` (falling back to `"Dockwell / <service>"` when environment is unset) so multiple environments deploying the same commit never collide. One Check Run per change is created with `external_id = change_id` and updated in place (`PATCH /repos/:owner/:repo/check-runs/:id`) as the deploy moves through `queued`, `in_progress`, and `completed` (`success`, `failure`, or `cancelled`), carrying `details_url` pointing to `/changes/<id>` when a public panel domain is configured. Before every create (including attempt 0 after a restart between create and DB write), Dockwell looks up an existing check run by `external_id` so duplicates are never created. New GitHub App manifests request `checks: write`. Migration 0062 adds `permissions` JSON to `github_installations`; on a 403/422 refusal, Dockwell re-reads the installation's live permissions from GitHub before concluding `checks: write` is missing so a single archived repository never disables reporting for the rest of the installation. Settings -> Integrations flags missing Checks permission per App/installation with a direct link to GitHub's permissions page and a `Check again` action (`GitProviderService.RefreshGitHubApp`, `EFFECT_APPLY`), and background delivery checks auto-refresh installations lacking `checks: write`.
- **GitLab Commit Statuses (`gitlab.connection` resource kind).** Rather than overloading the app-linked infrastructure `connection` kind (ADR 0099, whose secrets are delivered to agents and probed from agent containers), slice 2 adds a dedicated organization-level `gitlab.connection` resource kind (`Spec.gitlab_connection = 131`, ID prefix `glc_`). Each connection holds a normalized HTTPS instance URL, an encrypted access token with `api` scope (never returned by the API and never reused across a changed URL), an optional group/project `path_prefix` (most specific match wins), and optional project reach. All outbound GitLab verification (`GitProviderService.CheckGitLabConnection`), project listing (`GitProviderService.ListGitLabProjects`), and commit status calls (`POST /api/v4/projects/:id/statuses/:sha`) run from the control plane through `netguard` with `netguard.Options{Private: true}` (same rules as `alert.Guard`, allowing admin-configured RFC 1918 self-managed GitLab hosts while blocking loopback, link-local, metadata, multicast, reserved addresses and redirects; `CheckGitLabConnection` requires an admin session). Project paths reject `.` / `..` / empty / odd segments and escape each path segment when constructing remote links. Duplicate status retries that return GitLab's 400 "Cannot transition status" are verified idempotently against the commit's existing status.
- **Schema and proto numbers.** No agent protocol change is required. Migration `0062` (`0062_ci_status.sql`, adding `github_installations.permissions`, `api_tokens.deploy_repository`, and `ci_status_outbox`). `specs.proto`: `Spec.gitlab_connection = 131`, `GitLabConnection` fields 1 through 4. `token.proto`: `TokenService.SetTokenDeployRepository` RPC, `Token.deploy_repository = 15`, `CreateTokenRequest.deploy_repository = 10`, `SetTokenDeployRepositoryRequest` (1, 2), `SetTokenDeployRepositoryResponse` (1). `change.proto`: `ChangeService.RetryDeployStatus` RPC, `Change.deploy_status = 26`, `DeployStatusState` 0 through 4, `DeployStatusTransition` 0 through 6 (`DISCARDED = 6`), `DeployStatusReason` 0 through 13, `DeployStatus` fields 1 through 15 (`reason = 13`, `token_repository = 14`, `action_url = 15`), `RetryDeployStatusRequest` / `RetryDeployStatusResponse`. `service.proto`: `ServiceDeployment.deploy_status = 8`. `gitprovider.proto`: `GitProviderService.RefreshGitHubApp` (`EFFECT_APPLY`), `GitProviderService.CheckGitLabConnection`, and `GitProviderService.ListGitLabProjects` RPCs, `ListGitProvidersResponse.gitlab_connections = 2`, `GitHubAppInfo.checks_permission_missing = 13`, `GitHubAppInfo.permissions_url = 14`, `GitHubInstallation.checks_permission_missing = 11`, `GitLabConnectionState` 0 through 5, `GitLabConnectionInfo` fields 1 through 10, `CheckGitLabConnectionRequest` fields 1 through 3, `CheckGitLabConnectionResponse` fields 1 through 5, `RefreshGitHubAppRequest` / `RefreshGitHubAppResponse`, `ListGitLabProjectsRequest` (1, 2), `ListGitLabProjectsResponse` (1, 2), `GitLabProject` (1 through 4), `GitLabProjectConnection` (1 through 4).

## Consequences

The panel and API can trace an external deployment to the exact source and artifact as soon as it is planned, and report rollout state back to GitHub pull requests and commits (Check Runs) and GitLab commits (Commit Statuses) through a durable outbox. One pipeline call can follow the ordinary health-gated rollout while Settings, Deployments, and Activity surface live delivery status, missing permissions, and one-click retry. See [Deploy from CI](../deploy-from-ci.md).
