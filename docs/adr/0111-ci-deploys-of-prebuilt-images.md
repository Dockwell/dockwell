# 0111. CI deploys of prebuilt images

- Status: Accepted (slice 2 built)
- Date: 2026-11-26

## Context

Dockwell can build from Git or deploy the image a pipeline has already pushed. The second path needs a receipt tied to the commit, a way for the pipeline to wait for rollout, and a token that does just that. A pipeline may retry a request whose response it lost, including while Dockwell restarts. See [ADR 0046](0046-builds-from-git.md), [ADR 0071](0071-api-tokens-narrowed-to-projects-and-a-role.md) and [ADR 0098](0098-connecting-github-as-an-app.md).

## Decision

### Correlation and rollout

- `DeployService` accepts a CI provider, repository URL, full commit SHA, Git ref and run URL. URLs are HTTPS without user information, query strings or fragments. These facts come from the pipeline and identify its reported source. Dockwell keeps each attempt's reported provenance in normalized columns keyed by change. The latest-attempt key can move independently of that history.
- The plan keeps the requested image reference and the immutable manifest digest. Accept an image by digest, or resolve its tag on a target server using the app's registry login and the existing image-read call. Store the pinned image in the proposed service spec. The rollout and rollback use the usual revision engine. The deployment record inherits provenance from the change that produced its revision.
- Migration 0061 adds a unique key on service ID, manifest digest and normalized commit SHA. The transaction that records the plan claims the key. A racing request returns the winning change and leaves no duplicate plan or event. A retry follows an applicable plan, an applying change, or a successful change whose pinned revision still owns the live deployments. A failed, discarded, stale or replaced attempt lets the transaction move the key to a new plan. An older commit can deliberately redeploy its digest and uses the same approval rules. A CI attempt can record a new revision for the same image to keep its own commit visible. Both CI tables advance the control backup position on SQLite and Postgres. A tag that moves to another digest is a different artifact.
- The API returns provenance for changes and service deployments. Deployments and Activity show the commit and CI run. GitHub and GitLab have known commit URL formats, and other providers supply a commit URL.
- `dockwell services deploy --wait` applies the plan and follows its terminal result. It prints a link to the change and leaves approval of protected or host-sensitive plans to someone in the panel. It retries transient proposal failures when it has correlation, and reconnects to dropped watches by reading the change again. The default deadline is 30 minutes. Failed, rolled back, awaiting approval at the deadline, timed out and discarded outcomes have distinct rollout exit codes.

### Tokens and shipped workflows

- The Deployments sheet uses `TokenService.CreateToken` and the existing passkey step-up. Deploy scope is a read-write credential bound to exactly one service, its existing environment and project, capped at developer. It allows planning a correlated deploy for that service and applying, reading and streaming that deploy's change. The issuer's current role and ordinary host and protected-environment rules still apply. The token name and target are audited using existing token events. Only the creation response carries the secret.
- The GitHub composite action is at `ci/github/action.yml`, addressed by the Dockwell release tag or commit. With a commit pin, pass a matching release tag to choose the CLI. The GitLab input template at `ci/gitlab/dockwell-deploy.yml` is includable from the same release tag and can move unchanged to a GitLab Catalog project. Both invoke the same script. GitLab downloads the release asset and verifies its checksum with a checksum-pinned Cosign before executing it. The script uses a pinned Cosign executable, the exact Dockwell tag's release-workflow certificate identity and issuer, and the signed SHA-256 of the Linux amd64 or arm64 full binary archive. The CI token is read from the runner's environment.
- No agent protocol change is required. Public fields are `DeployServiceRequest.deploy_origin` 6, `Change.deploy_origin` 25 and `ServiceDeployment.deploy_origin` 7. `DeployOrigin` uses fields 1 through 8. `DeployProvider` uses values 0 through 3. `TokenScope` adds value 3, `CreateTokenRequest.deploy_service` is 9, and `Token.deploy_service`, `Token.deploy_environment` and `Token.deploy_service_name` are 12, 13 and 14.

### Status in slice 2

- **Durable outbox (migration 0062).** `ci_status_outbox` records each status transition (`queued`, `applying`, `healthy`, `failed`, `rolled_back`) inside the same revision transaction as the change state transition, with a monotonic per-change `transition` number, provenance copied from `ci_deploy_origins`, the image digest, panel change URL (`/changes/<id>`), a per-transition `idempotency_key` (`dockwell:<change_id>:<transition>:<state>`), delivery state (`pending`, `delivered`, `skipped`, `failed`, `superseded`), provider `remote_id` and `remote_url`, `credential_ref` kept separate from `ci_deploy_origins`, `attempts`, `next_attempt_at`, `retry_since`, and `last_error`. Changes without a `ci_deploy_origins` row receive no outbox entries. `ci_status_outbox` is excluded from the control backup change-position triggers (like `alert_deliveries` and `alert_sends`) so retries do not churn backup schedules while snapshots still capture the table.
- **Worker ordering, no-regression, and bounded retries (`internal/control/cistatus`).** Delivery runs asynchronously outside the revision engine and its write lock. Per-change serialization delivers transitions in ascending `transition` order. Any pending transition older than `max(delivered transition)` is marked `superseded`; if an earlier transition is waiting in backoff while a newer transition is due, the stale earlier transition is superseded so a newer status is never blocked or regressed. Transient failures (network errors, HTTP 429, 5xx) retry with exponential backoff (5 s base, capped at 5 m, respecting `Retry-After`) and resume cleanly across control-plane restarts. After a bounded window (30 minutes or 12 attempts), delivery marks the entry `failed`, stores the one-line reason on the outbox row, and records `ci_status.failed` on the audit log and Activity. `ChangeService.RetryDeployStatus` requeues the latest transition with a fresh retry window.
- **GitHub Check Runs (`checks: write`).** Dockwell reports GitHub CI deploys as Check Runs named `"Dockwell / " + serviceName` rather than Commit Statuses or GitHub Deployments. One Check Run per change is created with `external_id = change_id` and updated in place (`PATCH /repos/:owner/:repo/check-runs/:id`) as the deploy moves through `queued`, `in_progress`, and `completed` (`success` or `failure`), carrying `details_url` pointing to `/changes/<id>`, a title, and a one-line summary. Retrying after a lost response looks up an existing check run by `external_id` before creating another. New GitHub App manifests request `checks: write`. Migration 0062 adds `permissions` JSON to `github_installations`; Settings -> Integrations flags missing Checks permission per App/installation with a direct link to GitHub's permissions page and a `Check again` action (`GitProviderService.RefreshGitHubApp`). When no installation reaches the repository or project, Dockwell records a one-line skip reason on the deploy row instead of retrying forever.
- **GitLab Commit Statuses (`gitlab.connection` resource kind).** Rather than overloading the app-linked infrastructure `connection` kind (ADR 0099, whose secrets are delivered to agents and probed from agent containers), slice 2 adds a dedicated organization-level `gitlab.connection` resource kind (`Spec.gitlab_connection = 131`, ID prefix `glc_`). Each connection holds a normalized HTTPS instance URL, an encrypted access token with `api` scope (never returned by the API and never reused across a changed URL), an optional group/project `path_prefix` (most specific match wins), and optional project reach. All outbound GitLab verification (`GitProviderService.CheckGitLabConnection`) and commit status calls (`POST /api/v4/projects/:id/statuses/:sha`) run from the control plane through `netguard` (blocking loopback, link-local, metadata, multicast, reserved addresses and redirects). Duplicate status retries that return GitLab's 400 "Cannot transition status" are verified idempotently against the commit's existing status.
- **Schema and proto numbers.** No agent protocol change is required. Migration `0062` (`0062_ci_status.sql`). `specs.proto`: `Spec.gitlab_connection = 131`, `GitLabConnection` fields 1 through 4. `change.proto`: `ChangeService.RetryDeployStatus` RPC, `Change.deploy_status = 26`, `DeployStatusState` 0 through 4, `DeployStatusTransition` 0 through 5, `DeployStatus` fields 1 through 12, `RetryDeployStatusRequest` / `RetryDeployStatusResponse`. `service.proto`: `ServiceDeployment.deploy_status = 8`. `gitprovider.proto`: `GitProviderService.RefreshGitHubApp` and `GitProviderService.CheckGitLabConnection` RPCs, `ListGitProvidersResponse.gitlab_connections = 2`, `GitHubAppInfo.checks_permission_missing = 13`, `GitHubAppInfo.permissions_url = 14`, `GitHubInstallation.checks_permission_missing = 11`, `GitLabConnectionState` 0 through 5, `GitLabConnectionInfo` fields 1 through 10, `CheckGitLabConnectionRequest` fields 1 through 3, `CheckGitLabConnectionResponse` fields 1 through 5, `RefreshGitHubAppRequest` / `RefreshGitHubAppResponse`.

## Consequences

The panel and API can trace an external deployment to the exact source and artifact as soon as it is planned, and report rollout state back to GitHub pull requests and commits (Check Runs) and GitLab commits (Commit Statuses) through a durable outbox. One pipeline call can follow the ordinary health-gated rollout while Settings, Deployments, and Activity surface live delivery status, missing permissions, and one-click retry. See [Deploy from CI](../deploy-from-ci.md).
