# 0054. The agent keeps its desired state, and puts back what goes missing

- Status: Accepted
- Date: 2026-11-07

## Context

PRD principle 5 says the control plane is optional at runtime: if it goes down, servers keep serving and reconcile to their last desired state. The PRD's non-functional table makes that a launch gate, and [ADR 0007](0007-one-binary-two-roles.md) promised it: agents cache their desired state and reconcile locally. Issue #32 asks for it, done when restarting an agent with the control plane down restores every workload, crashed containers are restarted locally, and the cache is integrity-checked and encrypted where it holds secrets. `dockwell local` (#33) and the control plane's backup (#34) build on it.

What holds today, and what doesn't:

- **Docker already keeps most of it running.** A container's restart policy is `unless-stopped` unless its spec says otherwise, so Docker restarts one that crashes, and starts it again after a reboot. The ingress keeps its last config and starts with it, and puts back a copy a power cut damaged.
- **Nothing puts back what Docker can't.** A container that's gone, removed by hand, by `docker system prune` (which takes stopped ones), or with Docker's data, comes back only when the control plane applies it again. Neither does one Docker tried to start and couldn't, as after a reboot where a disk mounted late, or a network that's gone. With the control plane away, nothing on the server knows what should be there.
- **The agent hears every step, and keeps none.** `agent.Desired` is told the spec of each step the agent applies and verifies, and nothing sets it yet.
- **A step's values reach the agent for that step alone.** The values of the variables and secrets a spec uses travel sealed to a key the agent keeps for one stream, and are cleared when the step ends ([ADR 0022](0022-secrets-encrypted-at-rest.md)). A container made again needs them. Docker keeps them, in the clear, in the container's own configuration on the server's disk, stopped containers included, which the [threat model](../security/secrets.md) counts as root's to read; once the container is gone, so is that copy.
- **The firewall leans on this.** ADR 0052, in #288, has the agent record a spec as what it should hold only once it's confirmed, so its cache of desired state never re-applies rules that were rolled back, and puts the last confirmed table back as it reconciles.

## Decision

### What the agent keeps, and where

- **One record for each resource it runs:** the spec the last step applied and verified on this server, the revision and change that step ran toward, the values of the variables and secrets the spec uses, at the revisions it pins, the name of its scope, which its containers are named after ([ADR 0035](0035-containers-named-after-their-environment.md)), and for a service or a container the image it runs, by its ID, and by its digest where it came from a registry. A volume's record keeps no options, which can hold a share's password: a volume is never made again alone (below), so nothing needs them.
- **In the agent's data folder,** `<data>/agent/desired/`, one file for each resource, named by a hash of its kind, scope and name. The folder is `0700` and each file `0600`, owned by the agent's user. A file is written as the ingress writes its config: to a temporary file, synced, renamed over the old one, and the folder synced, so a power cut leaves the old record or the new one. What a power cut leaves of a write is removed as the cache opens.
- **Each record is sealed whole,** with AES-256-GCM under the cache's key, `<data>/agent/desired.key`: 32 random bytes made on first use, `0600`, never sent anywhere and never in a backup Dockwell takes. The additional data is the format's version, the server's ID and the resource's kind, scope and name. So a record reads only with the key, only for that resource on that server, and one that was edited, torn or copied from another server doesn't open. The key is written beside its place and linked into it, which fails if another start made one first, so two starts on one folder settle on one key. A key others can read is made the agent's alone again, and the log says so.
- **That is the integrity check.** The agent opens every record as it starts. One that doesn't open, or is of a format this agent doesn't know, as after going back to an older agent, is moved to `desired/damaged/`, logged, counted in the hello, and never acted on. A record it can't read now, as for a disk error, isn't damage: the cache doesn't open, and the agent says why and runs without one. A lost key leaves every record unreadable, which reads as an empty cache: the agent makes a new key, and the control plane fills it again (below).
- **The cache has an ID,** derived from its key, so it changes when the key does and says nothing of it. The hello carries it, so the control plane can tell when a server's cache isn't the one it last saw.
- **Why the values are kept.** Without them nothing that uses a secret, which is most of what has a database, can be made again while the control plane is away. Each record holds only the values of what runs on its server now, which [ADR 0022](0022-secrets-encrypted-at-rest.md) already trusts that server's agent with, and Docker keeps the same values in the clear beside it. So this changes ADR 0022's "the agent writes none" to: the agent writes them sealed, in this cache, and nowhere else. They leave it as what holds them does: a step that rotates a value rewrites the record, a deletion leaves a tombstone with no value, a step whose record can't be written takes the older record with it, and what the server no longer runs is forgotten as the agent next connects.
- **What it costs, said plainly.** The key sits on the same disk, so sealing hides nothing from root, who reads the values through Docker anyway, and it changes two things in practice:
  - **A copy of the agent's data folder now opens anywhere.** A VM snapshot, a disk image or a by-hand copy of `/var/lib/dockwell`, the folder people copy to move a server, carries the key beside the records. Sealing helps only a copy of `agent/desired/` alone. Before this, that folder held no values, and Docker's copy sits under `/var/lib/docker`, which file backups often leave out.
  - **The fill on connect widens what a stolen agent identity gets.** The same copy holds the agent's mTLS key and its certificate, good for 30 days. An agent that connects with them, and says it keeps nothing, is sent every live resource on that server with its values, at once, sealed to its own stream (below). Before, it got only the values of steps that ran while it was connected. So each fill that carries values goes on the server's timeline, and says when the cache isn't the one the control plane last saw, with how to replace the identity.
  - An older copy of a record from this server also opens: a record is bound to its server and resource, not its revision, so root can put an older one back. A step or a fill writes it again.

Holding the key in a TPM or the kernel's keyring can come later without changing the records, and is what moving secrets into files on tmpfs will want.

### When a record is written

- **A step that passed always writes.** A record is written once a step has applied on this server and passed, verified. A step under the firewall's timer writes none: it can't say whether it will be confirmed, and the access manager keeps what was (ADR 0052). That is where `agent.Desired` hears of it. A plan writes none, nor a step that failed, nor one still running. A step says what runs, so it's kept whatever revision the cache held: a control plane whose store went back, restored from a snapshot or rebuilt (#34), numbers lower, and what runs still wins. A restart, a restore or a backup acts on a resource as it is, and writes its record again at the revision it had.
- **A deletion leaves a tombstone,** sealed like a record, with the deletion's revision and nothing else. Nothing reads it, and no hello lists it. It holds back what the control plane sends of the resource (below) at or below its revision, so a fill that read what ran before the deletion can't bring the record back, password and all. A step can, and a fill above it can. A tombstone goes after 7 days, far longer than any fill, whose calls each end within a minute.
- **A step whose record can't be written,** as for a full disk or a folder made read-only, takes the older record with it, as that no longer says what runs. If that can't be removed either, nothing reads it and no hello lists it. The step still passes, and its result says it wasn't kept (`ApplyResult.unkept`), so the control plane counts it as lacking and sends it as the agent next connects.

### The control plane fills what's lacking, and forgets what's gone

- **The hello says what the agent holds:** each resource with its revision, how many records didn't open, which can't say what they were, and the cache's ID.
- **As an agent connects, the control plane fills it.** For each resource whose latest revision is live on this server, and which the agent doesn't hold at that revision, it sends it (`RememberCall`), its values sealed to the stream as a step's are, through the same check the keeper makes for a step: only the latest revision placed on that server, and only what it pins. A volume's options aren't sent. It sends nothing for a resource the agent holds a later revision of, as of a step that ended after its stream did: resuming that change decides, as it does now. A fill is held to the revision the agent keeps, and to a tombstone's.
- **It forgets what the server no longer runs.** For each resource the agent holds that isn't placed on that server at all, as after a delete step that failed partway, a move to another server, or a server's last change that never ran there, it has the agent forget it, if it still holds it at the revision the control plane saw: a step since then has the say. What a change applying now placed there, live or not, is left to that change.
- **It keeps what its store doesn't know.** The store never deletes a resource, nor goes back on a revision, so a resource the agent holds that the store has no record of, or only at an earlier revision than the agent's, can only follow a store restored from a snapshot or rebuilt (#34). What the agent keeps of it may then be the only copy of later values, beside Docker's, and what runs wins: it's left as it is, never forgotten for it. How many there are goes on the server's timeline (`server.desired_unknown`), in a warning's tone, when that count changes, with how to bring the store up to date: apply them again from the control plane.
- **None of it changes the server,** so it's no change and no revision. One fill of a server runs at a time, and what the stream knows the agent holds follows each step, fill and forget, so a fill that runs again on the same stream sends nothing twice. Each spec is opened only as it's sent.
- **A fill that carries values goes on the server's timeline** (`server.desired_sent`), with how many resources it sent and how many came with values. The first cache the control plane sees for a server, as when its agent is updated to one that keeps a cache, is said plainly. One that isn't the cache it last saw, as after a reinstall, a lost data folder, or another holder of the server's identity, says so in a warning's tone, and says to remove the server and join it again if neither of the first two happened. The cache's ID stays in the store.

### On its own, while the control plane is away (slice 2)

- **The control plane leads while a stream is up.** As soon as a stream ends, and every 60 s while there's none, the agent looks at what each record says should run and notes how it stands. Once it has had no stream for 60 s, from its start or from the last one ending, it also acts on what it sees. It polls rather than reading Docker's event stream, which it doesn't otherwise read: a look is one call for each record, once a minute, and only while away. When a stream opens, what it is doing then finishes, and nothing new starts, but for a pull, which stops, as stopping it destroys nothing.
- **It notes how each container stands while a stream is up too,** from the list of the server's containers the health monitor reads every few seconds anyway: whether it runs, and the volumes Docker made for the paths its image declares. A step or a fill says what should run, not how it stands, so neither changes what was noted, but for a step that started the container (made it, made it again, or restarted it). A look taken before a step or a fill ended, or of a resource with a step under way, is old news, and is left.
- **Why a container is down is something it knows, never a guess from its being down.** Docker's state can't say: a container someone stopped and one Docker stopped as it came back from being killed both read exited, exit 0, no error, on a real engine (Docker 28.0.4, in the Chaos on Docker job; [the chaos tests](../testing/chaos.md) keep what it printed). What Docker says happened can, so once a container the agent has a record of has stood stopped for two of the monitor's lists, the agent asks Docker once for the events it still holds, and settles it one of three ways, in its sealed record:
  - **Stopped,** when someone stopped it: `docker stop`, `docker kill` and `docker compose stop` each leave `kill` after the container's `start`. One that ended by itself, which leaves `die` alone, where its restart policy leaves it, is kept the same way: a job that finished isn't run again.
  - **Lost,** when Docker stopped it as it came back from being killed. Without `live-restore`, containers outlive a killed engine, and the engine that returns stops each of them, saying `kill`, `stop` and `die` as of a person's stop, and counts them stopped by hand, so only those whose policy is `always` come back. But it remembers no event from before, and no container runs under it that it didn't start, so that stop has no `start` before it. That holds only while Docker still holds everything since it started: it keeps its last 256 events, of every kind, so the agent counts a stop with no start as Docker's own only when Docker holds well under that. With `live-restore`, what ran keeps running through a restart, so there a stop with no start before it is someone's.
  - **Unsure,** when Docker can't say: its events no longer reach back to the container's start, or it holds nothing of the container at all, as for one already down when Docker last started. Nobody may have stopped it, or somebody may. The agent doesn't start it, and says on Activity, once, that it's down, why it wasn't started, and to start it from the control plane if it should run.
  - **Two lists, not one,** as `docker rm -f` kills a container on its way to removing it, and a single look between the two would take that for a stop. One that's only made, or being removed, hasn't stopped. One Docker tried to start and couldn't has an error in its state, isn't a stop, and is read in full once.
  - **When the agent itself was down** while it happened, it asks the same question as it starts, of the same events: a stop someone made while it was down is known as long as Docker still holds it; what Docker stopped as it came back is started; and when Docker restarted after someone's stop, taking what said so with it, the agent is unsure, and leaves it and says so. It never starts what it can't place.
  - A container that runs again, whoever started it, is noted as running, and what was settled is forgotten. Docker not answering settles nothing, and the next list asks again. This reads Docker's events on demand and closes: nothing stays open, and nothing is held between.
- **What that rule makes of the other ways a container reads stopped with nobody having stopped it:**
  - **A server shutting down.** Docker stops each container while it still answers, and says of each what it says of a person's stop, after the container's start. Two lists in that time take it for someone's stop, which is wrong. It doesn't last: the agent starts nothing for a stop, Docker doesn't count a container it stopped while shutting down as stopped by hand, so it starts it again at boot, and the first list that sees it running forgets the mark, with nothing on Activity. It would stick only for a container that's gone by then, which then isn't made again. Docker's events can't tell this from a person's stop, so the rule doesn't try.
  - **`docker restart` by hand.** A stop and a start in one. Lists that land between them, as a slow stop allows, take it for a stop, and the next one, with it running, forgets that. Right in the end, and nothing is started or said meanwhile.
  - **A container made and never started outside a step,** as `docker create` by hand leaves one. It hasn't stopped, so the rule says nothing of it, and the agent neither starts it nor writes anything down. A creation of the agent's own that was interrupted is finished by its receipt, as before.
  - **A container Docker is removing, or gave up on removing.** No news, as above.
  - **Two containers answering to one service,** as a twin made by hand does. The service runs if either does: a list's stopped twin doesn't have the one that runs taken for stopped, whichever comes last. With neither running, the one the list has last is the one settled, and the agent makes no twin of its own.
  - **A step that changes a container in place, and a fill.** Neither says how it stands, so what was settled outlasts them, lost and unsure as stopped does, until a step starts the container or a list sees it run. One that's lost is still started.
  - **A container Docker couldn't start, which someone then stops.** Whether Docker leaves its error in the state then, which would have the agent take it for one to start, isn't known: the evidence script asks a real engine, and the answer goes here.
- **It knows a silent connection for lost.** A network that drops every packet closes nothing, and TCP would take a quarter of an hour to say so. The agent's connection asks with an HTTP/2 ping after 15 s of hearing nothing, and takes the connection for lost if 15 s more bring no answer, so it's away, and acts, as the control plane closes a stream silent for 30 s.
- **It takes each resource's mark as a step does.** Reconciling a resource holds the mark `unfinished` keeps for a step under way, so a plan or an apply from a control plane that comes back meanwhile is told to wait, and nothing races. Before changing Docker it durably reserves a journal ID and time. If that write fails, it waits for room in its data folder. Completion uses that same receipt, and a newly made container carries the ID in `dev.dockwell.reconcile`. After a kill, the agent can account for its completed creation even while connected, or finish the first start of its own container that Docker has never started. A container that exited or was stopped is left alone. A different container is left alone and the interrupted action is reported as waiting. An interrupted network creation is reported as waiting when the network exists, as it has no container marker to prove who made it.
- **It asks each resource's driver for a plan, and takes only what destroys nothing.** It goes in the order a plan does: networks, volumes, then services and containers, then routes. For each record it plans as a step would, without asking anything to run:
  - **Made again:** a service's or a container's container that's gone, from its record, with its values. It's made with the spec's own image reference, so it reads back with no drift. If that reference now names another image on the server than the record's, as after a pull by hand, the agent tags the record's image with it first, and the journal says the tag moved back. If the record's image is gone, it's pulled by its digest, then tagged. It's never pulled by a tag, which may have moved. A record with no image ID, as a fill for a container that's gone writes, takes the tag only if the image it names has the record's digest, and otherwise pulls by the digest. With neither the ID nor the digest, it waits, and says so.
  - **On the volumes its image kept data in.** A database's image declares a volume (postgres, mysql, redis, mongo), and a spec that mounts nothing at that path keeps its data in one Docker made for it. Made again, the container mounts those volumes by name at their paths, as a replace from the control plane carries them over, so it starts on its data. If one is gone, or its image declares a path the agent never saw a volume at, it waits, and says why: made again, it would start empty. Where an image keeps data is read from the image, so the agent has the image its record names in place first, moving a tag back or pulling by digest, and reads that one. An image that isn't there, that Docker can't read, or whose paths the record has no volume for, holds the container back with the reason: a fill of an agent that kept nothing, for a database since removed and pruned with its image, has no volumes in its record, and waits.
  - **Not as a twin.** If another container mounts one of its volumes, as one that replaced it by hand under another name would, it waits: two databases on one data folder don't see each other's lock.
  - **Not made again when it's stopped, or the agent is unsure.** The driver makes a container and starts it in one, so one that was stopped and then went, as `docker system prune`, which removes only stopped containers, does, waits for the control plane, and the journal says so. So does one the agent couldn't tell wasn't stopped. What someone stopped and pruned between two of the health monitor's lists, a few seconds, reads as running. A container Docker is removing, or gave up on removing (`removing`, `dead`), is no news either way: `docker rm -f` kills a container on its way out, and a look that found it so would otherwise take it for stopped, and never make it again. That Docker shows it so is from its source: on a real engine (28.0.4), the list said running and then nothing, 20 to 30 times a round in five rounds, and never `removing` or `exited`, so this guards a moment that wasn't caught there. **Which container stands for a service,** when more than one answers to it, as what a rollout left behind when it failed or was cut short does, or a twin made by hand: never one that's leaving, which beside a live one would hide it and a stop of it; then one that runs before one that doesn't, as the service runs if any of its containers does; then the highest number, as a rollout that starts the new one first numbers it one on, so a service deployed more than once has no number 1; then the greater ID, which means nothing but is the same to everyone. The monitor's list and the agent's own read of a container choose by this one rule, so they can't disagree. A step reads the driver's own order instead, which finishes a rollout that was cut short. A container with no number label, or one that isn't a number, counts as number 0, as one Dockwell didn't make does: it stands only where nothing numbered does, and where two have one number the greater ID does. **When Docker's error is news.** Docker leaves an error in the state of a container it tried to start and couldn't, and the agent starts such a one while the control plane is away. That error is news of the service only when the container stands alone, with no other of the service's that isn't leaving, and its record covers it. Beside another container the error is as likely the leftover's as the service's, and a stop of the other is what happened: nothing is started, and the service is noted as stopped. So with more than one container answering to a service, the agent starts none of them: which one is the service is the control plane's to say. **What a record covers.** A container that was taken on, as the 1Panel importer and Adopt take them: Dockwell didn't make it and it carries no revision, and its record was made of it as it stood. A container made for a revision no later than the record's: a record is only ever of a revision that was applied and passed, so a later one is of a deploy that never did, and an earlier one is the record's own, as a fill, or a step that left the container as it was, moves the record on without making it again. And a container that says no revision, as every one made by a release from before that label does (v0.1.0 and v0.2.0) until a step replaces it, when its image is the record's own, by the image's ID, or by the digest a fill gave the record. Never one made from another image than the record's, whatever it says: a restart, or a pull that found a newer image, makes its container for the revision the record already has, and that image never passed here. **One that stands alone and isn't covered is left down, and isn't noted as stopped,** as nobody stopped it: the agent doesn't start what its record doesn't describe, and Activity says once, while the control plane is away, that Docker couldn't start it, that the agent left it down and why, and to start it from the control plane or apply it again. If it later goes, it's made again from its record. What a failed start-first rollout leaves, its new container made and not started beside the old one, is there only until the control plane's rollback removes it, which it resumes as the server reconnects ([#424](https://github.com/Dockwell/dockwell/issues/424) has when it doesn't).
  - **Started:** a container Docker tried to start and couldn't, which Docker leaves with an error in its state (`State.Error`), when its policy says it should run. That error is the only reliable sign across a reboot: an exit code says nothing of who stopped it, and Docker's restart count goes back to nothing with the daemon, so an `on-failure` policy's count can't be read after one. So the agent tries at most 10 times for each container after each boot, or each start of the agent, after 10 s and then twice as long each time, up to 5 min, and then stops and says so. A container whose start fails at boot has no other way to stay down. Docker restarts what crashes, and the agent doesn't race it.
  - **Started, with the control plane there too:** a container that's lost, as above. Nobody asked for that stop, Docker won't undo it, and the control plane starts nothing by itself, so a killed engine would otherwise leave every app whose policy isn't `always` down until someone noticed. The agent starts it as soon as it's settled, takes the resource's mark as a step does, tries as often as for a start Docker couldn't make, and writes it down for Activity, which gets it on the stream that's up. It's the one thing the agent does on its own while a stream is up, and it only ever starts a container that's there: it makes nothing, and changes nothing.
  - **A network, only once Docker's behaviour is known.** A container attached to a network that's gone keeps the old network's ID, and, as Docker is understood to behave, doesn't start until it's reconnected or replaced, which the agent may do neither of. Slice 2 proves what Docker does in the Docker job first. Until then the agent makes a missing network again only when none of its containers names the old one, and otherwise waits, and says why.
  - **Put back:** config that holds no data. The ingress already starts with its last config. The firewall puts back its last confirmed table, as ADR 0052 has it, which holds only if the firewall driver's step returns once the change's verdict is in, never before: otherwise its record isn't "confirmed". #288 holds its driver to that.
- **What each kind gets.** The agent keeps a record of every kind it applies, so a fill and a forget cover them all, and acts alone on four:
  - **Networks, volumes, services and containers** are looked at as above. A volume is only ever waited for.
  - **Routes** are left to the ingress, which starts with its last config and reconciles it itself.
  - **Scheduled tasks** are left to the agent's own `tasks.json`, which runs them on the server's clock whether or not a stream is up ([ADR 0053](0053-scheduled-tasks.md)). Their records are a second copy that nothing acts on.
  - **Database users** are left alone. A user lives in its database's data, so it comes back with the volume, and making one again means running SQL with a password, which is a change and not a repair. Its record holds the password's value, sealed as any record's values are.
  - **Alert rules and channels, backup policies and destinations, projects, environments, variables and secrets** run on no server, so no agent is sent them and none keeps a record of them. Alerts are judged by the control plane, so none fire while it's away.
  - **Files, terminals, uploads and downloads, processes and server updates** aren't managed state: they have no spec and no revision, so there is nothing to keep or put back. A terminal or a transfer ends with its stream.
  - **Firewall rules and the firewall's policy** are left to the access manager ([ADR 0052](0052-a-servers-firewall-ssh-and-fail2ban.md)), which keeps the last confirmed table and loads it again as the agent starts, before it connects anywhere. A step under the firewall's timer can't say whether it will be confirmed, so it writes no record here: the agent keeps none of either kind, and a fill sends it none. Reading the firewall, as the Firewall tab does, is no managed state.
  - A kind new to the agent is added to `reconciledKinds` or `leftAlone` in `internal/agent/reconcile.go`, with its reason; a test fails until it is.
- **What it never does alone:**
  - Remove, replace or change in place anything. A container that differs from its record stays as it is: that is drift, which the control plane shows when it returns, and #33 adds adopting or reverting it.
  - Make a volume again. An empty one would hide that the data is gone, and Docker would make one for a container that mounts it, so a missing volume, and every container that mounts it, waits, and says why.
  - Start a container someone stopped, one it can't tell wasn't stopped by someone, or one whose policy says it stays stopped: `no`, or `on-failure` that ran out while the agent watched.
  - Finish, undo or roll back a change. Each resource stays at the last revision a step applied and verified, even when that leaves a change half done, and the control plane resumes it when it returns, as it does now.
  - Touch a resource with a step still running, or one whose record didn't open.
  - Anything while a stream is up, but start what Docker stopped as it came back from being killed.
  - Hold a resource longer than its deadlines: a minute for each look at Docker, 10 minutes for a pull, and 5 for making it again. A control plane turned away meanwhile is told how long, and to check Docker and restart the agent if it goes on.
- **A server removed from the fleet stops.** Its agent, still running, would otherwise reconcile forever. The control plane refuses its connection with a reason of its own (`server_removed`, under the key the API's reasons travel under), and the agent then stops reconciling, and removes its records and key. A server the control plane doesn't know isn't told that: that can be a control plane rebuilt from nothing, and then the agent's records are what puts its server back.
- **A delete step that fails drops the record,** as one whose record can't be written does: what's left is the control plane's to finish, not the agent's to make again.
- **A record that can't go is cut short.** One that no longer says what runs, in a folder that won't let it be removed, is cut to nothing, which needs only the file's own write permission, so it doesn't open after a restart either.
- **A fill names the image too.** A fill for a container that's gone, as after a reinstall, finds no image on the server, so `RememberCall` carries the deployment's digest, which the control plane keeps, for the record to pull.

### Where the agent can still be wrong

How a container stands is read from its being down, with no error, in one of the agent's looks. Each way that reading can be wrong is here, with what you'd see. #378 replaces the reading with what Docker says happened, and closes those marked so. "Run" names a Chaos on Docker run whose log shows what Docker did.

**It starts, or makes again, what a person stopped.** This is the direction it must never go, and these remain. [#417](https://github.com/Dockwell/dockwell/issues/417) asks whether the first two can be closed.

- **Stopped, and gone before a list saw it stopped.** Someone stops a container, and it's removed, as `docker system prune` does, before the health monitor's next list: a few seconds. Its record still says it runs, so once the control plane is away the agent makes it again and starts it. You'd see the app you stopped running again, and on Activity that the server made it again while the control plane was away.
- **`docker stop` of a container Docker couldn't start.** Docker records nothing of that stop: the error stays in the container's state, no event is said, and it isn't counted stopped by hand (run 42770589216). The agent takes it for one Docker couldn't start, and starts it while the control plane is away. You'd see it running, and on Activity that the server started it. To keep one down, remove it, or change it from the control plane.
- **Stopped, and removed, while the agent itself wasn't running.** The same as the first, without the few seconds' limit: the agent has no look from that time, and its record says the container ran. Once the control plane is away, it's made again and started.
- **A job that finished, and was pruned before a list saw it finished.** It reads as gone, not as ended, so it's made again, and runs again.
- **The server's clock set back.** A look older than a record's last keeping is left as old news, so with the clock behind that time, stops aren't noted until it has passed. One stopped and removed meanwhile is made again.
- **A container made by hand with a service's labels, that runs.** It stands for the service, so a stop of the real one isn't noted while it does. Nothing is made while either is there. If both are later removed while the control plane is away, the service is made again and started. Activity says nothing of the twin: the agent can't tell it from one of its own.

**It leaves down, or doesn't make again, what nobody stopped.** The safe direction: something is down that needn't be, and the control plane's drift says so when it's back.

- **Docker killed, with no `live-restore`.** The engine that returns stops every container that outlived it, and leaves those whose policy isn't `always` down, reading exactly as a person's stop does (run 42762502373). The agent takes them for stopped, and leaves them; one that then goes isn't made again, and Activity says "It was stopped, and is gone". #378 closes this: it starts what Docker stopped as it came back.
- **A server shutting down, and `docker restart` by hand.** Read as a stop for a moment, and forgotten at the first look that sees the container run. Nothing is said. It sticks only for a container gone by then, which waits with "It was stopped, and is gone".
- **A kill on its way to a removal,** as `docker rm -f` makes. A look that caught the container killed and not yet gone would take it for stopped. A container Docker shows as `removing` or `dead` is no news, but a real engine's list showed running and then nothing (run 42770589216), so a look that reads it exited in that moment isn't ruled out. #378 closes this by settling a stop only after two lists.
- **A container made and never started, alone,** as `docker create` by hand leaves one. It reads as stopped, so if it goes it isn't made again. #378 closes this.

**Closed by when Docker's error is news, and what a record covers:** what a failed rollout left that Docker couldn't start, beside a container a person then stopped, which the agent would have started, at a revision that never passed; a twin made by hand that Docker couldn't start; a container of a later revision than the record's standing alone; and one of the record's revision but another image, as a pull that never passed leaves, once the old container is removed.

**Closed by which container stands for a service:** a service deployed more than once, whose container isn't number 1, which before was never looked at, so a stop of it by a person wasn't noted (found by run 42770589216); a dead or half-removed leftover numbered above the live one; a leftover that's only made, or stopped, beside one that runs; and two with one number.


### Handing back

- **It writes down what it did,** in `<data>/agent/desired/journal`: each entry the resource, what it did (made it again, started it, or waits, and why), and when, never a value or a spec. A wait that goes on is written down once, until it changes, and not again each time the control plane goes away and comes back, as the journal remembers the last wait the control plane heard of each resource. A Docker that doesn't answer is one wait for the whole server, not one for each resource. Each entry has an ID, the boot's ID and a sequence, so it means one thing however often it's sent. It keeps at most 500 entries, the oldest going first, and counts what it dropped.
- When a stream opens, the agent sends its journal, and how many entries it dropped (`ConnectRequest.reconciled`). The control plane makes what it says fit to show, as an agent that was taken over could say anything: one printable line of reason, short names, and a time neither ahead of now nor more than 30 days back. It puts each entry on Activity and the server's timeline (`server.reconciled_made`, `_started`, `_waiting`, and `_dropped` for the count), by the server as actor, once: an entry's event is named by the server, the entry's ID and the time the agent sent, never the time it's shown at, which depends on when it's heard; and the count by the newest entry dropped (`Reconciled.dropped_to`), so one sent again is kept once. Once it has them, it says the last it has (`ConnectResponse.heard`), and the agent drops the entries up to it. What it can't keep is sent again on the next stream.
- Then the control plane fills the cache, as above. Its drift check shows what the agent left as it was.

### What it costs

- **Memory:** an index of the records, each its resource and revision, about 160 bytes: a test opens 1,000 records with 8 KiB of spec and values each, and the index holds 158 KiB. A record's spec and values are read only as reconciling needs that record, and dropped, the values cleared as a step's are. While connected, nothing runs beyond writing a record after a step, and noting from the health monitor's list what changed, which reads a record only when how it stands changed. While away, one goroutine with a timer, and a look at each record's resource each minute. `make budgets` goes on measuring the idle agent against the 40 MB budget ([ADR 0018](0018-keep-the-budgets-in-rss.md)).
- **Disk:** a record is its spec and values, a few KiB, and a value is at most 64 KiB. A tombstone is a few dozen bytes, for 7 days.
- **Numbers:** the agent protocol's fields for this are in 160 to 169: the hello's `desired` is 160, `Call.remember` and `CallResult.remember` 161, `ApplyResult.unkept` 162, `ConnectRequest.reconciled` 163 and `ConnectResponse.heard` 164. The timeline's are in event fields 140 to 149: `Event.desired_sent` is 140, and `Event.reconciled` 141.

## Consequences

- Workloads come back with no control plane, from what their server held, those that use secrets included, and a server says what it did once the control plane is back.
- The values of what runs on a server are on its disk twice: Docker's copy in the clear, and the cache's, sealed under a key beside it. A copy of the agent's data folder is as good as the server's secrets, and a stolen agent identity gets every value its server runs on connect, which the timeline shows. Moving secrets into files on tmpfs, as the threat model plans, has to take the cache's copy with it, and wants the key off the disk.
- A server can stay halfway through a change for as long as the control plane is away. That is what was verified there, and the control plane takes it from there.
- A volume that's gone stops what mounts it until someone acts, where making it again would have run on empty data.
- `dockwell local` (#33) reads the cache for status, and keeps the revisions before for its rollback, under the same rules. A lost control plane's state can be rebuilt from what agents hold (#34), and a step that runs after such a rebuild writes what runs, whatever revision the cache held.
- It comes in three slices: the cache, written after each step, filled and pruned by the control plane; reconciling while away, and handing back; and the proof in the Docker job, with the control server stopped, a container removed and one that can't start, the agent restarted, everything back, and Activity saying so when the control server returns.
