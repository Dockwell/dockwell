# 0054. The agent keeps its desired state, and puts back what goes missing

- Status: Accepted
- Date: 2026-11-07

## Context

PRD principle 5 says the control plane is optional at runtime: if it goes down, servers keep serving and reconcile to their last desired state. The PRD's non-functional table makes that a launch gate, and [ADR 0007](0007-one-binary-two-roles.md) promised it: agents cache their desired state and reconcile locally. Issue #32 asks for it, done when restarting an agent with the control plane down restores every workload, crashed containers are restarted locally, and the cache is integrity-checked and encrypted where it holds secrets. `dockwell local` (#33) and the control plane's backup (#34) build on it.

What holds today, and what doesn't:

- **Docker already keeps most of it running.** A container's restart policy is `unless-stopped` unless its spec says otherwise, so Docker restarts one that crashes, and starts it again after a reboot. The ingress keeps its last config and starts with it, and puts back a copy a power cut damaged.
- **Nothing puts back what Docker can't.** A container that's gone, removed by hand, by `docker system prune` (which takes stopped ones), or with Docker's data, comes back only when the control plane applies it again. Neither does one Docker tried to start and couldn't, as after a reboot where a disk mounted late, or a network that's gone. With the control plane away, nothing on the server knows what should be there.
- **The agent hears every step, and keeps none.** `agent.Desired` is told the spec of each step the agent applies and verifies, and nothing sets it yet.
- **A step's values reach the agent for that step alone.** The values of the variables and secrets a spec uses travel sealed to a key the agent keeps for one stream, and are cleared when the step ends ([ADR 0022](0022-secrets-encrypted-at-rest.md)). A container made again needs them. Docker keeps them, in the clear, in the container's own configuration on the server's disk, stopped containers included, which the [threat model](../security/secrets.md) counts as root's to read; once the container is gone, so is that copy.
- **The firewall leans on this.** ADR 0052, in #288, has the agent record a spec as what it should hold only once it's confirmed, so its cache of desired state never re-applies rules that were rolled back, and puts the last confirmed table back as it reconciles.

## Decision

### What the agent keeps, and where

- **One record for each resource it runs:** the spec the last step applied and verified on this server, the revision and change that step ran toward, the values of the variables and secrets the spec uses, at the revisions it pins, the name of its scope, which its containers are named after ([ADR 0035](0035-containers-named-after-their-environment.md)), and for a service or a container the image it runs, by its ID, and by its digest where it came from a registry. A volume's record keeps no options, which can hold a share's password: a volume is never made again alone (below), so nothing needs them.
- **In the agent's data folder,** `<data>/agent/desired/`, one file for each resource, named by a hash of its kind, scope and name. The folder is `0700` and each file `0600`, owned by the agent's user. A file is written as the ingress writes its config: to a temporary file, synced, renamed over the old one, and the folder synced, so a power cut leaves the old record or the new one. What a power cut leaves of a write is removed as the cache opens.
- **Each record is sealed whole,** with AES-256-GCM under the cache's key, `<data>/agent/desired.key`: 32 random bytes made on first use, `0600`, never sent anywhere and never in a backup Dockwell takes. The additional data is the format's version, the server's ID and the resource's kind, scope and name. So a record reads only with the key, only for that resource on that server, and one that was edited, torn or copied from another server doesn't open. The key is written beside its place and linked into it, which fails if another start made one first, so two starts on one folder settle on one key. A key others can read is made the agent's alone again, and the log says so.
- **That is the integrity check.** The agent opens every record as it starts. One that doesn't open, or is of a format this agent doesn't know, as after going back to an older agent, is moved to `desired/damaged/`, logged, counted in the hello, and never acted on. A record it can't read now, as for a disk error, isn't damage: the cache doesn't open, and the agent says why and runs without one. A lost key leaves every record unreadable, which reads as an empty cache: the agent makes a new key, and the control plane fills it again (below).
- **The cache has an ID,** derived from its key, so it changes when the key does and says nothing of it. The hello carries it, so the control plane can tell when a server's cache isn't the one it last saw.
- **Why the values are kept.** Without them nothing that uses a secret, which is most of what has a database, can be made again while the control plane is away. Each record holds only the values of what runs on its server now, which [ADR 0022](0022-secrets-encrypted-at-rest.md) already trusts that server's agent with, and Docker keeps the same values in the clear beside it. So this changes ADR 0022's "the agent writes none" to: the agent writes them sealed, in this cache, and nowhere else. They leave it as what holds them does: a step that rotates a value rewrites the record, a deletion leaves a tombstone with no value, a step whose record can't be written takes the older record with it, and what the server no longer runs is forgotten as the agent next connects.
- **What it costs, said plainly.** The key sits on the same disk, so sealing hides nothing from root, who reads the values through Docker anyway, and it changes two things in practice:
  - **A copy of the agent's data folder now opens anywhere.** A VM snapshot, a disk image or a by-hand copy of `/var/lib/dockwell`, the folder people copy to move a server, carries the key beside the records. Sealing helps only a copy of `agent/desired/` alone. Before this, that folder held no values, and Docker's copy sits under `/var/lib/docker`, which file backups often leave out.
  - **The fill on connect widens what a stolen agent identity gets.** The same copy holds the agent's mTLS key and its certificate, good for 30 days. An agent that connects with them, and says it keeps nothing, is sent every live resource on that server with its values, at once, sealed to its own stream (below). Before, it got only the values of steps that ran while it was connected. So each fill that carries values goes on the server's timeline, and says when the cache isn't the one the control plane last saw, with how to replace the identity.
  - An older copy of a record from this server also opens: a record is bound to its server and resource, not its revision, so root can put an older one back. A step or a fill writes it again.

Holding the key in a TPM or the kernel's keyring can come later without changing the records, and is what moving secrets into files on tmpfs will want.

### When a record is written

- **A step that passed always writes.** A record is written once a step has applied on this server and passed: verified, and for the firewall, confirmed (ADR 0052). That is where `agent.Desired` hears of it. A plan writes none, nor a step that failed, nor one still running. A step says what runs, so it's kept whatever revision the cache held: a control plane whose store went back, restored from a snapshot or rebuilt (#34), numbers lower, and what runs still wins. A restart, a restore or a backup acts on a resource as it is, and writes its record again at the revision it had.
- **A deletion leaves a tombstone,** sealed like a record, with the deletion's revision and nothing else. Nothing reads it, and no hello lists it. It holds back what the control plane sends of the resource (below) at or below its revision, so a fill that read what ran before the deletion can't bring the record back, password and all. A step can, and a fill above it can. A tombstone goes after 7 days, far longer than any fill, whose calls each end within a minute.
- **A step whose record can't be written,** as for a full disk or a folder made read-only, takes the older record with it, as that no longer says what runs. If that can't be removed either, nothing reads it and no hello lists it. The step still passes, and its result says it wasn't kept (`ApplyResult.unkept`), so the control plane counts it as lacking and sends it as the agent next connects.

### The control plane fills what's lacking, and forgets what's gone

- **The hello says what the agent holds:** each resource with its revision, how many records didn't open, which can't say what they were, and the cache's ID.
- **As an agent connects, the control plane fills it.** For each resource whose latest revision is live on this server, and which the agent doesn't hold at that revision, it sends it (`RememberCall`), its values sealed to the stream as a step's are, through the same check the keeper makes for a step: only the latest revision placed on that server, and only what it pins. A volume's options aren't sent. It sends nothing for a resource the agent holds a later revision of, as of a step that ended after its stream did: resuming that change decides, as it does now. A fill is held to the revision the agent keeps, and to a tombstone's.
- **It forgets what the server no longer runs.** For each resource the agent holds that isn't placed on that server at all, as after a delete step that failed partway, a move to another server, or a server's last change that never ran there, it has the agent forget it, if it still holds it at the revision the control plane saw: a step since then has the say. What a change applying now placed there, live or not, is left to that change.
- **It keeps what its store doesn't know.** The store never deletes a resource, nor goes back on a revision, so a resource the agent holds that the store has no record of, or only at an earlier revision than the agent's, can only follow a store restored from a snapshot or rebuilt (#34). What the agent keeps of it may then be the only copy of later values, beside Docker's, and what runs wins: it's left as it is, never forgotten for it. How many there are goes on the server's timeline (`server.desired_unknown`), in a warning's tone, when that count changes, with how to bring the store up to date: apply them again from the control plane.
- **None of it changes the server,** so it's no change and no revision. One fill of a server runs at a time, and what the stream knows the agent holds follows each step, fill and forget, so a fill that runs again on the same stream sends nothing twice. Each spec is opened only as it's sent.
- **A fill that carries values goes on the server's timeline** (`server.desired_sent`), with how many resources it sent and how many came with values. The first cache the control plane sees for a server, as when its agent is updated to one that keeps a cache, is said plainly. One that isn't the cache it last saw, as after a reinstall, a lost data folder, or another holder of the server's identity, says so in a warning's tone, and says to remove the server and join it again if neither of the first two happened. The cache's ID stays in the store.

### On its own, while the control plane is away (slice 2)

- **The control plane leads while a stream is up.** Once the agent has had no stream for 60 s, from its start or from the last one ending, it reconciles from its records: then every 60 s, and as Docker reports one of its containers dying or going, until a stream opens. What it is doing then finishes, and nothing new starts.
- **It takes each resource's mark as a step does.** Reconciling a resource holds the mark `unfinished` keeps for a step under way, so a plan or an apply from a control plane that comes back meanwhile is told to wait, and nothing races. It writes the journal entry once the action ends.
- **It asks each resource's driver for a plan, and takes only what destroys nothing.** It goes in the order a plan does: networks, volumes, then services and containers, then routes. For each record it plans as a step would, without asking anything to run:
  - **Made again:** a service's or a container's container that's gone, from its record, with its values. It's made with the spec's own image reference, so it reads back with no drift. If that reference now names another image on the server than the record's, as after a pull by hand, the agent tags the record's image with it first, and the journal says the tag moved back. If the record's image is gone, it's pulled by its digest, then tagged. It's never pulled by a tag, which may have moved. With neither, it waits, and says so.
  - **Made again created, not started,** when the agent last saw the container stopped by someone. It notes that from Docker's events, which it already reads: a stop or a kill it didn't do itself, which leaves no error, marks the record "stopped", and a start marks it running again. That covers `docker system prune`, which removes only stopped containers.
  - **Started:** a container Docker tried to start and couldn't, which Docker leaves with an error in its state (`State.Error`), when its policy says it should run. That error is the only reliable sign across a reboot: an exit code says nothing of who stopped it, and Docker's restart count goes back to nothing with the daemon, so an `on-failure` policy's count can't be read after one. So the agent tries at most 10 times for each container after each boot, after 10 s and then twice as long each time, up to 5 min, and then stops and says so. A container whose start fails at boot has no other way to stay down. Docker restarts what crashes, and the agent doesn't race it.
  - **A network, only once Docker's behaviour is known.** A container attached to a network that's gone keeps the old network's ID, and, as Docker is understood to behave, doesn't start until it's reconnected or replaced, which the agent may do neither of. Slice 2 proves what Docker does in the Docker job first. Until then the agent makes a missing network again only when none of its containers names the old one, and otherwise waits, and says why.
  - **Put back:** config that holds no data. The ingress already starts with its last config. The firewall puts back its last confirmed table, as ADR 0052 has it, which holds only if the firewall driver's step returns once the change's verdict is in, never before: otherwise its record isn't "confirmed". #288 holds its driver to that.
- **What it never does alone:**
  - Remove, replace or change in place anything. A container that differs from its record stays as it is: that is drift, which the control plane shows when it returns, and #33 adds adopting or reverting it.
  - Make a volume again. An empty one would hide that the data is gone, and Docker would make one for a container that mounts it, so a missing volume, and every container that mounts it, waits, and says why.
  - Start a container someone stopped, or one whose policy says it stays stopped: `no`, or `on-failure` that ran out while the agent watched.
  - Finish, undo or roll back a change. Each resource stays at the last revision a step applied and verified, even when that leaves a change half done, and the control plane resumes it when it returns, as it does now.
  - Touch a resource with a step still running, or one whose record didn't open.
  - Anything while a stream is up.
- **A server removed from the fleet stops.** Its agent, still running, would otherwise reconcile forever. The control plane refuses its connection with a reason of its own, and the agent then stops reconciling, and removes its records and key.
- **A fill names the image too.** A fill for a container that's gone, as after a reinstall, finds no image on the server, so `RememberCall` carries the deployment's digest, which the control plane keeps, for the record to pull.

### Handing back

- **It writes down what it did,** in `<data>/agent/desired/journal`: each entry the resource, what it did or why it couldn't, and when, never a value or a spec. Each entry has an ID, the boot's ID and a sequence, so it means one thing however often it's sent. It keeps at most 500 entries, the oldest going first, and counts what it dropped.
- When a stream opens, the agent sends its journal, and how many entries it dropped. The control plane puts each entry on Activity and the server's timeline, once, by server and entry ID, as something the server did while the control plane was away, and answers with the highest ID it has. The agent drops the entries up to it.
- Then the control plane fills the cache, as above. Its drift check shows what the agent left as it was.

### What it costs

- **Memory:** an index of the records, each its resource and revision, about 160 bytes: a test opens 1,000 records with 8 KiB of spec and values each, and the index holds 158 KiB. A record's spec and values are read only as reconciling needs that record, and dropped, the values cleared as a step's are. While connected, nothing runs beyond writing a record after a step. While away, one goroutine with a timer, and the Docker event stream the agent already reads. `make budgets` goes on measuring the idle agent against the 40 MB budget ([ADR 0018](0018-keep-the-budgets-in-rss.md)).
- **Disk:** a record is its spec and values, a few KiB, and a value is at most 64 KiB. A tombstone is a few dozen bytes, for 7 days.
- **Numbers:** the agent protocol's fields for this are in 160 to 169: the hello's `desired` is 160, `Call.remember` and `CallResult.remember` 161, and `ApplyResult.unkept` 162; slice 2 goes on from 163. The timeline's are in event fields 140 to 149: `Event.desired_sent` is 140.

## Consequences

- Workloads come back with no control plane, from what their server held, those that use secrets included, and a server says what it did once the control plane is back.
- The values of what runs on a server are on its disk twice: Docker's copy in the clear, and the cache's, sealed under a key beside it. A copy of the agent's data folder is as good as the server's secrets, and a stolen agent identity gets every value its server runs on connect, which the timeline shows. Moving secrets into files on tmpfs, as the threat model plans, has to take the cache's copy with it, and wants the key off the disk.
- A server can stay halfway through a change for as long as the control plane is away. That is what was verified there, and the control plane takes it from there.
- A volume that's gone stops what mounts it until someone acts, where making it again would have run on empty data.
- `dockwell local` (#33) reads the cache for status, and keeps the revisions before for its rollback, under the same rules. A lost control plane's state can be rebuilt from what agents hold (#34), and a step that runs after such a rebuild writes what runs, whatever revision the cache held.
- It comes in three slices: the cache, written after each step, filled and pruned by the control plane; reconciling while away, and handing back; and the proof in the Docker job, with the control server stopped, a container removed and one that can't start, the agent restarted, everything back, and Activity saying so when the control server returns.
