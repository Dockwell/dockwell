# 0022. Variables and secrets, encrypted at rest and referenced by services

- Status: Accepted
- Date: 2026-11-04

## Context

The PRD asks for "encrypted secrets per environment, referenced not copied" at launch, and its security rows say secrets are "envelope-encrypted at rest; never written to logs or plans". Its Connections section adds three rules that apply to every secret, not only a connection's:
- **Injection.** Values reach containers at start, never in Compose files, image layers or logs. A server receives only the secrets of apps placed on it, and the agent decrypts them in memory.
- **Rotation is a plan.** Editing a value opens a plan listing every app and environment that will restart.
- **Bind is not read.** Binding a secret doesn't let you see it. Revealing a value needs a passkey and lands in the audit log, and API tokens can't read values.

What was there:
- [ADR 0009](0009-resources-revisions-and-plans.md) marks fields that may hold secrets `(sensitive)`, and plans say such a field changed but never show it.
- [ADR 0017](0017-the-change-api-and-the-agent-stream.md) noted the gap this record closes: revision rows, and the change items that ask for them, held specs in the clear, a container's environment included.
- `internal/seal` seals the CA's key and authenticator secrets under the install's key, a file beside the database.
- [ADR 0011](0011-claim-and-sign-in.md) gave people passkeys and sessions, and [ADR 0016](0016-scoped-api-tokens.md) kept tokens away from destructive and sign-in methods.
- The agent's cache of desired state (#32) was to plug in at `agent.Desired`. [ADR 0054](0054-the-agent-keeps-its-desired-state.md) built it.
- [ADR 0021](0021-the-docker-driver.md) runs services on Docker, and left this record what it calls plain values and secret references: a volume's options are sensitive, an export names what may be secret, and `environment()` in the container runtime is where a spec's environment becomes Docker's.

Issue #29 asks for all of it: the specs, encryption at rest, delivery, revealing, the panel's screen and the CLI.

## Decision

### Two kinds, in an environment

- **`variable`** holds a value that isn't secret, such as `LOG_LEVEL=info`. Plans, history and the panel show it.
- **`secret`** holds one that is, in a field marked `(sensitive)`.
- Both live in an environment and have revisions and plans like any kind. They run on no server themselves: each is a `resource.Valuer`, whose value goes to the servers of the services that use it.
- Their names are what a process's environment takes, such as `DATABASE_URL`. A variable and a secret can't share a name in one environment, as the panel shows them as one list.
- A value is at most 64 KiB and has no zero byte, which no environment can hold. A secret can't be empty, which is almost always an empty file read by mistake.

### Services use them by reference

- A service's spec names the variables and secrets it uses, each under the name the service sees: `secrets: {DATABASE_PASSWORD: DB_PASSWORD}` gives the service the secret `DB_PASSWORD` as `DATABASE_PASSWORD`. An empty name means the same name.
- **Each use is pinned to a revision.** When a change is planned, the revision store writes the revision each use resolves to into the service's spec, in `revisions`, a field Dockwell sets and an edit can't (`google.api.field_behavior = OUTPUT_ONLY`). So a service's spec says exactly which value it runs with, and a new value makes a new spec.
- **Rotation is a plan.** A change to a variable or secret takes in every service that uses it, with its uses pinned again. Each gets a revision of its own, and its agent plans the restart. The plan lists the value as changed, without it, and every service and server that restarts, with downtime. Undo and rollback put the old revision back, and the services with it.
- **A change applies only while its pins hold.** Applying checks again that each pin is still the latest revision, and that no service started using a changed value since the change was planned. Otherwise the plan is out of date, as for a base revision that moved.
- A service can use only what its environment has, and nothing it uses can be deleted while it does, unless the same change stops using it.
- **Making a variable a secret, or a secret a variable,** is one change that deletes the one and makes the other under the same name. A plan where a name changes between a variable and a secret, in either direction, masks the value on both sides, as it may have been a secret all along, in Activity and to every reader of the change. That covers undoing a switch, and a rollback of one, which put the variable back. A delete in one change and a create in a later one can't be linked, so the first is the plan of a plain variable, which shows its value. The panel doesn't carry a variable's value over to the secret it becomes: it asks for a new one, and says why. It takes in every service that uses the value, with its use moved to the new kind under the same names (`resource.Rebinder`), so the switch is one plan, with a restart for each. A service the change edits itself keeps what the edit says, and is refused if it still uses what the change deletes. The panel proposes the two edits; so can REST, and `dockwell changes propose`, with the secret's edit read from a file with `--edits @file`.
- **What each revision uses is kept in the clear beside it,** in `revision_uses`: the name it sees each value as, the value's kind and name, and the revision it is pinned to, never a value. Finding the services that use a value, as every proposal and commit does, and listing an environment's values with their services, read it and open no spec. A change opens only the specs of the services it pins again, and of the volumes they mount, to say what they reach. The check that a service's volumes and networks stay there opens a stored service only when the change touches a volume or a network (`resource.Referrer`).
- The plan of a rotation reads like any other: the secret's `value` is changed and sensitive, and each service's step shows `revisions[DATABASE_PASSWORD]: 3 → 4`.
- **Setting a secret's value is a rotation, whatever it is.** An edit that sets the value of a sealed kind that holds values, which today means a `secret`, always plans as a change: a new revision, and a restart of the services that use it. That is where the panel, `dockwell secrets update` and the API take a new value. It counts as changed, and is never compared with the one there (`resource.DiffRotating`). Otherwise proposing a value would say whether it is the one there: a read-write token, or a stolen cookie with no passkey, would get no change for the right guess and one for a wrong one. Dockwell keeps the value, so deploys refer to secrets by name and never send one again; setting one is always deliberate, so closing this costs nothing.
  - The change item records it (`change_items.rotates`), so applying plans it again the same way.
  - An undo and a rollback rotate a secret too, so neither says whether the change they put back set the value it had. What a change takes in, such as the services that use a value, doesn't rotate, nor does keeping or reverting drift.
  - An edit that sends no value doesn't rotate. A secret has nothing else to edit today: its only field is `value`, and an edit without one is refused.
  - For a secret, nothing else in a plan depends on whether its value is the one there: its counts, actions, steps, downtime and wording are the same, and so is the work proposing does, as no value is compared.
- **A workload's own sensitive fields compare as usual.** A container's inline `env` is compared like any field: an equal value is no change, and one that differs is a change that stays masked. Edits carry whole specs, so rotating it would make every apply restart: re-importing an unchanged Compose file would restart every service with an environment, and deploying a new image of `web` would restart `db` for its `POSTGRES_PASSWORD`. Applying the same thing twice must change nothing, which deploys depend on. Use secrets for anything secret: that is what keeps a value out of workloads' specs and lets it rotate on its own.
- **A volume's password never compares.** A workload can't read a volume's options, so what excuses a container's `env` doesn't hold here: comparing a password would let a read-write token confirm a guess at it, as the right one planned nothing and a wrong one was refused as a change. So an edit of a volume that exists goes through `resource.Keeper`, before anything compares it:
  - An edit that gives the volume as it is but for a password, by the names `volume.HoldsPassword` reads, gets the password the volume was made with, whatever it gave. It plans the same for a right guess and a wrong one, and a plan says so (`kept_password`).
  - An edit that gives a password and differs in anything else, its driver included, is refused in the same words, whatever the password is and wherever it places the volume. Moving a volume makes it anew on another server, so keeping the password there would take it to the address the edit names, and planning the edit's own password would let the paths a plan says changed tell a guess.
  - An edit that gives no options keeps them, as an export leaves them out (`kept_options`).
  - **What a volume keeps goes only to the servers that have it.** A plan sends a spec to the agent of every server it would run on, before anyone applies it, so keeping a password on an edit that adds a server would hand it to that server's agent on a proposal alone. That breaks the rule that an agent is trusted with the secrets of what runs on it and nothing else, and a person's approval comes too late to stop it. So an edit that keeps anything and adds a server is refused, in the same words whatever it gave, before any plan call goes out. Sending the plan without the password isn't enough: applying it would still have to give the new server the stored password, for a plan nobody could read it in. To run such a volume on another server, make one of another name there, giving its options, which are then the caller's own.
  - An edit that gives options of its own and no password keeps nothing. They compare as usual: where the volume is, they are refused as any change is, and on a move the volume is made anew with what the edit gave, so nothing stored goes with it. So a volume's password doesn't change or move by an edit: that takes a volume of another name.
  - Adopting drift takes what a server has, which no caller said, so it keeps nothing. Someone who remakes a volume by hand with a new password can adopt it. A plan would send that to every server the volume is on, so each is asked what it has first, which sends it nothing. If one has something else, the adopt is refused before any plan call goes out, so its agent never hears a password made by hand. An offline server can't be asked, so that's refused too. One removed from the fleet isn't asked, as nothing runs there any more.
  - **An undo keeps nothing either, and goes only where a revision ran.** An undo, and the rollback of a change that failed, put back the revision a change replaced, on the servers that revision ran on. No caller said any of it, so `resource.Keeper` isn't asked (`Edit.Reverses`). Asking it would refuse the undo of a move, as the volume there has options of its own, and take a server that had the volume all along for a new one. The password stays where it was, by induction over how a revision comes to be: an edit that keeps anything can't add a server, an edit that keeps nothing has no stored password in it, an adopt stays on the servers it's on, and a reversal sends a revision's spec only to that revision's servers. So every server a stored password can reach is one that revision was placed on. An undo is open for 7 days, as long as a server keeps a volume it let go of, so that server still has it unless someone removed it by hand. That's checked as an undo is proposed and again as it applies, before anything is sent, so one left planned can't outlast it. It compares no guess, as neither side is what a caller wrote: a password in an edit never reaches a revision of a volume that exists. So undoing an adopt is refused, as Docker can't change a volume, where keeping what's there would plan nothing and read as undone. A rollback doesn't come into this, as `RollBackTo` serves services alone.
- **Write access to a scope can read its values through a workload.** A read-write token, or a stolen session, can deploy a container that uses any secret its scope can attach, and have it send the value out. So the boundary is that the API never returns a secret's value without a step-up, not that a token can't learn one. The rotation rule closes the API's equality oracle for secrets, as that is cheap and a plan is quiet. An oracle on a workload's own fields doesn't move the boundary, as a token can read those values through a workload anyway, so inline `env` isn't covered. Applying a guess is a write too: it is on the timeline, and restarts what uses the value.
  - **`keep_env` lowers that bar, and doesn't move it** (#234). An edit can keep a service's own values without reading them (`Edit.keep_env`) while it changes what runs, so a command of `env` piped to a server elsewhere reads them out with no image of anyone's own, where before it took one pushed somewhere a pull reaches. The same write could deploy such an image, so the boundary is where it was, and the edit is a change on the timeline like any other. What it keeps goes only where it has been, as a volume's password does (`checkKept`): an edit that keeps a value and adds a server is refused, and setting the value again in the edit is how to run it there. It also needs the revision it read (`base_revision`), so what it keeps and what it read come from the same spec.

### A command, an entrypoint and a health check name values too

A Compose file can put a value in what runs, as `command: redis-server --requirepass ${REDIS_PASSWORD}` does. That used to land as text in `app.command`, so it was in the plan, the `changes` table, `GetChange` and `ExportCompose`, where a read-only token reads it. By variable name, 10 files from 7 apps in 1Panel's public store do this (#96).

- **By name, and not by masking.** Hiding those fields on a service whose values came this way would have been smaller, but an approver has to be able to read a command, on a change from a token most of all. So the field keeps showing, and what it shows is the name.
- **A field names what the container's environment has.** `Container.references` lists which of `command`, `entrypoint` and `healthcheck.test` name values. In one of those, `${NAME}` is the value of `NAME` in the container's own `env`, or of what its service uses under that name, and `$$` is a `$` of its own, as in a Compose file and as Kubernetes has it for `$(NAME)`. A field can name only what its container has a value for, which `Validate` checks, on a service with what it uses too. So there is no second home for a value. All of it is already true of the environment: it is sealed, a plan masks it, an equal value is no change and a new one is a change that stays masked. A secret or a variable a service uses keeps its pin, so a rotation reaches it and the keeper's rules hold: a server gets a value only as it runs what uses it. What a check prints is masked by the same values (`health.SpecEnv`), from 6 characters, as for any value in an environment.
- **A `$` in any other field is a `$`, as it always was.** So a revision from before this means what it did, a field with no name in it plans exactly what it did, and `$$` round-trips through an export and an import. A list in `references` says which fields read so, rather than a mark on a word, so a field reads one way throughout, with the same rule a file has.
  - **A plan says when that is likely a slip.** A spec written by hand with `${PW}` in its command, and no `references`, runs Redis with the password `${PW}`, which anyone who reads the plan knows. So where a field not listed holds `${NAME}` for a name the container or its service has a value for, the plan says so, and how to name the value (`named_as_text`), and the CLI adds the flag, `--app-references command`. It refuses nothing, so older specs mean what they did. A shell's script, the word `sh -c` reads past its options, as in `bash -o pipefail -c` or a `CMD` test that runs a shell, or a `CMD-SHELL` test, reads `${NAME}` from the environment itself, which is right, so that says nothing. The words after a script are its `$0`, `$1` and so on, which the shell passes on as they are, so `entrypoint: [sh, -c, 'exec "$@"', --]` with `${PW}` in the command is noted.
- **The value goes in only as the container is made.** The runtime writes the values in as it asks Docker for a container, and nowhere else (`rendered`). The spec a step holds keeps its names, so its labels and its config hash are of the names, and neither says anything of a value: a hash of the text would let anyone who can read a container's labels check a guess at a short password offline. An entrypoint that comes to `""` is sent as none, as a spec's entrypoint of `""` and Compose's `entrypoint: ""` are, and reads back the same.
- **Reading a container back goes by a label, never by the text.** Docker has what the fields came to, and `dockwell.uses` can't hold words, and doesn't name a value of a container's own. So `dev.dockwell.references` holds the fields as the spec has them, which is names and never a value. `Project` works them out again from that container's own environment, and if they come to what Docker has, reads the field back as its names. So what an agent reports, and so what a plan and drift compare, is names on both sides, with no false drift, and nothing proposed is ever compared with what a value comes to: a literal guess at a command plans the same change whether it is right or wrong. A field that doesn't come to what Docker has, as when `docker compose up` ran an export with no value in its shell, reads as a fixed sentence (`binding.Unread`), as it may hold anything: it shows as drift, and can't be kept as a spec, as it names nothing. A label that can't be read does the same for all three fields.
- **What Docker says of a command is masked where it answers.** Docker quotes what it couldn't run, as in `exec: "…": executable file not found`, so a value in a command's first word would reach a plan's error, the timeline and the log. The container's values are masked out of Docker's answer before anything wraps it (`hideIn`). A value of 6 characters or more goes wherever it is, and a shorter one where it stands alone, as a value that short would otherwise take digits out of a number.
- **An import turns what variables give those fields into this.** A variable from an `.env` or the request lands in such a field as its name, however the file writes it, `${P}`, `$P`, `${P:-x}`, `${P:?why}` or `${Q:+--requirepass "${P}"}`, and its value goes in the container's `env`. A default that is used is the file's own words, so it stays text, and a variable with nothing in it writes nothing, as before. A field a file wrote with no variable landing in it is as it was.
- **A value that isn't secret goes the same way.** `--port=${PORT}` plans as `--port=${PORT}`, and a change of `PORT` is a change that says so and masks it. The only other ways to tell a port from a password are by a variable's name or by its shape, and each is a guess that shows a password when it is wrong, and each flips with the value, so the same file would plan differently from one value to the next. A person reads the name and can follow that rule. Whoever wants the number in the plan writes it in the file, or makes it a variable of the environment, which every reader can see, and uses that.
- **In a command written as one string, a value of several words is text, and only that value.** Compose splits such a line into words once its variables are in, and 5 files from 4 apps in 1Panel's store write a whole command line as `command: ${START_COMMAND}`. One name can't stand for several words. Dockwell splits the line with its names in, and works out what those words come to. If that isn't what Compose makes of the line, it writes into the line, as text, each value with a space, a quote, a backslash or another character Compose reads as part of a line, splits again, and keeps every other name, as long as the words then come to just what Compose makes of it. So a password beside an address of several words, as npc's line has, keeps its name, and only the address is text. The plan warns of each value that is text, by variable and field and never by value, with how to keep it hidden: write it as a list, with each word its own variable, where a value stays one word.
  - That also covers a value with a backslash Compose would take out, or a `;` Compose stops reading at, which are text as Compose reads them.
  - Where the words still don't come to what Compose makes, the whole line keeps the file's meaning as text, and the warning for each name says that another value on the line made it so. That takes an odd line, such as one where a value ending in `$` meets the line's own `(`, which Compose then reads as a command's, and no file in 1Panel's store comes near one.
  - A list, and a health check, which a shell splits, don't have any of this. A line Compose can't read with the value in it, as with a lone quote, has nothing to hold to, so the value stays one word.
- **One name has one value.** A file can write `environment: {P: a}` beside `${P}` from a variable worth `b`. Compose would run with both. A container's `env` holds one, so that is refused, and says which name, and never either value. No file in 1Panel's store does it.
- **A name in a command is also in the container's environment.** That is what the first rule costs: `command: run --key ${KEY}` runs with `KEY` set too, where `docker compose` wouldn't set it. The plan shows it as a masked `env[KEY]`, and an export has it as `KEY: null`, so `docker compose up` from the export sets it too. A name an image reads means what the file meant by it. A variable named as something an image and what runs in it need, `PATH`, `HOME`, `HOSTNAME` or `LD_*`, would replace that, as a typo or an `.env` meant for a shell can do, so an import that would add one that way is refused, by name, with how to fix it. A file that sets one in `environment` itself means it, so that stands. No file in 1Panel's store names one.
- **A guess at a secret gets nothing.** A file names a secret by the label an export writes, and in those fields it needs no value there. A file, an `.env` or a request that gives it one is refused as set twice, in the same words whatever the value is, and nothing compares it with the secret's. A form doesn't ask for it. A value in a variable of the same name with no label is the file's own, and nothing connects it to the secret. A value that is a container's own compares as any `env` does, which is what lets importing a file again plan nothing, so someone who can propose can confirm a guess at it, as the rule above has it for inline `env`: they can read it through a workload anyway. A secret is the place for what that matters to.
- **An export writes `${NAME}`,** whatever it names, and says so in the file's comment. A `docker compose` reads that from its shell or an `.env` beside the file, not from `environment`, so `omitted` lists it, a variable a service uses included, whose value is in the file. Importing it asks for a container's own value in `variables`, where a value that matches plans no change, and needs nothing for what a service uses.
- **An agent that can't write them in gets none, and reads none.** One from before this would run `${NAME}` as the words it is, so a Redis with a password anyone who reads the plan knows. So an agent says it can (`Hello.writes_references`), and the control plane refuses to plan or apply such a spec on one that doesn't, and says to update it.
  - **It reads none either.** Such an agent reads a container's command as Docker has it, value and all, whatever spec it is asked about. So when a server goes back to an older agent, as `install.sh --version` or a mirror serving an older release as the latest can do, its reports would carry the value into drift, which a read-only token reads and `AdoptDrift` keeps, and into any plan there, even one whose spec names nothing, such as an undo.
  - So the stream asks the keeper which of what it reads, plans or applies on such an agent names values (`Keeper.NamingValues`), and refuses those, at every entry: reading back, planning and applying. "Names values" means in the latest revision, or in any revision that server was given, as what a server runs can be older than the latest. That holds the server to more than it may run now, but updating the agent is the way out of either. `control.New` gives the streams the keeper to ask, and with none to ask, such an agent is refused all of it, so a control plane built without one fails closed.
  - Drift reports the server as unchecked, `agent_outdated`, with how to fix it, and the control plane logs a warning when such an agent connects. A plan of what never named a value goes on as ever.
  - **A control server that goes back has none of this,** as the check is the control plane's, and one from before it would open the database and read its own agent's commands with the values in. So migration 19 changes nothing but the schema version, and no dockwell from before it opens a database one from after has used. Going back on a control server means restoring the database from before the upgrade.
  - **The install script doesn't go back on its own.** It refuses a release older than the one installed, the latest from a mirror included, or one over a build whose version it can't read, such as `devel`, and says what that costs on that server, unless it is run with `--downgrade`. With no binary installed there's nothing to compare, and an uninstall keeps the data, so it doesn't refuse a reinstall: there the database and the check above hold.
- **What stays as it was, and isn't this record's to change.**
  - Root on a server reads a command through `docker inspect` or `/proc`, as it reads a container's environment. See the [threat model](../security/secrets.md).
  - A plan from before this holds what it held, as nothing rewrites a plan. A value that went through one should be rotated.
  - An app that prints its own command line has printed the value, to a log that may be kept. Reading a log takes a grant of its own, and nothing there is redacted ([ADR 0025](0025-logs-per-deploy.md)).
  - A container someone made by hand on a server, without the label, reads as what it says. Nothing there came from Dockwell's values.
  - A value under 6 characters isn't masked in what a check prints, as for any value in an environment ([ADR 0027](0027-health-checks-rollouts-and-rollback.md)).
- **What 1Panel's store comes to** (`TestAppStore`). Of its 341 files that read with a value for every variable, a plan warned on 30, with 10 warnings about a credential, by its name or its app's form. It now warns on 2, and neither of a credential. 28 files keep a value by name, and every one of the 10 files from 7 apps that #96 counted has no value left in its plan.

### Keys at rest

```
the install's key           <data>/control/key, 0600, never in the database
 └ key-encryption key       a row of key_encryption_keys, sealed with the install's key
    └ data key              a row of data_keys, wrapped under the key-encryption key
       └ spec               a revision's or change item's spec, sealed under its data key
```

- **What is sealed.** Every stored spec of a kind whose message has a `(sensitive)` field, at any depth: secrets, services and containers, whose environment may hold one, and volumes, whose options hold a CIFS password. The gap ADR 0017 noted is closed for every such kind, not only for secrets. Variables, networks, projects, environments and firewall rules stay in the clear, as they hold nothing secret.
- **A data key for each stored spec, bound to where it is stored.** Proposing a change seals each such item under a new data key, and applying it seals the revision under another. Each is AES-256-GCM with a random nonce. Its associated data names the resource's ID and kind, and the revision's number, or the change's ID and the item's position (`store.SpecAt`). So a sealed spec copied anywhere else doesn't open: into another resource's row, into another revision of the same resource, such as a leaked value passed off as its rotation, or into another change's item. A revision is sealed for the number it is about to get, the next after its base, which the commit has just checked is the latest; the store refuses to write it under any other.
- **The key-encryption key** is random, 256 bits, and kept sealed with the install's key, under a purpose that names it (`internal/seal`). Data keys are AES-256-GCM under it, bound to their own ID and the key-encryption key's.
- A stored spec says whether it is sealed: it starts with a zero byte, which no protobuf encoding does. A spec of a kind that may hold secrets must be sealed: one stored in the clear is refused when it is read, so someone who can write the database, without the key file, can't put a spec of their own where a sealed one belongs. A spec of any other kind is stored as it is.
- **Fingerprints don't give a secret away.** A plan's fingerprint hashed each item's spec, and a backup holds the fingerprint, so a guess at a short password could be checked against it. A sealed kind's spec is digested with HMAC-SHA256 under a key derived from the install's key (`seal.Key.Derive`), over the change's ID and the spec. So a fingerprint is useless without the key file, and it is the change's own: applying reproduces it, and no two changes' fingerprints match because they set one value, such as a guess beside an undo that puts an old value back. The same edits against the same state still give the same plan, and the same fingerprint when they set nothing sealed. Which kinds are sealed is said once, by `resource.Sealed`.
- **A change records how its fingerprint was made** (`changes.fingerprint_scheme`): 1 for every spec hashed as it is, 2 for the keyed digests bound to the change, with whether each item rotates. A change planned before the upgrade has 1, and is checked the way it was fingerprinted, so it applies while its plan is the one reviewed. When it isn't, it says an earlier version planned it, and to propose it again, rather than that the servers changed. An item it holds for a kind that may hold secrets, such as a container planned for a server that was offline, was stored in the clear, so it is refused: the change says an earlier version planned it, and to propose it again.
- **Plans mask by the schema.** An agent's steps say which field changes are sensitive; the control plane masks every change whose path the schema marks sensitive, whatever the agent says, before a plan is kept. It reads a path as `resource.Diff` writes it: field names, a list's index, and a map's key in brackets, which may hold dots, as a label such as `traefik.enable` does. A path that names a whole message, or a whole map or list of them, is sensitive when anything within it is: a change at a service's `app` would carry its container's environment.
- **Revisions stay immutable.** Rotating the key-encryption key wraps every data key again, in their own table, and changes no revision.

### Rotating the key-encryption key

`dockwell rotate-key`, on the control server, as the user that runs dockwell:
1. makes a new key-encryption key;
2. wraps every data key under it;
3. retires the old one, emptying its sealed copy;

all in one transaction, which the audit log records as `secrets.rotate_key`. The control plane can keep running: it reads the active key in each transaction that seals, and finds each data key's own key when it opens one. It keeps no key-encryption key in memory beyond the transaction that unsealed it, which costs a small read and an AES-GCM open, so once `rotate-key` retires one beside it, the running control plane holds it nowhere, and needs no restart. Rotating the install's key itself, the root, means sealing again the key-encryption keys, the CA's key and the authenticator secrets; that has no command yet.

### What a database backup alone reveals

Nothing of a value that was only ever a secret. It holds:
- sealed specs, data keys wrapped under a sealed key-encryption key, and keyed fingerprints;
- plans that say a secret changed, and never what it is;
- audit events that name which secret was revealed, by whom and when, never the value.

A value that was a plain variable before it was made a secret is the exception: the variable's revisions keep it in the clear, as every variable's are, so a backup holds it. The plan of the switch doesn't show it, as below, and the panel says, as you make a variable a secret, that the old value stays in the variable's history: enter a new value, and rotate the old one wherever it was issued.

The install's key is a separate file, and a backup of the database without it opens none of this. With the key file, it all opens: back them up apart. `TestADatabaseDumpHoldsNoSecret` makes secrets, a service that uses them and a container with a secret in its environment, rotates, undoes, discards, reveals and leaves a change planned. It then reads every row of every table, on SQLite and Postgres, and finds none of the values: as they are, in hex, or in base64.

### Delivery

- **Only to the servers a service runs on.** When the engine applies a step that runs a service, the agent stream asks the keeper for the values its spec uses (`resource.Values`). The keeper refuses unless the service's latest revision is placed on that server and is the spec being applied. It then reads each value at the revision the spec pins. A deletion carries none, and planning and observing carry none.
- **Sealed to one stream.** Each agent stream makes an X25519 key pair, keeps the private key in memory, and sends the public key in its hello (`delivery_key`). The values for a step travel in the `ApplyCall` sealed to it with HPKE (RFC 9180: DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, AES-256-GCM, Go's `crypto/hpke`). The info binds them to the server and the resource. So values never appear in the clear in a message, even within mTLS. They can't be opened for another resource or server, nor once the stream ends, as the key that opens them is gone.
- **A call sent again is sealed again.** A step the agent refuses as it moves to a renewed certificate goes to its next stream (ADR 0017). The values are read once, and sealed to the delivery key of each stream the call goes out on.
- **An agent that sends no delivery key** can't run a service that uses a variable or secret, and the step says to update it.
- **Where the code is, for the two builds** ([ADR 0023](0023-a-full-build-and-an-agent-build.md)). The agent build links `internal/delivery`: the stream's key pair, the suite and info, and opening. With the service driver it links `internal/resource/binding`, which builds a container's environment and label, and `internal/resource/variable`, which names the kinds and checks the names a service uses. Sealing the values for a stream (`secrets.SealValues`), and everything at rest, the key chain, the store, step-ups and the CLI's `rotate-key`, are the full build's alone. These add no package to the agent build beyond themselves, as the agent build links `crypto/hpke` already.

### On the agent

- The agent opens the values for one step in memory and hands them to the driver through the call's context (`resource.WithValues`). It clears them when the step ends. They go into no log, error, plan, file, Compose file or image. `agent.Desired` hears of the step with the call's own context, which holds none. [ADR 0054](0054-the-agent-keeps-its-desired-state.md) changes that last part: the agent keeps them, sealed, in its cache of what its server should run, and in no other file.
- **On Docker.** The service driver builds the container's environment with `binding.Environment(ctx, svc)`: the app's own variables, then each value under the name the service sees. It runs a copy of the app with that environment (`binding.App`), so the values go no further than the call, and `environment()` in the container runtime turns them into Docker's. The stored spec keeps references alone, and the config hash leaves every value out. It records which variables and secrets it used, with their revisions and never their values, in the container label `dockwell.uses`. `binding.Restore` reads the service back from that label, so observing a service gives its spec, pins and all, and drift compares like with like. A name the label has and the container's environment doesn't reads as no longer used, so it shows as drift.
- **Drift sees that a service has a value, and never what it holds.** A variable gone from a container reads as no longer used, and so does a bare name, as what runs hasn't got it, and either shows as drift. A variable set by hand to an empty or a wrong value reads as no drift. Nothing that reads a container has the value to compare it with: an agent holds one for a step and no longer, and the config hash leaves values out. Offering that comparison is what this record is careful not to do, and a keyed hash of a value on the container would be that comparison, so there is none, by decision. Changing a value takes Docker on the server, which is as good as root there, and root on a server has what runs on it whatever drift says. `TestDriftSeesThatAValueIsThereAndNeverWhatItIs` holds each of these. The one trace is in the words a value fills: a command that names it no longer comes to what Docker has if only the environment changed, and reads as `binding.Unread`, which is drift.
- **`agent.Desired` gets the whole spec, and none of the values sent with it.** It hears of each step with the pinned spec, which names what the service uses and at which revision. Values sealed to a stream are useless after it ends, so a cache can hold nothing that opens them. A spec also holds what is written in it, a container's own `env` and a volume's options, a CIFS password among them. So the cache that keeps specs on disk (#32) has to seal them, as the store does, and nothing sets `Desired` until it does. A server that restarts a service on its own while the control plane is away (#32) needs the values from the control plane again. Docker keeps running containers running meanwhile. [ADR 0054](0054-the-agent-keeps-its-desired-state.md) changes this: `agent.Desired` hears of a step's values too, and the agent's cache keeps them sealed under a key of its own, for what its server runs now.
- **Docker itself** keeps a container's environment in its own configuration, on the server's disk, readable by root. That is Docker's, not Dockwell's, and anyone who is root there can read a running process's environment anyway. Files under `/run/secrets`, on tmpfs, avoid it for images that read `*_FILE` variables; they come later, through the same seam.

### Compose files

- **An export holds no secret, and keeps what a service uses.** A secret a service uses is written by name alone, as `KEY: null`, for `docker compose` to take from its shell, and listed in `omitted`, as a container's own environment is. A variable it uses isn't secret, so its value is written, as ADR 0021 expected. The label `dockwell.uses` goes in too, names and revisions alone, with `env:KEY` in `dev.dockwell.set` for each. So a container `docker compose up` makes from the file reads back as the service, and shows as drift only if the shell had no value for it.
- **Importing an export keeps those uses.** The label says what a name in `environment` is. A name it lists is a reference, and the file's value for a variable is the one the export wrote, so importing the file again plans no change, restarts nothing and loses nothing, with `remove_orphans` too, which never takes variables or secrets. Taking a name out of the file stops using it, and the plan says so.
- **What can't be kept is refused, by name.** A variable the file gives another value is set twice, so it is refused rather than dropped. So is a secret given any value, in the file or in the request: a file's value is never compared with a secret's, so importing one can't confirm a guess. A name with no value and no label is refused as before, and so is a label naming a kind a service can't use. A service can use only what its environment has, as for any edit.
- **A container's own environment and a volume's options stay as ADR 0021 has them.** An export writes the one by name alone, and leaves out the other. Importing the file asks for the first in `variables`, where a value that matches is no change, and keeps a volume's options, as it gives none, and says so. Nothing is lost either way.
- **What runs names a value, with no value of its own in the file,** as [above](#a-command-an-entrypoint-and-a-health-check-name-values-too) says.

### Revealing a value, and changing how you sign in: a step-up

- **`RevealSecret` needs three things:**
  - a signed-in session;
  - a proof from `FinishStepUp` for revealing that secret;
  - nothing but a person: no API token can call it, whatever its scope.
- **A step-up is a fresh passkey assertion** that confirms one action on one target in one session (`AuthService.BeginStepUp`, `FinishStepUp`):
  - The options allow only the person's own passkeys for this address that aren't flagged as copied, and require user verification. Finishing checks the assertion against every passkey the options allowed, and it must come from one of them.
  - Finishing checks the assertion, its counter and copies as sign-in does, in one transaction, and audits it as `auth.step_up`, or `auth.step_up_failed` when refused.
  - It returns a proof of 256 random bits. Only the proof's hash is kept, in memory. It works once, within a minute, in that session, for that action and target. A proof given for anything else is spent all the same.
- **Changing how you sign in takes one too.** Otherwise a stolen session could add a passkey of its own and pass every step-up with it. Each of these needs a proof for itself, as its request's `proof`:

  | Action | Method | Target |
  | --- | --- | --- |
  | Adding a passkey | `BeginAddPasskey` | you |
  | Removing a passkey | `RemovePasskey` | the passkey |
  | Setting up codes, which ends with recovery codes | `BeginTotpSetup` | you |
  | Turning codes off | `DisableTotp` | you |
  | Making new recovery codes | `RegenerateRecoveryCodes` | you |
  | Creating an API token | `TokenService.CreateToken` | you |
  | Applying a plan that's as good as root on a server ([ADR 0021](0021-the-docker-driver.md#host-access)) | `ChangeService.ApplyChange` | the change |
  | Saving a file that's a way back onto a server ([ADR 0032](0032-files-on-a-server.md)) | `FileService.SaveFile` | the server and the path |

  - **Everything else is checked first, and the passkey asked for last.** Called without a proof, each action, revealing included, checks what else would refuse it: the last way in, codes that are off, a token's name or the most tokens, a secret that isn't there. Only then does it refuse with `needs_step_up`. The panel calls each so, and asks for the passkey only when that is the answer, then calls again with the proof. A proof given is spent only once nothing else refuses, in the transaction that acts, so a refusal for another reason neither prompts for a passkey nor costs one.
  - The ceremony that adds a passkey works only in the session that began it.
  - **Setting up codes finishes where it began.** It ends in recovery codes, which sign in and add a passkey, so it is held as tightly as the step-up that began it. The pending secret is bound to the session that proved that step-up, for 10 minutes, and any other session is told nothing is waiting, however many codes it tries. 5 wrong codes discard the secret, which is on the timeline as `totp.setup_discarded`, so starting again takes the passkey. The count is its own, on the user's row (migration 0016): sign-in's limits count by email and source address and lock sign-in itself, and a wrong code here says nothing about signing in. Closing the sheet forgets the secret (`CancelTotpSetup`). The other pairs that begin and finish hold no such state: the ceremonies that add a passkey and step up are in memory, for 5 minutes, one use, in the session that began them; claiming takes its link at both ends; and signing in takes the passkey.
  - `RemovePasskey` is `POST /v1/passkeys/{id}:remove`, so its proof is in the body, never in a URL.
  - Revoking sessions and tokens, signing out and unlocking codes need none: they take access away, and someone who lost their passkey must still be able to.
- **Someone with no passkey here adds one by signing in again.** That is how someone adds one after adding a domain, or after losing every passkey they had. A sign-in that needed no passkey here confirms adding one, as a step-up would, within 10 minutes of signing in, and only:
  - **a link from `dockwell recover`**, which takes a shell on the control server;
  - **a recovery code**, as getting back in after losing your passkey is what codes are for. Adding a passkey so is a security event on the timeline of its own, `passkey.add_with_recovery_code`, which Activity shows as worth a look, naming the passkey;
  - **an authenticator code, only when no usable passkey is registered for this address**, as after adding a domain. A member with no shell has no other way there. A code is phishable in real time, and with a passkey here, one phished code would otherwise become a passkey, then a token, then every secret. Where there is none, that risk stays, as [sign-in.md](../security/sign-in.md#known-gaps) lists; adding one so is a security event too, `passkey.add_with_authenticator_code`.
  - **It is used once.** Adding one passkey ends it for that session, which the session's row records (`sessions.added_passkey_at`) in the transaction that stores the passkey, so neither a restart nor a second ceremony begun beside the first gets another.
  - **The window is checked at both ends.** Finishing the ceremony checks the 10 minutes again, and the rest of the rule, so a ceremony begun at the last minute can't stretch them.
  - It confirms nothing else. A passkey sign-in confirms nothing, as a step-up with the passkey is at hand.

  Asked to add a passkey otherwise, `BeginAddPasskey` says a step-up is needed (`needs_step_up`), or with no passkey here to give one, to sign in again (`needs_fresh_sign_in`), as `BeginStepUp` does. The audit log says which confirmed each passkey added. Claiming makes the first passkey in its own transaction, as before.
- **Revealing reads the value and records `secret.reveal` in one transaction:** who, which secret and revision, from where. If the record can't be written, nothing is revealed.
- **Reveals are on the timeline** among access events ([ADR 0020](0020-the-event-timeline.md)), as "Revealed the secret DB_PASSWORD", and so are rotations of the key-encryption key. Step-ups, and refused ones, stay in the audit log with the other attempts.
- **No token, three times over.** A method option, `(dockwell.v1.needs_session)`, puts `RevealSecret` beyond every token in the interceptor. The handler and the auth service refuse a token's principal as well. AuthService, where step-ups begin, was already beyond tokens. The PRD's later `connections:read` scope would be a new scope, decided on its own.
- **No authenticator-code fallback.** A step-up's worth is that a stolen session can't make one: it needs the person's authenticator, bound to this origin, with their fingerprint, face or PIN. A six-digit code is guessable within code sign-in's limits, and phishable in real time by whoever holds the session. Nobody needs to reveal a secret to use it, since binding isn't reading, and someone without a passkey here can sign in again, add one and then reveal.
- The ceremony and proofs live in memory, like sign-in's, on one control plane.

### The API, the CLI and the panel

- **Changing variables and secrets is ChangeService's,** as edits of kind `variable` and `secret`, so every change is a plan, with undo and the timeline.
- **`VariableService`** reads an environment's variables and secrets (`ListVariables`, `GET /v1/variables`), by name, a page at a time: each variable's value, never a secret's, and the services that use each, under each name they use it as. It opens no sealed spec. It also reveals (`RevealSecret`, `POST /v1/secrets/{id}:reveal`).
- **The CLI is generated, as ADR 0019 has it.**
  - `dockwell variables` and `dockwell secrets` hold the kind's `create`, `update` and `delete` beside the service's `list` and `reveal`: a kind's verbs join a noun a service's methods already have, and the noun's help names them all.
  - A sensitive scalar field takes no value on the command line. Its flag names a file, `--value-file path`, or `-` for standard input, which asks without echo on a terminal. So a secret stays out of shell history and the process list, with no option of its own. It reads at most what a secret holds, 64 KiB.
  - A flag that takes a message as JSON, such as `dockwell changes propose --edits`, takes it inline, from a file with `@file`, or from standard input with `-`. Inline JSON that sets a secret's value is refused, and the error says to use `--edits @file` or `--edits -`. A test keeps that the only flag that may hold one, beside `--value-file`.
  - A workload's environment is configuration, as `docker run -e` has it: masked in plans, not a secret boundary. So `--env KEY=VALUE` works, and so does a container's `env` in inline JSON. Anything secret belongs in a secret.
  - A CIFS mount's password has nowhere to go but a volume's `o` option, so it stays off the command line as a secret's value does (`volume.HoldsPassword`: an option named `password`, `pass` or `password2`, or an item of one in a list). A volume's `--options` takes such an option from the environment alone, as `--options o`; inline JSON that gives one is refused, as a secret's value is; and `--compose`, marked `(dockwell.v1.from_file)`, reads a file, `@compose.yaml`, or standard input, and refuses a file on the command line that gives a volume one. The refusal never repeats the value. `--variables` is like `--env`: a value the file takes from it is on the command line, so keep a password in the `.env`, `--env-file`.
  - Kinds that run on no server have no `--on`, and fields Dockwell sets have no flag.
  - `dockwell secrets reveal` needs a person, and says to use the panel.
- **The panel's screen is an environment's variables and secrets,** at `/variables`, following `App-Environment`. Its environment switch shows once there are two environments. You reach it from the command bar, which has an entry for each environment once there are several, from the More tab on phones, which it sits under, and from Activity, where a change to a variable or secret, and a reveal, link to its environment: a reveal's event names the secret's environment as its subject's `scope`. The app screens (#31) will show an app's slice of the same list. Adding, editing and removing each open the plan sheet straight away, rather than the mock's tray of unapplied edits: one review step, the plan sheet, serves one edit. A secret shows masked, with Reveal, which asks for the passkey, then the value with Copy and Hide. It hides again after a minute.

## Consequences

- Every spec that may hold a secret is encrypted at rest, and a plan never carries one, so the PRD's security row holds for containers and services too, not only secrets.
- A backup of the database is safe to store apart from the key file, and useless without it. Losing the key file loses every secret, the CA and authenticator secrets with it, as before: the install guide says to back it up apart.
- Each sealed spec costs a row in `data_keys` and two AES-GCM operations to read. Reading a spec now takes a transaction, which every reader already had.
- Every service that uses a value restarts when it changes, in the change that changes it, one server at a time, as its driver plans. Rolling restarts with two replicas, and keeping the old value valid until every replica is healthy, as the PRD's rotation describes, come with replicas.
- A change can go out of date because of a value it uses, not only its own resources, and says which.
- The agent can't restart a service that uses secrets on its own while the control plane is away. #32 decides whether its cache keeps values sealed to a key of its own, a trade of principle 5 against what a stolen disk holds. [ADR 0054](0054-the-agent-keeps-its-desired-state.md) decides it does, and what that costs: a copy of the agent's data folder carries the key, so it opens anywhere; and an agent that connects with a stolen identity and an empty cache is sent every value its server runs, which goes on the server's timeline.
- Change items planned before this, for a server that was offline, may still hold a container's environment unsealed. They can't apply: no agent had drivers then, and now they are refused as unsealed. Discarding them doesn't erase them. No install is known to have any. A change an earlier version left applying finishes on the next start, under the scheme it was planned with; one holding such a spec in the clear would be refused, stay applying and say why, and hold up no other. None can exist in a release, as committing one took an agent with drivers.
- Revealing needs a passkey for the panel's current address. After adding a domain, add a passkey there first, as for sign-in: sign in there with a code, a recovery code or a link from `dockwell recover`, then add it within 10 minutes. The panel points to `dockwell recover` there, which needs no code.
- A stolen recovery code, with the person's email, is still a way to add a passkey of one's own, then make a token, then reveal secrets. That is what a recovery code is for; it is 80 random bits, works once and is shown once, and adding a passkey with it is a security event on the timeline, where the person sees it and can remove the passkey, revoke the session and make new codes.
- A stolen session can't add a passkey, codes or a token of its own, nor remove the person's: each takes the person's passkey, just now. People without a passkey at an address make one in the minutes after signing in some other way, and every change to how they sign in prompts for the passkey, as revealing does.
- Each change records how its fingerprint was made (`changes.fingerprint_scheme`), each of its items whether it rotates (`change_items.rotates`), and each revision of a service what it uses (`revision_uses`). None holds a value, and each is history like the rows beside it: triggers on both databases refuse to change or delete it, as for revisions and changes (ADR 0009).
- A value in a command is in the container's environment too, which a Compose file wouldn't do, and a value that isn't secret is hidden as one that is. A plan shows `--port=${PORT}`, and nobody reads the number there.
- A label now holds a command that names values, so a container carries its command twice, once as names.
- The threat model is in [docs/security/secrets.md](../security/secrets.md).
