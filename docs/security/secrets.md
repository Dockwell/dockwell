# Secrets: threat model

How Dockwell keeps an environment's secrets, and every spec that may hold one, encrypted at rest. It also covers how it gets them to the servers that run what uses them, and how a person reveals one. It says what an attacker could try, and what stops them. The design is in [ADR 0022](../adr/0022-secrets-encrypted-at-rest.md), beside sign-in's threat model in [sign-in.md](sign-in.md). The code is in `internal/secrets`, `internal/delivery`, `internal/resource/binding`, `internal/resource/variable`, the revision store in `internal/revision`, `internal/auth/stepup.go` and `internal/control/variables`.

## What there is to protect

| Asset | Where it lives | Why it matters |
| --- | --- | --- |
| Secrets' values | Sealed in `revisions` and `change_items`, in `<data>/control/state.db` or Postgres; in memory on the control plane while it reads one; in memory on an agent for one step; in the running container's environment | They are the credentials the apps use: databases, payment providers, storage |
| Containers' and services' environments | Sealed the same way, as their specs may hold a secret | People put credentials there too |
| A volume's options | Sealed the same way, as a CIFS mount's password goes in them. Docker keeps them with the volume on the server | A password for a file share |
| The install's key | `<data>/control/key`, 0600 | It opens every key-encryption key, so every secret, the CA's key and the authenticator secrets |
| Key-encryption keys | `key_encryption_keys`, sealed with the install's key | Each opens every data key wrapped under it |
| Data keys | `data_keys`, wrapped under a key-encryption key | Each opens one stored spec |
| An agent stream's delivery key | The agent's memory, for one stream | It opens the values sent on that stream |
| Step-up proofs | Hashes in the control plane's memory | Each reveals one secret, once, within a minute |

## Trust boundaries

- **The control server** is trusted with everything above, as for sign-in. Whoever is root there, or the user that runs dockwell, has the key file and the database, so every secret.
- **A database backup, or the database server alone,** is untrusted. Postgres may run elsewhere, and backups travel.
- **Each server's agent** is trusted with the secrets of what runs on it, and with nothing else. Root on a server can read what runs there, through Docker or `/proc`, so nothing hides a server's own secrets from its root.
- **The network between agents and the control plane** is untrusted, as for every other message, beneath mTLS.
- **People with a session** may use secrets: bind them to services, rotate them, delete them. Revealing a value takes them, at the keyboard, with their authenticator, each time.
- **API tokens, and wherever they are kept,** are untrusted with values. The API never returns a value without a step-up, which no token can make. That is the boundary, not that a token can't learn one: write access to a scope can read its values through a workload, as [known gaps](#known-gaps) says.
- **Logs, plans, the timeline and the audit log** are read by more people, and kept longer, than secrets should be: Dockwell puts no value there of its own accord. A Compose file can: a value it writes outside `environment`, such as in a command, is part of what it asked to run, and a plan shows that, as [known gaps](#known-gaps) says.

## Threats and mitigations

| Threat | Mitigation |
| --- | --- |
| A database backup, or a copy of the Postgres database, leaks | Every spec of a kind that may hold a secret is sealed under a data key of its own. Data keys are wrapped under a key-encryption key, which is sealed with the install's key, a file never in the database. Plans mask what changed, and fingerprints digest such specs with a key derived from the install's key, so a guess at a password can't be checked against them. Audit events name a reveal, never the value. A test reads every row of every table, on SQLite and Postgres, after secrets are made, used, rotated, undone, discarded, left planned and revealed, and finds no value in any encoding. That holds for every value that was only ever a secret: one that was a plain variable before it was made a secret stays in the variable's revisions, in the clear. |
| A variable is made a secret, and its value, which may have been a secret all along, shows in the switch's plan, in Activity and to read-only tokens | A plan where a name changes between a variable and a secret, in either direction, masks the value on both sides; tested on the plan as it is kept, for the switch, its undo and a rollback of it. The panel doesn't carry the variable's value over: it asks for a new one, and says that the old value stays in the variable's history and should be rotated where it was issued. |
| The install's key leaks with the backup | Then everything opens, as it was meant to: the key is what makes the backup the install's. Back the key file up apart from the database, and keep it 0600, which `dockwell run` checks. |
| A sealed spec is copied to another row, to read it as that one: a production secret into a staging one someone may reveal, or a leaked value into the revision that rotated it | A spec is sealed with where it is stored as associated data: its resource's ID and kind, and the revision's number, or the change's ID and the item's position. So it opens only where it was sealed for. Tests move one to another resource, kind, revision and change item, and fail to open it, and reveal and plan from a revision whose row holds another revision's spec, and are refused. |
| Someone with write access to the database, and not the key file, puts a spec of their own in the clear where a sealed one belongs, such as a container with their image | A spec of a kind that may hold secrets must be sealed, and one stored in the clear is refused when it is read; tested by revealing and planning from such a row. |
| A key-encryption key leaks, or might have | `dockwell rotate-key` makes a new one, wraps every data key under it and retires the old, forgetting it, in one transaction, and the audit log records it. A running control plane holds a key-encryption key only for the transaction that unsealed it, so it forgets the old one too, with no restart; tested with a data key put back under the retired key. A copy of the old key opens only data keys from a backup taken before. |
| Stored specs are changed, such as a value swapped | Every seal is AES-256-GCM: a changed byte fails to open, and the change fails rather than run something else. |
| A plan, the timeline or an error shows a value | Fields that may hold one are `(sensitive)`, and a value a Compose file writes in any other field shows, with the plan saying so, as [known gaps](#known-gaps) says. Diffs say they changed and never show them, and the API blanks them again on the way out. What an agent reports is masked by the schema's own field paths, not by what the agent says, so an agent that gets it wrong can't put a value in a plan; tested. A map's key is read as a key, dots and all, so a label such as `traefik.enable` still shows, and a path the schema doesn't have is masked. So is a path that names a whole message holding a sensitive field, such as a service's `app`, which holds its container's environment; tested for services and containers. Drivers' errors, which reach plans and progress, name what is missing, never a value; tests check theirs. A rotation's plan shows each service's revision of the secret moving, as `revisions[DATABASE_PASSWORD]: 3 → 4`. |
| A server receives secrets it doesn't run | The agent stream asks for the values of a step's spec only when it applies it. The keeper refuses unless the service's latest revision is placed on that server and is that spec, and then reads only what the spec uses, at the revisions it pins. Tested by asking for another server and for another spec, and across two real agent streams. |
| A message on the agent stream is read or replayed | Values travel sealed with HPKE to a key the agent made for that stream and keeps in memory, bound to the server and the resource, beneath mTLS. They can't be opened for another resource or server, or once the stream ends. A step the agent refuses as it moves to a renewed certificate goes out again on its next stream, sealed again to that stream's key; tested with a drain mid-apply. |
| An agent's disk, or a snapshot of it, holds values | The agent writes none: it opens them in memory for one step and clears them after. `agent.Desired` hears of specs that name what they use and at which revision, with a context that holds no value; tested. Docker keeps a running container's environment in its own configuration, on the server's disk, as for any container. That is the server's root's to read anyway, and files on tmpfs for `*_FILE` variables come later to avoid it. |
| A container's label gives a value away | The `dockwell.uses` label names what a service uses, its kind and its revision, never a value. |
| A Compose file gives a value away | An export writes a secret a service uses by name alone, and a variable's value, which isn't secret. `docker compose` takes the secret from its shell. The label it carries holds names and revisions. |
| Someone who may propose imports a Compose file with a guess at a secret, to see from the plan whether it is right | A file that gives a secret any value is refused as set twice, whether or not it is the value there: a file's value is never compared with a secret's. A secret a service uses can only be named in a file. |
| What the store keeps in the clear about uses gives a value away | `revision_uses` names, for each revision of a service, what it uses, under which name, and the revision it is pinned to, never a value. It is how the store finds a value's services, and lists them, without opening a sealed spec. The dump test reads it with every other table. |
| A developer binds a production secret to read it | Binding is an edit of the service: the plan shows the binding, and the change is on the timeline. Its value goes to that service's container, so someone who can deploy any image can read what that image is given; that is deploying, not reading, and both are on record. Revealing through Dockwell takes a passkey and is audited. Roles that may deploy but not bind production secrets come with roles. |
| An API token reveals a value, or begins a step-up | `RevealSecret` is marked `(dockwell.v1.needs_session)`, so the interceptor refuses every token for it. Its handler and the auth service refuse a token's principal too, and step-ups begin in AuthService, which no token reaches. Tested over every protocol with read-only and read-write tokens, and with a token holding a person's fresh proof. |
| A script with someone's session cookie reveals values | It needs a fresh passkey assertion for each secret, which needs the person's authenticator and its user verification. A proof works once, within a minute, in its session, for one secret. |
| Someone with a stolen session adds a passkey of their own, then steps up with it | Adding a passkey takes a step-up with one the person already has for this address, as do removing one, setting up or turning off codes, making recovery codes and creating an API token ([sign-in.md](sign-in.md)). Only a session signed in with a recovery code or a link from `dockwell recover`, or with an authenticator code where no passkey is registered for this address, adds one without, once, within 10 minutes of signing in, checked again as it is stored. Tested through the API and in `make e2e`. |
| A refusal for another reason costs a passkey prompt, or a proof | Every action a step-up confirms checks everything else first, and asks for one with `needs_step_up` last; the panel calls without a proof, and prompts only then. A proof given is spent only once nothing else refuses. Tested for each action. |
| A step-up proof is replayed, or used for another secret, session or action | Proofs are 256 random bits, kept as hashes and taken out when used, whatever they are used for. Each is bound to the session, the action and the target, and expires after a minute. Tested for each. |
| A person with two passkeys here can't step up, so reveals with none | Finishing checks the assertion against every passkey the ceremony allowed, and that it came from one of them. Tested with two, and in `make e2e`. |
| A passkey assertion is replayed into a step-up | Each ceremony's challenge is random, works once, expires after 5 minutes, and is bound to the session and site that began it. An answer to another ceremony is refused and audited. |
| A copied passkey steps up | Its counter is checked against the stored one in the same write transaction as at sign-in. A count that goes back flags the passkey, refuses it and audits it. |
| A reveal goes unrecorded | The value is read and `secret.reveal` recorded in one transaction; if the record fails, nothing is revealed. Each step-up is recorded too, refusals included. |
| A secret lands in shell history or the process list | The CLI reads a secret's value from a file or standard input, `--value-file`, never from a flag's text, and asks without echo on a terminal. JSON on the command line, such as `dockwell changes propose --edits '<json>'`, is refused when it sets a secret's value, and the error says to pass `--edits @file` or `-`; tested, with a test that keeps that the only such flag. A container's environment can go on the command line, with `--env KEY=VALUE` or in that JSON: it is configuration, masked in plans, not a secret boundary. Anything secret belongs in a secret. |
| Someone who may propose, such as a read-write API token or a stolen cookie with no passkey, guesses a secret's value and proposes it, to see from the plan whether it is the one there | Setting a secret's value is a rotation: it plans as a change, and restarts what uses the secret, whatever the value is, and it is never compared with the one there. The counts, actions, steps, downtime and wording are the same for a right guess and a wrong one, and so is the work proposing does. An undo and a rollback rotate it too. A fingerprint digests a sealed spec for its change alone, so a guess's can't be matched with an undo's that puts an old value back, or with someone else's planned change. Tested through the engine, and through the API with a read-write token. This closes the API's equality oracle for secrets. A workload's inline `env` isn't covered: it compares as usual, as edits carry whole specs, so rotating it would make every apply restart, and a token can read its values through a workload anyway. Use secrets for anything secret. |
| A rotation leaves some service on the old value | A change to a variable or secret takes in every service that uses it, and its plan lists them. Applying checks that the pins still hold and that no service started using the value since; otherwise the change is out of date. Tested both ways. |

## Known gaps

These are tracked and not yet covered:

- **A value a Compose file writes outside `environment` shows, whether it comes from an `.env` or from `variables`.** With `command: redis-server --requirepass ${PASSWORD}`, the value is in `app.command`: in the plan, in the `changes` table, through `GetChange` and `ExportCompose`, where a read-only token can read it, and in `docker inspect`. A health check, a label, a port, a mount and every other field a spec keeps but `environment` and a volume's `driver_opts` are the same. Refusing it isn't an answer, as `--port=${PORT}` is legitimate, so the plan says so instead, by variable and field and never by value, with how to keep it hidden. If the file writes a value into a field that can't take it, such as `restart: ${PASSWORD}`, the refusal can repeat it, and so can the log. [#96](https://github.com/Dockwell/dockwell/issues/96) is the fix that keeps the value out.
- **A session signed in with a recovery code or a link, or with an authenticator code where no passkey is registered, adds one passkey without one, within 10 minutes.** That is how someone without a passkey at an address gets one; a cookie stolen in those minutes, before the person adds theirs, could add its own. A stolen recovery code does the same, and so does a phished authenticator code where no passkey is registered; each is a security event on the timeline. See [sign-in.md](sign-in.md#known-gaps).
- **Deleting a variable, then making a secret of its name in a later change,** can't be linked as a switch, so the delete is the plan of a plain variable, which shows its value.
- **A variable made a secret keeps its old value in its history,** in the clear, as a variable's value always was. The panel asks for a new value and says to rotate the old one; nothing erases the history, as revisions never change.
- **Deploying is reading.** Write access to a scope can read its values through a workload: whoever can deploy an image with a secret bound, such as a read-write token or a stolen session, can make it print the value, or send it out. So the boundary is that the API never returns a value without a step-up, not that a token can't learn one. Roles that separate binding production secrets from deploying come with roles.
- **The old value stays valid until every replica is healthy** isn't there yet: a service restarts with the new value at once, one server at a time. It comes with replicas.
- **Docker keeps a container's environment on disk.** Values as files on tmpfs, for images that read `*_FILE`, come later, through the same seam.
- **The agent can't restart a service that uses secrets while the control plane is away.** Docker keeps running ones running. #32 decides whether to keep values sealed to a key of the agent's own.
- **Rotating the install's key itself** has no command yet. It would seal again the key-encryption keys, the CA's key and the authenticator secrets.
- **Proofs and ceremonies live in one control plane's memory,** as sign-in's do. A highly available control plane needs shared state for them.
